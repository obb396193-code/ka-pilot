# B1b 回灌、聚合与数据对平设计

> 日期：2026-08-19
> 状态：老板已批准推荐方案；实现分支 `be/b1b`
> 上游：R-008、契约 v1.1、B1a SHA `f98952f`

## 1. 目标与边界

B1b 要把 B1a 的可用组件连成可恢复的数据生产链：90 天历史离线数据可断点回灌，raw 可重复抓取但 canonical 不重复计算，派生口径只由 domain 纯函数产生，每个日期聚合后自动执行数据质量检查，并让实时任务始终优先于历史任务。

本批不做真实内网启航联调，不猜 HTTP 200 业务鉴权码，不实现 B1c 的 Web API，也不新增契约未冻结的业务表。

## 2. 方案比较与选择

### 方案 A：每天复用 `etl_full`（不采用）

优点是代码少。缺点是现有 full 每次都会重新发现账户、抓 D-1 离线数据和连续 7 天实时数据；90 天会产生大量重复请求，历史和实时语义混杂，失败恢复也无法精确到目标日。

### 方案 B：协调器 + 独立 `backfill_day`（采用）

`backfill_historical` 只做账户发现和日任务扇出；每个 `backfill_day` 只抓一个目标日的 `account_offline`。日期之间完全独立，单日失败不阻塞其他日期，能够精确重试和展示进度。通过确定性 job UUID 保证协调器或阶段衔接重试时不重复入队。

### 方案 C：按 7/30 天范围批量请求（暂不采用）

请求次数最少，但失败后只能整段重跑，`cursor_date` 和单日质量检查难以准确表达；接口的最大日期范围与分页边界尚未内网实证。待 B7 确认媒体约束后再考虑批量优化。

## 3. 任务与优先级模型

- `etl_incr=1`：实时增量最高优先级。
- `rule_scan=3`：规则扫描居中。
- 普通任务默认 `5`。
- `backfill_historical/backfill_day=9`：历史回灌最低优先级。

数据库当前按 `priority ASC` 领取，因此不能沿用 R-008 原文的 `backfill=1`。协调器给每个日期生成稳定键 `backfill:{backfillId}:{ds}`，应用层转成确定性 UUID，`INSERT ... ON CONFLICT DO NOTHING`。同一批次同一天只会有一个子 job。

`backfill_jobs.cursor_date` 表示已经进入终态的最高连续日期，不简单记录“最后完成的乱序日期”。失败日达到最大重试后也属于终态，因此不会永久卡住后续日期；批次最终状态区分 `done` 与 `partial_failed`，失败详情保留在 `jobs` 和 `etl_runs`。

## 4. 数据流水线

```text
backfill_historical
  ├─ 一次账户发现
  ├─ N 天确定性 backfill_day job
  └─ backfill_jobs = running

backfill_day(ds)
  ├─ account_offline(ds, ds)
  ├─ raw append(resource + request_params + payload)
  └─ 确定性 canonical_merge(ds)

canonical_merge(ds/range)
  ├─ 每账户/日/resource 取 latest raw
  ├─ domain 合并与派生指标
  ├─ 生效考核价与渠道系数快照
  ├─ canonical upsert
  └─ 确定性 data_quality_check(ds/range)

data_quality_check
  ├─ total_reconciliation
  ├─ cpa_outlier
  └─ missing_consecutive_days
```

raw 保留所有抓取历史用于审计，聚合和对平必须先按 workspace/account/ds/resource 取最新行，不能把重试生成的重复 raw 直接求和。

## 5. 口径与对平

canonical 继续使用 `mergeAccountCanonical` 和 `computeDerivedMetrics`，不允许 Agent 或 SQL 各算一套。历史均值调用 `excludeZeroSpendDays` 的同一规则；考核价和渠道系数按指标日期取生效版本；`field_sources` 记录 offline、realtime、gap_filled 与 derived。

三类检查：

1. `total_reconciliation`：比较 canonical cost 与最新 offline raw `cost_api` 总额。允许差异为 raw 总额绝对值的 0.1%；raw 总额为 0 时要求绝对差异为 0。
2. `cpa_outlier`：`real_cpa > 5 × assessment_price_snapshot` 时设置 canonical `data_anomaly=true`，并把账户样本写入检查记录。
3. `missing_consecutive_days`：在账户应处于活跃期的日期范围内，连续两天没有 canonical 时失败并写 outbound 告警。

每次检查写 `data_quality_checks`，包含 sample、passed、delta 和 checked_at。检查失败不回滚已完成的 canonical，只产生可追踪状态和告警。

## 6. Lease 与失败恢复

Worker 启动时把 lease 超过 10 分钟且仍为 leased/running 的 job 重新排队。处理 job 期间按 lease 时长的一半发送 heartbeat 延长 lease，避免启航单次请求最长 120 秒时被第二 Worker 重复领取。

普通错误继续指数退避；`blocked_auth` 不重试并只通知凭证 owner；达到 max_attempts 后标 failed 并通知 workspace 管理员。回灌子任务失败不会阻止其他日期被消费，批次完成阶段汇总成功/失败数量。

## 7. 留痕与测试

`etl_runs.scope` 记录 workspace、credential owner、日期范围和 resource；`step_failed` 使用 `fetch:* / parse:* / persist:* / merge / aggregate / quality:*` 前缀；rows_ingested 记录 raw 或 canonical 行数。耗时由 finished_at-started_at 计算。

测试分三层：

- domain：指标边界、零耗日、CPA 异常规则。
- repository/worker：确定性入队、优先级、lease heartbeat/回收、断点推进、三类质量检查、失败告警。
- PostgreSQL 冒烟：生成 10 账户 × 90 天 mock raw，跑完整 canonical 与对平，断言 900 行 canonical、三类检查通过并输出进度证据。

## 8. 审查注意事项

审查以本设计和 `inbox-arch.md` P-005 为准，不以 R-008 中“每日复用 etl_full”和“backfill=1”的字面描述为准。真实启航数据与错误码仍须 B7 内网验证，mock 通过不等于真实 API 已联通。
