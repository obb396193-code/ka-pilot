# B3 安全执行内核设计

> 日期：2026-08-19
> 状态：老板已批准“真实执行留适配口、内部安全内核先行”路线
> 实现分支：`be/b3`

## 1. 目标

实现不依赖 Multica/快手真实协议的变更集安全核心：状态机、30 分钟 TTL、确认前 from-value 复核、逐项 dry-run/执行结果、幂等执行、UNKNOWN 禁止盲重试、反向变更集草稿和完整执行审计。

本批不宣称完成真实调价。生产写链路仍必须经过 webhook→agent→CLI→`RESULT_JSON`，且 demo 期写权限只对老板开放。

## 2. 方案比较

### 方案 A：直接按现有 OS 实证拼生产写链路

已证实 webhook 和 `RESULT_JSON` 能走通，但真实 CLI 写操作请求/回执 schema、取消/继续和业务错误映射并未冻结。直接做会把测试探针当生产协议。不选。

### 方案 B：只做纯状态机

最安全，但无法验证数据库事务、重复确认、部分成功和 Worker 重试边界，价值不足。不选。

### 方案 C：领域内核 + PostgreSQL 审计 + 执行端口

内部状态和持久化按现有 schema 实现；真实读取当前值、dry-run、execute、UNKNOWN reconcile 均定义端口并用 fake 验证。OS 契约冻结后再补适配器。选用。

## 3. 边界与已知契约缺口

- `changeset_items` 没有账户归属，campaign/unit/creative 无法可靠取得同账户锁键；本批只锁 changeset，自身不假装实现同户冲突锁；
- `from_value/to_value` 是 TEXT，无法区分数字、布尔、对象和媒体默认值；内部比较采用严格字符串快照，不发明 JSON 编码；
- `execution_runs.status/result_payload` 没有冻结枚举和回执 schema；本批使用内部类型，数据库原样存 JSON；
- `changesets.status` 有枚举注释但无完整动作转换；
- dry-run 是 execution_run，不是 changeset 状态；是否必须 dry-run 成功后才能 confirm 尚未冻结；
- T+1 指标和带外变更依赖 B3 后续结构快照/数据源，本批只留调度端口。

以上写 P-006，不修改 `packages/contract/`。

## 4. 组件

### 4.1 领域状态机

`packages/domain/src/changesets.ts`：

- 允许的状态迁移；
- TTL 检查；
- 当前值与 from-value 的逐项冲突报告；
- dry-run 和 execute 的逐项结果聚合为 success/partial/failed/unknown；
- UNKNOWN 明确返回 `reconcile_required`，禁止 execute retry；
- 反向草稿只交换成功项的 from/to，未成功项不进入回滚。

### 4.2 PostgreSQL Repository

`packages/db/src/changeset-repository.ts`：

- 原子创建 header + items；
- 所有查询通过父 changeset 强制 `workspace_id`；
- `SELECT ... FOR UPDATE` 保护确认和状态变化；
- 同一 changeset 重复确认幂等；
- execution_run 按 attempt 留 request/result；
- 执行结果逐项更新 `item_status/fail_reason` 并聚合 header；
- UNKNOWN 之后普通执行领取直接拒绝。

不新增迁移，不依赖不存在的唯一约束。

### 4.3 Worker 执行编排

`apps/worker/src/changesets/changeset-execution-handler.ts` 依赖：

- `CurrentValueProvider`：确认/执行前读取真实当前值；
- `ChangeExecutor`：`dryRun`、`execute`、`reconcileUnknown`；
- `ChangeSetStore`：状态和执行审计；
- `FollowUpScheduler`：成功/部分成功后安排 T+1。

执行时序：再次复核 from→记录 execution_run→调用端口→逐项落结果→聚合状态→成功项安排 T+1。任何 UNKNOWN 不自动重发，只入 reconcile 流。

## 5. 幂等与故障

- changeset id 是外部 idempotency key；
- Worker 重试前读取状态：success/partial/failed 不重放，unknown 只对账；
- sent/executing 的租约恢复不直接重发，先查询执行结果；
- item 级部分成功完整保留；
- from-value 任一冲突时整单不确认，返回逐项冲突；
- TTL 到期后变为 expired，必须重新生成草稿；
- 数据不新鲜和权限门继续由上层 API/授权层阻断，本批不绕开。

## 6. 验证

- 领域：状态合法/非法、TTL 边界、冲突明细、结果聚合、反向草稿；
- DB：租户隔离、原子创建、重复确认、状态并发、执行审计、部分成功；
- Worker：正常、部分成功、UNKNOWN、执行前冲突、重跑幂等、T+1 仅成功项；
- 四包 tests/coverage/typecheck/lint/audit 与复杂度门禁。
