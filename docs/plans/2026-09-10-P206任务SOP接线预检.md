## 真实执行证据

在 Worker 目录执行 `node --import tsx --input-type=module`，读冻结 graph fixture，把 `{graph,paramsSchema}` 交给真实 `compileWorkflowGraph` 与空 Registry。它在 schema 阶段即拒绝，不是因为假上游没数据，也不是 Registry 缺能力之后才失败。

结果：

```json
{"publicGraph":"workflow-graph/v1","compilerRejectsPublicGraph":true,"issuePaths":["graph.version","graph.nodes.0.kind","graph.nodes.0.capability","graph.nodes.0.inputs","graph.nodes.0","graph.nodes.1.kind","graph.nodes.1.capability","graph.nodes.1.inputs","graph.nodes.1","graph.nodes.2.kind","graph.nodes.2.capability","graph.nodes.2.inputs"],"noExternalIo":true}
```

内部/公开模型原本就有边界，**拒绝本身不是新引擎 bug**；缺的是受控转换和装配。不能改一个 version 字符串或删除 strict 校验绕过去：

- 公开 conditional edges 有 `condition.expr`，内部 edges 只有 id/source/target；静默丢 condition 会执行错误分支。
- 公共 paramsSchema 是 JSON Schema；内部是显式参数数组。
- 内部 Registry ID 为 snake_case 且版本锁定；样例用 `account.open_flow`、`account.recharge_request` 等点号能力名，需要受信映射，不能把浏览器的任意 capability 当可执行句柄。
- 样例 human_confirm/wait_reconcile 等待 24 小时左右，内部单次 capability timeout 最大 15 分钟；需要持久化等待语义，不把进程挂一整天，也不简单扩大单次 timeout。
- stage 的六步与图的十节点不是一一映射；成功事件、分支跳过、失败未知态、人工 stage 覆盖的优先级不可从中文 label 猜。
