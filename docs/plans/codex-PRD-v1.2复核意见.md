# Codex 对 PRD v1.2 的二轮复核意见

> 日期：2026-08-18
> 复核对象：`docs/20-PRD-v1.md`（v1.2）
> 原始基线：`docs/14-老板需求追踪总表.md`（126 条）
> 结论：**有条件通过，但当前不可冻结进入契约，也不应立即生成 v3 原型。** 六项老板终裁和 Codex 首轮意见在能力层面基本补入，但合并后保留了多组相反旧文案，凭证归属、三部署单元、共享数据库和工作流数据模型仍有会直接造成返工的矛盾。

## 三、冻结前必须修正的问题

### P0-1：规范 Schema 与“示意 Schema”互相否定

§3.1 先要求 `workspace_id`、`task_accounts`、raw/canonical 分表、强类型广告实体、变更集四表拆分；紧接着的示意 Schema 却继续使用：

- `users.role` 单列；
- `accounts.task_id` 单值；
- `account_metrics_daily(...source)` 同表；
- `account_structure` 混 campaign/unit/creative；
- 单表 `changesets` 同时承担头和明细。

本文又声明是开发唯一依据，这两套不能并存。契约前应删除旧示意，或直接替换成与硬要求一致的契约骨架；不能写“以后再按意见重构”后仍让开发照旧表开工。

### P0-2：三部署单元与调度、目录、SQLite 不一致

§4.1 已正确拆成 Web/API、Worker/Scheduler、DingTalk Gateway，但其他位置仍写：

- ETL 使用“`node-cron`，常驻 FaaS 进程内”；
- monorepo 只有 `apps/web`，ETL、Agent、Multica、DingTalk 仍全在 `apps/web/server`；
- “历史拓扑”仍展示单 Web 应用承担 Cron/Agent，并把 Chromium 同时放进不同单元；
- demo 继续使用 SQLite 单文件。

三个独立 FaaS 无法共享单机 SQLite 文件。若三单元是终态，daily 联调前必须有网络数据库；SQLite 只能用于单进程本地开发和 mock，不能作为三应用 daily 的共享数据库。代码结构应至少改成：

```text
apps/web
apps/worker
apps/dingtalk-gateway
packages/contract
packages/db
packages/domain
```

调度统一写成 job/outbox + DB lease，删除进程内 cron 的规范性表述。

### P0-3：后台运行的凭证所有权未定义

交互操作使用当前用户自己的 PAT 是清楚的，但下列无活跃请求的运行没有归属规则：定时基建、延迟执行、失败重试、T+1 回查、账户结构同步、Agent 后台任务。

必须在契约中规定：

- 每个需要用户权限的 job 固化 `credential_owner_user_id`、`initiator_user_id`、`workspace_id` 和授权快照；
- 重试始终使用原运行绑定的凭证，不自动换成老板 PAT；
- 用户凭证失效/撤销时进入 `blocked_auth`，通知本人重新授权，不借其他人的凭证继续；
- 老板 PAT 只可临时承担明确列出的服务级 Demo 任务，不可执行属于其他用户的媒体写操作；
- `mcn_` 仅作为正式服务身份路线，能做什么仍按平台实证和最小权限确定。

此外，§3.1/§3.16 写“只存 secret reference”，§6 又写“凭证只进 config vars”。FaaS config vars 适合应用级密钥，不适合每用户三凭证。正式方案必须指定加密凭证库/内部 Secret 服务；数据库只存 reference 和元数据。

### P0-4：工作流存在两套数据模型

正文要求模板和自建流程同一数据模型，并列出 `workflow_definitions/versions/nodes/edges/runs/events`；同节又新增 `workflow_templates(steps JSONB)`。这会导致模板商店与自由画布两套保存、两套版本和两套执行。

应统一为：模板也是 `workflow_definition` 的一种发布态/资产类型；用户复制时产生新的 definition/version；节点、边、参数 Schema、发布版本和运行固定版本全部共用。`workflow_templates.steps JSONB` 应删除或明确只是只读导入格式，不是运行真相。

### P0-5：老板终裁仍有相反旧文案

需要直接删除或改写：

- §3.5 仍写“L1/L2 押后”，§3.15 又写 L0–L3 全做；
- §3.15 先写公共资产五段全套，后面又写“五段生命周期后置”；
- §3.10 仍使用“充值申请提交人批”的表述，§3.16 才说明它只是自愿快捷方式。应统一改成“申请充值协作”，明确不阻断充值动作。

### P0-6：Provider 抽象后仍残留旧通路描述

§3.6 前两行已如实写 IdeaLab 为 OpenAI-compatible、Claude 需另申请或走官方 API；下一行仍写“IdeaLab Anthropic 兼容端点、同一 AK 可切 Qwen/DeepSeek”。应删除旧行，按 Provider Capability Matrix 表达：模型是否支持工具调用、流式、结构化输出、超时/重试和 Claude Agent SDK 协议，必须实测后才能启用。

## 四、导航与页面清单问题

老板终裁的九个入口本身可以采用，但当前文档有四个版本同时存在：

1. 标题写“8 项”；
2. 总表实际是 9 项；
3. ASCII 导航和编号表只有 7 项，漏自动化、知识库；
4. §5.2 又写“顶部导航 7 项”。

§2.2 页面清单也没有承接已经拍板的新入口，至少缺：

- 完整数据总表；
- 工作流画布、工作流详情/版本、自动化运行中心；
- 商品池、素材拆解/相似查找；
- Agent/OS Run 监控；
- 钉钉卡片管理、值守与警报配置；
- 公共资产治理页面或各资产统一治理入口。

在 R-002 生图前必须先统一导航和路由清单，否则 11 张图会继续固化旧七项布局。

## 五、可以保留的改动

以下变化方向正确，无需推翻：

- 工作流恢复模板商店 + 自由画布 + Agent 帮编；
- Gateway 独立成部署单元；
- B1 拆为契约存储、回灌口径、数据服务页面三段；
- 加/关账户、选品、相似查找、群建工作项、Run 监控和 Capability Registry 已补入；
- 开户/充值不强制审批的边界已经写回；
- 当前用户使用自己的 PAT，未绑定时降级只读，方向正确；
- 商品素材按数据可得性决定深度，避免发明接口；
- 工作台警报区、完整数据总表、值守配置归钉钉中心是合理的信息架构补充。

## 六、最终结论

**有条件通过，不可冻结。** v1.2 已经把老板原始需求的能力地图补齐，完全缺失从 8 条降为 0，说明合并方向成功；但它仍不是一份内部一致的开发唯一依据。

建议 arch 只做一次定向清理，不再扩功能：修正上述六个 P0、统一九项导航与路由清单、更新 B7 验收为“模板+画布+Agent 编排+固定版本运行”。完成后 Codex 只做 diff 复核；通过才标记“可冻结进契约”，再启动 R-002 的 11 页原型生成。
