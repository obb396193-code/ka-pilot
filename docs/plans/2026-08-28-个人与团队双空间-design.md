# 个人与团队双空间设计

## 目标

在不破坏个人数据隔离的前提下，让用户在“我的工作台”和“团队数据”之间切换。个人空间可承载
本人授权和未来受控写操作；团队空间只读展示团队业务全量，任何团队数据源异常不影响个人空间。

## 三种方案与选择

1. **两个独立 workspace（采用）**：数据库、查询和 lineage 全部以 workspace 隔离；session 切换
   active workspace。边界最清楚，也能复用现有多租户表。
2. 单 workspace 加 `owner_user_id`：查询都必须额外拼个人/团队条件，容易漏过滤和串数，不采用。
3. 前端同时请求个人和团队数据后合并：浏览器获得过多数据，权限与口径不可审计，不采用。

## 身份与权限

- `workspaces` 增加 `kind=personal|team`。
- 每个 identity 必须拥有一个 active personal membership；可额外加入 active team membership。
- session 默认 active personal workspace；只有 active membership 才能切换。
- approved auth context 使用判别式 scope：
  - personal：`explicit_accounts`，只包含本人显式 grants；
  - team：`team_workspace_readonly`，只允许查询该 team workspace 已持久化的数据。
- team scope 不通过浏览器提交账户列表，不受 header 长度冒充“全团队范围”；Data API 必须从受信
  session/BFF 上下文获得 scope mode，并在 Repository 输出再次校验 workspace。

## 数据流

```text
个人启航身份 ──> personal workspace Raw/Canonical ──> 我的工作台

KA Data 或部门启航 ──> team workspace Raw/Canonical ──> 团队数据（只读）
```

数据源选择由服务端配置和 capability probe 决定。响应保留 `selectedSource/dataAsOf/coverage`；
team source unavailable 时仅团队页降级，个人查询不切源、不拼接、不等待。

## 功能边界

- personal：账户、任务、账户型工作项、本人无账户工作项；未来允许本人 grant 下的受控写。
- team：账户、任务、指标、账户型异常/工作项；不展示个人 self/agent_question，不展示个人操作
  行为排名，不开放 ignore/process/dispatch 或媒体写。
- 官方模板/规则/教学从版本化公共资产读取，不写入任一业务 workspace。

## 错误与安全

- 无 membership、workspace kind/scope mode 不匹配、跨 workspace row、team write 请求全部 fail closed。
- workspace 切换不会复用前一个空间的缓存、账户 scope 或请求结果。
- account_id 同号必须继续以 `(workspace_id,media,account_id)` 隔离。
- 日志不得记录 session token、BUC subject、启航 userId、完整账户列表或真实金额。

## 验收

- 同一 identity 可进入自己的 personal 和获准 team workspace；不能进入其他 personal/team workspace。
- 两个 workspace 存在同 media/account_id 时数据不串；切换后缓存不闪现上一空间内容。
- personal 空账户仍能看到官方公共资产；team source 不可用不影响 personal 200。
- team 所有 GET 可读，所有业务/媒体写返回 403/405；个人写仍必须经过确认门。
