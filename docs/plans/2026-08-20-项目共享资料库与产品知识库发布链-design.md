# 项目共享资料库与产品知识库发布链设计

> 日期：2026-08-20  
> 状态：老板已批准任务定义，按本设计直接实施  
> 范围：只建设仓库资料目录、索引、元数据规范、模板、首篇资料和审查交接；不开发产品知识库前端，不修改冻结 PRD / Contract。

## 1. 目标

建立“项目共享资料库 → 产品知识库”的同源资产链：

1. 建设期以仓库内共享资料库为唯一事实源，所有开发、审查 Agent 可按索引检索和引用。
2. 原始资料、分析判断、产品映射分层保存，避免把来源事实和 Codex 推断混成一个结论。
3. 经审查批准的资料未来通过统一导入/发布流程进入产品知识库，供优化师、运营、负责人和产品内 Agent 检索。
4. 仓库正文只维护一份；产品知识库是发布目标，不手工复制维护第二份正文。

## 2. 方案选择

### 方案 A：Codex 单篇滚动笔记

优点是落地快；缺点是其他 Agent 难以检索，原文、判断和结论容易混写，无法稳定发布到产品知识库。未选。

### 方案 B：共享资料目录 + 机器索引 + 分层文档（已选）

每份资料有稳定 `document_id`，原文、分析卡和未来产品映射分开；统一索引记录版本、hash、权限、证据、审查与发布状态。兼顾人读、Agent 检索和未来导入，是当前最小且可演进的做法。

### 方案 C：直接写入产品知识库数据库

能尽早验证产品形态，但当前产品知识库前端与导入契约尚未冻结，会造成仓库与数据库双写、字段漂移和未审查材料误发布。当前不做。

## 3. 目录结构

```text
docs/knowledge-sources/
├── README.md                         # 总入口、状态流、权限与引用规则
├── AGENTS.md                         # Agent 检索、引用和禁止事项
├── index.json                        # 机器可读的全部资料索引
├── schemas/
│   └── index.schema.json             # 索引 JSON Schema
├── templates/
│   └── document-entry-template.md    # 单篇录入模板
├── mappings/
│   └── product-kb-field-mapping.md   # 未来产品知识库字段映射
└── documents/
    └── <document_id>/
        ├── raw.md                    # 原文或合规留存，不写分析
        └── analysis.md               # 判断、证据、产品映射，不改写原文
```

首篇使用稳定 ID `ka-src-0001`。ID 一经分配不因标题、版本或状态变化而改变。

## 4. 元数据模型

`index.json` 每条至少包含：

- 身份：`document_id`、标题、标签；
- 来源：来源类型、来源名称、URL/定位信息、原始版本、发布日期、抓取日期；
- 完整性：`content_hash_sha256`、raw/analysis 路径；
- 权限：`access_level`、敏感性说明、允许的受众；
- 证据：`evidence_level`、证据说明、已验证/待验证边界；
- 流程：`lifecycle_status`、`review_status`、`publication_status`；
- 发布：目标知识库目录、未来产品字段映射版本；
- 许可：版权/许可证状态和引用边界；
- 演进：创建、更新时间以及替代/废弃关系。

## 5. 状态与权限

生命周期固定为：

```text
raw → analyzed → reviewed → approved → published → deprecated
```

- 未审查资料可以作为研发线索，但不得作为正式产品口径、默认 Agent 知识或自动执行依据。
- `review_status` 与 `publication_status` 独立记录，避免“已分析”被误报成“可发布”。
- 公开资料可标 `public`；内部资料默认 `project_internal`；受角色限制的资料标 `restricted` 并列出允许角色。
- 真实账户 ID、金额、考核价、内部人名、凭证等不得进入仓库。发现即阻断录入，先脱敏再计算 hash。

## 6. 证据等级

| 等级 | 定义 | 默认用途 |
|---|---|---|
| E1 | 当前有效的官方一手文档/API 定义 | 可作为接口与产品事实依据，仍需核对版本和权限 |
| E2 | 内部权威制度、正式平台文档、已验证实证 | 可作为内部实现依据，受权限约束 |
| E3 | 内部工作稿、用户提供材料、真实操作经验 | 可形成需求候选，需审查或实证 |
| E4 | 第三方竞品、行业文章、供应商宣传 | 只作对照和启发，不作为我方能力事实 |
| E5 | Agent 推断或待验证假设 | 只能进入分析卡的待验证区 |

同一文档可含多个主张；文档等级是最低保障，分析卡需对关键主张单独标注证据和推断。

## 7. 数据流

```text
用户给资料 / 官方抓取
  → 脱敏与许可检查
  → raw 合规留存
  → 计算内容 hash、登记 index
  → 独立 analysis 卡
  → 写审查信箱
  → 审查 Agent 逐项核实
  → approved 后进入未来导入队列
  → 产品知识库发布回写 publication_status
```

产品知识库不得反向成为正文编辑源。若产品内需要纠错，产生“修订请求”，回仓库修改、重审并发布新版本。

## 8. Agent 使用规则

1. 先查 `index.json`，再按权限和状态读取 raw/analysis。
2. 引用时必须带 `document_id`、版本、证据等级和具体路径。
3. `raw/analyzed` 资料只能写“资料主张/分析认为”，不得写成“产品已确认”。
4. 只有 `approved/published` 且权限匹配的资料，才可成为正式口径候选。
5. 资料冲突时并列呈现，不自动覆盖；交审查 Agent 裁决。

## 9. 首篇资料边界

首篇保存用户提供的《AI 投放平台产品能力对比：白盒平台 vs 黑盒平台》：

- raw：保留原始结构和措辞，注明来自用户粘贴、版本 v0.1、日期 2026-06-29、无可核验 URL；
- analysis：记录其价值、与我方 PRD 的覆盖关系、核心缺口和统计实验冲突；
- 证据等级：E3（内部工作稿/用户提供，未独立验证）；
- 权限：`project_internal`；
- 状态：录入后 `analyzed`，审查与发布均未通过；
- 不因录入而修改冻结 PRD/Contract。

## 10. 验证与失败处理

首批使用轻量、无额外运行时依赖的检查脚本验证：

- `index.json` 可解析并符合 Schema；
- `document_id` 唯一、路径存在；
- raw 内容 hash 与索引一致；
- 状态、权限、证据等级只取允许枚举；
- 未审查资料不得标为可发布/已发布；
- Markdown 不出现明显凭证模式或本项目禁止的真实数据标记。

抓取失败、版本未知、URL 失效或许可不清时，保留失败原因，状态不得超过 `raw`；不补造正文和版本。
