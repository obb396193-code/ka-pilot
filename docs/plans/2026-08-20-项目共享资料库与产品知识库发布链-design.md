# 项目共享资料库与产品知识库发布链设计

> 日期：2026-08-20
> 状态：老板已批准正式任务定义，按本设计直接实施
> 执行角色：KA 投放经营平台“资料研究与知识资产 Agent”
> 范围：只建设私有原始资料区、Git 内索引/评估/检索/发布规范和首篇资料；不开发产品知识库前端，不修改冻结 PRD、Contract 或生产代码。

## 1. 目标

建立一条同源知识资产链：

```text
内部/外部资料
→ 项目共享资料库
→ 开发与审查 Agent 可检索
→ 分析与审查
→ 批准后发布到产品“知识库”Tab
→ 业务用户与产品内 Agent 按权限检索引用
```

建设期以仓库资料索引和评估文档为事实源；内部原始正文保存在同项目的 Git 私有区。未来产品知识库是发布目标，不手工维护另一份正文。

## 2. 方案选择

### 方案 A：单篇滚动笔记

落地快，但其他 Agent 难以检索，原文与判断容易混写，无法稳定审查和发布。未选。

### 方案 B：私有原文区 + Git 索引/评估层 + 产品发布映射（已选）

内部完整原文放 `private/knowledge-sources/` 并由 `.gitignore` 阻断提交；Git 内 `docs/knowledge/` 保存机器目录、独立评估、检索和发布规范。每份资料共用稳定 `document_id` 和内容 hash，既保留内部信息，又避免进入 Git。

### 方案 C：直接写入产品知识库数据库

当前导入契约和 UI 未冻结，直接写库会造成双写、字段漂移和未审查材料误发布。当前不做。

## 3. 目录结构

```text
private/knowledge-sources/              # 内部原文、附件、下载快照；Git 永不跟踪
└── <document_id>/
    ├── source.md                       # 或原始文件格式
    └── attachments/                    # 可选

docs/knowledge/                         # 可提交、共享、可审查层
├── README.md
├── catalog.jsonl                       # 每行一份资料元数据
├── catalog.schema.json                 # 单行记录 JSON Schema
├── templates/source-card.md
├── assessments/<document_id>.md
├── agent-retrieval-guide.md
└── product-kb-publishing.md
```

首篇使用稳定 ID `ka-src-0001`；ID 不因标题、版本或生命周期变化而改变。

## 4. 三层边界

### 4.1 原始资料层

- 内部资料允许完整保存真实账户 ID、账户名称、金额、考核价和内部人名。
- 内部原文只进入 `private/knowledge-sources/`，不提交 Git。
- Token、Cookie、AK/SK、PAT、Webhook Token、数据库密码等凭证绝对禁止；发现后删除值，只保留 `secret_ref` 或凭证托管系统说明。
- 公开官方文档可下载归档，但记录 URL、抓取日期、版本和更新时间。
- 第三方资料记录来源和许可/引用边界。

### 4.2 资料索引层

`docs/knowledge/catalog.jsonl` 每行一份资料，供 Agent 快速检索。记录 `storage_ref` 指向私有原文或公开归档，不复制内部正文。

### 4.3 分析评估层

`docs/knowledge/assessments/` 只保存摘要、事实/推断/宣传/未证实分层、证据等级、产品映射和建议。允许提交 Git；不能把原文主张写成我方已确认事实。

## 5. 元数据

每条 catalog 记录包含：

- `document_id`、标题、资料类型；
- 原始来源、原始文件位置、来源系统、作者或责任方；
- 发布时间、抓取/收录时间、当前版本、内容 hash；
- 适用媒体、适用业务；
- 权限级别、允许角色；
- 证据等级、分析状态、审查状态、产品知识库发布状态；
- 替代或废弃版本；
- 相关产品模块、PRD/架构/接口；
- `storage_ref`、评估文档路径；
- 公开 URL、许可与引用边界（适用时）。

`content_hash` 以清理凭证后的原始文件字节计算。正文变化必须更新版本、hash 和审查状态。

## 6. 生命周期和发布门

```text
raw → analyzed → review_pending → reviewed → approved → published → deprecated
```

- 未审查资料可供研发和审查参考，但必须显示“未审查”。
- 未达到 `approved` 不得进入产品知识库，也不得成为产品内 Agent 的默认可信知识。
- `published` 必须同时记录审查人、审查时间、发布时间、发布目标与原文相同的 `document_id/content_hash`。
- 产品内纠错产生修订请求，回仓库/私有原文区更新并重新审查；不在产品端另维护一份正文。

## 7. 权限

- `public`：公开资料，可按许可公开引用；
- `project_internal`：项目成员/Agent 可在授权本机工作区读取；
- `restricted`：只允许 catalog 声明的角色读取；
- `confidential`：仅明确授权人/角色读取，不进入通用 Agent 默认检索范围。

产品知识库发布必须继承或收紧原权限，禁止自动放宽。索引可让无权限 Agent 知道资料存在，但不得泄露受限正文或敏感摘要。

## 8. 证据等级

| 等级 | 定义 | 默认用途 |
|---|---|---|
| E1 | 当前有效的官方一手文档/API 定义 | 接口与产品事实依据，仍需核版本/权限 |
| E2 | 内部权威制度、正式平台文档、可复现实证 | 内部实现依据，受权限约束 |
| E3 | 内部工作稿、用户提供资料、操作经验 | 需求候选，需审查或补证 |
| E4 | 竞品、第三方行业文章、供应商宣传 | 对照与启发，不作我方事实 |
| E5 | Agent 推断或待验证假设 | 只能进入待验证区 |

评估文档需对关键主张逐条标注“已确认事实/合理推断/宣传性表达/未证实项”，不能只给文档整体评级。

## 9. Agent 检索与引用

1. 先检索 `catalog.jsonl` 的标题、标签、媒体、业务、模块和关联接口。
2. 再检查权限、生命周期、审查状态和证据等级。
3. 有原文权限才读取 `storage_ref`；无权限只使用 catalog 允许暴露的元数据。
4. 引用必须带 `document_id`、版本、hash、证据等级、审查状态和具体来源位置。
5. 未审查材料只能表述为“资料主张/评估认为”，不得写为“产品已确认”。
6. 资料冲突并列呈现并交审查 Agent 裁决，不自动覆盖。

## 10. 产品知识库映射

未来导入至少映射：`document_id`、`source`、`title`、`content`、`revision`、`content_hash`、`visibility`、`allowed_roles`、`asset_state`、`evidence_level`、`reviewed_by`、`reviewed_at`、`published_at`、`source_url`、`source_file_ref`、`citations`、`related_business_objects`、`supersedes_document_id`。

导入器只能读取 `approved` 资料；产品记录与源资料必须使用相同 `document_id/content_hash`，发现漂移立即阻断发布。

## 11. 首篇资料

《AI 投放平台产品能力对比：白盒平台 vs 黑盒平台》按以下方式录入：

- 私有原文：`private/knowledge-sources/ka-src-0001/source.md`；
- Git 索引：`docs/knowledge/catalog.jsonl`；
- Git 评估：`docs/knowledge/assessments/ka-src-0001.md`；
- 来源：用户在会话中提供的内部对齐文档，版本 v0.1，日期 2026-06-29，无可核验 URL；
- 权限：`project_internal`；证据等级：E3；
- 录入完成状态：`review_pending`，不进入正式产品口径；
- 评估覆盖：白/黑/灰盒定位、AI 实验编排、实验与实时调控冲突、策略中心/工作流/基建/回收/知识库映射、一期/路线图/不建议项。

## 12. 验证

使用无第三方依赖的 Node 检查：

- JSONL 每行可解析并符合字段/枚举约束；
- `document_id` 唯一；
- 评估路径存在；私有 `storage_ref` 存在但未被 Git 跟踪；
- 内容 hash 与原文一致；
- 生命周期只能按允许状态；未批准材料不能标 published；
- 权限和允许角色完整；
- 原始资料与 Git 文档扫描常见凭证形态；
- `.gitignore` 必须覆盖 `private/knowledge-sources/`。

验证失败时不得提升状态或写审查通过。来源、版本、许可不清时保留未知，不补造。
