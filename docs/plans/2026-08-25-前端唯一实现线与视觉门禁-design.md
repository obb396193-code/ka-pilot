# 前端唯一实现线与视觉门禁设计

> 日期：2026-08-25  
> 状态：老板已拍板 A“视觉重建、功能继承”  
> 适用范围：KA 投放经营平台全部正式前端

## 1. 决策

当前任务“梳理前端组件与页面库”是唯一前端实现线。老板在本任务中逐项决定页面、组件、布局、视觉和交互；不另开前端 Entity。

`apps/ui-layout-demo/sidebar.html` 及其当前运行源码是唯一视觉母版。旧 F-001、旧“前端Agent”和已撤销的 ContentRadar 移植小样均不是视觉来源，不合并其页面、布局、主题或视觉组件。

选择 A“视觉重建、功能继承”：

- 视觉层从唯一母版向正式 `apps/web` 迁移。
- 功能层以 root 冻结的 PRD、API Contract、页面状态、权限边界和验收条件为准。
- 旧前端代码不整体合并；只有经 root 标记为 canonical 的非视觉代码和测试，才允许逐文件审计后复用。
- 页面分批进入正式运行时，不进行一次性全站重写或一次性大合并。

## 2. 职责

### 唯一前端实现线

负责：

- 页面、组件、交互、响应式、可访问性和前端工程。
- 官方/内部成熟源码选择、真实复制、来源登记和最小业务适配。
- 正常、加载、空、错误、部分、过期、无权限和禁用状态。
- 前端测试、视觉回归、键盘/焦点、性能和生产构建。
- 每个可见批次打开真实页面交老板验收。

不得：

- 自行计算 CPA、Gap、达成率、环比、归因或其他经营指标。
- 猜测接口、字段、权限或数据口径。
- 在 root 未开放 execute Contract 前提供真实媒体执行入口。
- 以旧前端页面为视觉参考，或在未拍板时制造第三/第四套页面。

### root / 审查线

负责：

- 冻结 PRD 功能、API Contract、状态、权限/租户和验收条件。
- 把旧前端已有能力整理为逐批“功能 + Contract + 状态 + 验收”清单。
- 判断旧非视觉代码或测试是否 canonical、可复用或应废弃。
- 对功能、数据、权限和写操作边界验收，不设计页面。

### 老板

负责：

- 逐项拍板视觉、组件、布局、密度、内容表达和交互手感。
- 对每个可见批次明确“通过 / 不通过 / 如何改”。
- 只有老板明确通过的页面状态才能成为新的视觉基线。

## 3. 四层前端结构

### 3.1 视觉母版层

- 唯一来源：`apps/ui-layout-demo/sidebar.html` 当前批准版本。
- 母版包含 Sidebar、Header、字体、token、KPI、图表、Tabs、DataTable、头像、间距与密度。
- 母版不是一次性截图；必须保留可运行源码和真实交互。
- 未经老板批准，不得改变母版的组件层级、核心几何、字体、密度和视觉节奏。

### 3.2 正式产品层

- 正式运行时为 `apps/web`。
- 正式页面只能组合已批准的母版组件、官方源码组件、批准的 ContentRadar 组件或经过对比拍板的 UI 资产。
- 页面业务数据、权限、状态和动作通过明确的 props/adapter 接入，不污染视觉原语。

### 3.3 Contract 适配层

- API response 先经过 schema 校验和 adapter，再进入组件。
- formatter 只格式化，不重新计算业务值。
- `0`、`null/—`、无数据、部分、过期和无权限保持不同语义。
- 写操作只到 ChangeSet preview/confirm；execute 未冻结时按钮明确只读或不可用。

### 3.4 来源与测试层

- 每个复制组件记录来源 URL/仓库路径、commit/ref、许可证、依赖、本地路径和修改清单。
- 每个业务组件有隔离状态样例和自动测试。
- 每个 P0 页面有视觉、键盘、焦点、console、overflow、状态和构建证据。

## 4. 旧前端已有功能的承接方法

不按“文件是否存在”判断功能已完成，按能力清单逐项处理：

| 旧资产 | 默认处理 | 进入正式前端条件 |
|---|---|---|
| 旧页面/布局/主题/视觉组件 | 不合并 | 无；视觉必须从唯一母版重新实现 |
| API Client/BFF | 候选 | root 确认 Contract 一致，测试通过，逐文件审计 |
| 类型/schema | 候选 | 与当前 canonical Contract 精确一致 |
| 纯数据 adapter/formatter | 候选 | 不计算业务指标，边界值测试齐全 |
| 权限/租户判断 | 候选 | root 确认权限和 workspace 边界 |
| 页面状态机 | 候选 | 覆盖八态且不隐藏错误 |
| 测试/fixture | 候选 | 对应当前 Contract，不保留过时 alias |
| 旧 mock 业务数据 | 默认不用 | root 确认脱敏、口径和字段后才可用 |

承接流程：root 发批次清单 → 前端建立能力映射 → 选择正式组件 → 接 Contract mock/API → 自动门禁 → 老板视觉验收 → root 功能验收 → 进入正式基线。

## 5. 成熟源码真实复制规则

### 5.1 来源优先级

1. 老板已批准的本项目视觉母版。
2. 官方完整 Page/Block/Component 源码。
3. 老板批准复制的 ContentRadar 真实源码。
4. UI 资产目录中已核来源、许可证和依赖的候选。
5. 仅当以上均不能满足时，编写最小业务组合层。

禁止根据截图仿写一个“看起来差不多”的版本，禁止只拿基础 Card 后自称复用了完整 Block。

### 5.2 ContentRadar 复制协议

- ContentRadar 原仓只读，不在其工作树修改。
- 复制完整组件、样式、资源和必需依赖，不只摘 JSX。
- 先在隔离入口保持原效果运行，再适配 KA Pilot 数据、中文、token 和路由。
- 记录原始绝对路径、原仓 commit、复制日期和逐项修改。
- 出现 React/Next/Tailwind/依赖冲突时先隔离，不静默重写底层行为。
- 复制件仍须通过本项目 Contract、状态、可访问性和老板视觉门禁。

## 6. 严格视觉门禁

以下任一失败，批次不得进入正式前端：

### Gate V0：来源

- 有明确视觉来源和源码 provenance。
- 不使用旧前端页面作为视觉来源。
- 同能力多候选时先在同业务容器比较，由老板拍板。

### Gate V1：母版一致性

- 未批准区域与母版的 DOM 层级、字体、token、尺寸、间距和图标保持一致。
- 禁止全局裸 `table`、`th`、`td`、`svg` 等选择器污染官方组件。
- 禁止为了塞业务内容擅自缩小字号、卡片高度和点击目标。

### Gate V2：单批可见改动

- 一个批次只处理一个明确区域或一个页面目标。
- 改动前后有截图/DOM/样式证据。
- 老板否决时整批回退，不在错误方向继续叠补丁。

### Gate V3：内容与数据

- 页面文案、任务、指标、单位和动作来自冻结需求或脱敏样本。
- 前端不计算经营指标；未知不写 0，不冒充达标。
- 内部 Contract 调试信息不占据普通用户首屏；需要时进入开发/诊断视图。

### Gate V4：状态与权限

- normal/loading/empty/error/partial/stale/no-permission/disabled 均有可验证表现。
- 权限不足、数据缺失和系统错误不得混成同一个空态。
- 写动作只到已开放的预览/确认边界。

### Gate V5：交互与可访问性

- 动作使用 button，导航使用 link；纯图标按钮有可访问名称。
- 键盘、Tab、Escape、焦点回收、Dialog/Drawer/Popover 行为正确。
- 支持 `prefers-reduced-motion`，无 `transition: all`。
- 数字/日期使用统一 formatter，图片有尺寸和 alt。

### Gate V6：自动质量

- TypeScript、lint、单元测试和 production build 通过。
- 目标桌面视口无横向溢出，console error 0；warning 必须解释或处理。
- P0 页面有视觉回归；桌面先行批次至少覆盖 1440×900 和 1366×768。
- 移动端进入对应批次后补 390×844，不用未完成移动端阻断已拍板桌面阶段。

### Gate V7：老板视觉签字

- 前端主动打开真实页面。
- 老板明确说“通过/这版可以”后，才能提交为新视觉基线。
- 未签字不得扩展相邻页面，也不得宣称视觉完成。

### Gate V8：root 功能签字

- root 按冻结功能、Contract、状态、权限和验收条件签字。
- 视觉通过不等于接口已接；接口通过也不等于视觉已通过。

## 7. 1V1 工作方式

1. 老板指出一个区域或目标。
2. 前端用一两句话复述本批只改什么、不改什么。
3. 前端复制/选择成熟源码并实现最小适配。
4. 自动跑 Gate V0–V6。
5. 打开真实页面，老板直接查看。
6. 不通过：整批回退或按老板下一条具体指令修改。
7. 通过：记录基线、路径、来源和截图，提交本批。
8. root 再做功能签字；两类签字齐全后该批完成。

## 8. Git 与现场保护

- 当前 `fe/f001` 含大量未提交现场，禁止 reset、checkout、批量覆盖或直接合并旧前端分支。
- 实施前建立独立接管 worktree/branch；先制作现状 manifest 和保护清单。
- `apps/ui-layout-demo/sidebar.html` 在正式迁移完成并双向核对前不得删除。
- 每批路径限定提交；视觉批次与 Contract 批次分开，便于回退和审查。
- 被老板否决的视觉批次不进入提交历史；必要时保留截图证据，不保留运行时代码。

## 9. 第一阶段范围

第一阶段只完成正式“工作台”桌面版：

- 把唯一视觉母版迁入正式 Next.js 运行时。
- 保持 Sidebar/Header/KPI/图表/Tabs/DataTable 的视觉结构。
- 接入 root 首批冻结的工作台 Contract 和八态。
- 建立可重复执行的 V0–V8 门禁。
- 老板工作台视觉签字后，才进入账户池或数据分析。

不在第一阶段一次性重写九页、移动端、Storybook 全站、完整 ECharts 模板库或全部 ContentRadar 组件。

## 10. 完成定义

一个前端批次只有同时满足以下条件才算完成：

- 来源与修改可追溯。
- 自动门禁通过。
- 老板视觉签字。
- root 功能/Contract/权限签字。
- 未接能力有明确状态和待办，不冒充实现。
- 代码进入正式基线并可安全回退。
