# B1c 语义查询内核设计

> 日期：2026-08-19
> 状态：老板已选择方案 1，进入实现
> 上游：B1b `50e3014`

## 1. 目标

先把数据分析页面共同依赖的 PostgreSQL 查询内核做实，让后续 Web API 只负责参数校验和响应映射，不在路由里重复写 SQL 或指标公式。

本批支持五类内部查询能力：

- `table`：账户日明细、筛选、白名单排序和分页；
- `summary`：加法指标汇总和基于汇总分子/分母计算的比率；
- `trend`：按日汇总趋势；
- `dimension`：账户、任务、业务三个当前可验证维度；
- `health`：canonical 覆盖、raw 新鲜度、ETL 和质量检查状态。

## 2. 边界

本批不新增 `apps/web` 路由，不修改 `packages/contract`，不实现契约尚未定义清楚的 `tier`，也不伪造当前 canonical 无法稳定支持的 `agent_type`、`resource_position`、`bid_tool`、`is_ubp`、`deduction_range` 维度。

所有业务查询必须显式接收 `workspaceId` 并在 SQL 第一层过滤。排序字段只允许代码白名单映射，其他条件全部参数化。

## 3. 方案比较

### 方案 1：仓储内核先行（采用）

在 `packages/db` 建 `SemanticQueryRepository`，返回稳定的内部数据结构。优点是能在 PostgreSQL 上独立验证租户隔离、聚合口径和分页；待前端工作树合并后，可接薄 API 路由。

### 方案 2：同时实现 API

会立即形成可调用端点，但当前后端分支没有 `apps/web`，且 API DTO 的部分字段尚未冻结；容易与前端脏工作树冲突。本批不采用。

### 方案 3：通用 SQL/报表 DSL

扩展性强，但会提前引入字段表达式、安全沙箱和查询成本治理，超过 B1c 当前目标。本批不采用。

## 4. 数据语义

### 4.1 粒度

- canonical 真相表粒度固定为 `workspace + account + ds`；
- `table` 每行仍是一户一日，关联任务以数组返回，禁止因 JOIN 扩行；
- `summary`、`trend` 和 `dimension` 的 CPA、CTR、CVR 等比率必须用汇总后的分子/分母计算，禁止平均行级比率。

### 4.2 任务历史关系

任务/业务筛选按 `task_accounts.valid_from/valid_to` 与指标日期匹配。若同一账户同一天命中多个任务，任务与业务聚合抛出 `AmbiguousTaskMappingError`，不静默双计，也不自创分摊规则。账户维度、全局汇总和趋势不依赖任务 JOIN，不受影响。

### 4.3 数据健康

内核只返回可证实的组成量：canonical 行数、活跃账户数、预期账户日、缺失账户日、各 raw resource 最新抓取时间、ETL 状态计数、质量检查通过/失败计数。覆盖率展示口径留给冻结后的 API/产品合同。

## 5. 错误与保护

- 非法日期范围、分页或不支持维度在进入 SQL 前失败；
- 每页最大 500 行；
- 排序列和方向从枚举映射，不接受原始 SQL 片段；
- 任务关系冲突返回可识别错误类型；
- 空数据返回零 totals/空数组，不用假数据补齐日期。

## 6. 验证

使用完全脱敏的 PostgreSQL fixture 覆盖：

1. 相同账户 ID 跨 workspace 不串数；
2. table 筛选、稳定排序和分页；
3. 任务关系按生效日期匹配且不会扩行；
4. 多任务重叠明确失败；
5. summary 从总分子/分母计算比率；
6. trend 与三个支持维度聚合；
7. health 使用最新 raw、ETL 和质量检查记录。
