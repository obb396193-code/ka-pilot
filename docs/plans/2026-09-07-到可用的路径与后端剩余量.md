## 三、两条路径，我建议第二条

### 路径 A：老板原话的顺序（全做完 → 审 → 联调）
全部 210 端点接完 → 两个后端自审 → arch 逐条审 → 对 PRD → 对原始需求 → 一次性联调 → 交付精修。
- **代价**：按两个后端现在的速度（各约 2–3 个子批/天，接线批每批露 3–8 个端点），接完约 **30–40 个子批**，**两周左右**；期间前端一直空转，老板一直看不到真数据。
- **风险**：第一次联调就要同时验 210 个端点 + 12 个页面，任何一个基础假设错了（比如 Session 透传、空间切换、缺数三态）会同时炸一大片，返工面最大。

### 路径 B：先打通一条竖切，再横向铺（**推荐**）
先只接**最小可用闭环**的端点，联调通，让老板能真用；然后每批接完就联调那一块。
- **最小可用闭环 = 登录 → 账户池 → 数据分析 → 工作台 → 任务**（老板定的精修顺序，正好也是价值顺序）。
- 需要的端点约 **45 个**，其中大部分内核已在，属"接线"。
- **好处**：约 **3–5 天**能看到真数据；基础假设一次性验穿（Session、空间、缺数、口径），后面每批风险都小；老板可以边用边精修，不用等两周。
- 之后按批联调：变更集与规则 → 报告结算 → 素材 → 策略大件 → 团队快照。

**两条路径的总工期其实差不多，差别是老板什么时候能开始用。** 路径 B 让"能用"提前一周半，而且把返工风险摊开。

## 四、审核那一环怎么做（两条路径都要）

1. **两个后端自审**：各自对着契约把自己域的端点逐条打勾，列出"契约有但没实现"和"实现了但契约没有"。
2. **arch 审**：我不看他们的自审结论，直接跑一遍脚本对比「契约端点清单 vs 实际路由表」，差集就是漏项；再逐条 diff 关键实现。
3. **对 PRD**：拿 `docs/20-PRD-v1.md` 的路由表 + 105 条验收基线逐条核，标 ✅/❌/降级。
4. **对原始需求**：拿 `docs/plans/工作台账.md` 里老板原话 185 条 + 需求表逐条核（上次全量偏差审计做过一轮，这次是第二轮）。
5. **联调**：每页对着真 data-api 跑一遍，验四件事——字段在不在、缺数是不是显 −、色标是不是从 DTO 来、空间切换对不对。
