# B2 队列闭环内核设计

> 日期：2026-08-19  
> 状态：老板已批准“契约安全内核”路线  
> 实现分支：`be/b2`

## 1. 目标

在不修改冻结契约、不猜内网 OS 接口的前提下，完成 B2 可独立验证的后端内核：规则判断、工作项去重与状态流转、通知分级，以及 Worker 扫描编排。B2 的 Web API、钉钉真实发送和缺失数据库字段留给 arch 冻结契约后接入。

## 2. 依据与边界

事实优先级：实际代码与最新实证 > `packages/contract/` > PRD v1.6 > 验收基线 > 历史会话与旧文档。

本批使用现有表：`alert_rules`、`work_items`、`jobs`、`outbound_messages`、`account_metrics_daily`、`accounts`、`task_accounts`。不新增表、不修改 API 契约、不接真实媒体写链路。

明确不假装完成：

- `alert_rules` 当前只能表达单指标条件，无法持久化“超成本且消耗超过阈值”等复合条件树；
- 0 曝光规则需要计划创建时间与计划级消耗，当前 canonical 数据未完整提供；
- 消耗断崖规则要求排除主动预算调整，操作史要到 B3 才完整；
- 户级静音、跨严重度重弹、P2 整点攒批的持久化语义尚未完全冻结；
- `/api/v1/work-items` 与 `/api/v1/rules` 只有摘要级合同，暂不实现路由 DTO。

这些缺口写入 arch 信箱，不通过临时字段或隐藏约定绕过。

## 3. 方案比较

### 方案 A：按 PRD 直接把 B2 API 和三条规则全部写完

速度表面最快，但会自行发明条件树、状态机和通知配置，Claude 回来后很可能推翻，且违反契约纪律。不选。

### 方案 B：等待 arch 把 B2 契约全部补齐

返工最低，但领域规则、工作项生命周期和 Worker 编排本身并不依赖外部 DTO，全部停工没有必要。不选。

### 方案 C：领域内核先行，外部边界后接

先实现纯函数、Repository 与 Worker 适配接口；所有未冻结数据通过显式接口注入，生产适配器不伪造。arch 回来只需审查契约差异并补薄适配层。选用。

## 4. 组件设计

### 4.1 规则判断内核

`packages/domain/src/alert-rules.ts` 提供：

- 可组合条件树：`all`、`any`、数值比较、布尔条件；
- 三值结果：命中、未命中、数据不足；
- 条件级 trace，支撑“为什么没触发”；
- 首发三条规则的领域定义和输入类型；
- 冷启动保护、无穷 CPA、缺失指标等边界。

条件树是内部领域模型，不作为冻结数据库或 API 字段。持久化映射等待 arch 裁决。

### 4.2 工作项生命周期

`packages/domain/src/work-items.ts` 负责：

- 状态转换白名单；
- 终态保护，禁止已完成事项被普通动作改写；
- 严重度排序与“跨 P 级重新弹”判断；
- 规则+账户去重键的确定性构造；
- 忽略、处理、完成、拒绝、升级、带外处理的命令校验。

### 4.3 通知分级

`packages/domain/src/notification-policy.ts` 只做确定性决策：

- P0 立即发送并突破静默；
- P1 正常发送，静默时延后；
- P2 攒到下一整点；
- opportunity 默认不触发紧急推送；
- 输出 `send_now | schedule | suppress` 和可解释原因。

它不解析未冻结的 `subscriptions.config` JSON，也不直接调用钉钉。

### 4.4 数据仓储

`packages/db/src/work-item-repository.ts` 使用当前 schema：

- 全查询强制 `workspace_id`；
- 用 PostgreSQL advisory transaction lock 串行化同一规则+账户的生成；
- 查找活动工作项并执行去重或严重度升级；
- 原子状态转换带旧状态条件，避免并发覆盖；
- 忽略原因、静音日期、SLA、证据快照原样留痕。

不新增 `dedupe_key` 字段。若后续需要跨历史高效检索，再由 arch 决定索引或列。

### 4.5 Worker 编排

`apps/worker/src/rules/rule-scan-handler.ts` 依赖四个端口：

- `RuleCandidateProvider`：提供待判定账户快照；
- `RuleEvaluator`：返回 trace；
- `WorkItemSink`：去重创建/升级工作项；
- `AlertSink`：按通知决策入队。

首批实现内存假端口单测和数据库 WorkItemSink；数据不充分的两条规则返回 `insufficient_data`，绝不生成误报告警。

## 5. 数据流

```text
ETL 成功
  → rule_scan job
  → CandidateProvider 提供账户快照
  → RuleEvaluator 逐规则输出 result + trace
  → 命中：WorkItemRepository 原子去重/升级
  → NotificationPolicy 给出发送时机
  → AlertSink 入 jobs/outbound
  → 未命中/数据不足：保留 trace，仅用于规则 explain，不生成工作项
```

## 6. 失败与安全

- 缺数据默认不命中，不用 0 填充；
- P0 的业务静默突破只影响通知，不绕过写操作确认门；
- 重跑同一扫描不能重复生成活动工作项；
- workspace 不一致直接拒绝；
- Worker 失败沿用现有 job 重试，终态进入失败告警；
- 本批不执行媒体写操作，也不读取或保存真实 token。

## 7. 验证

- 纯领域单测覆盖三条规则、数据不足、冷启动、trace、状态非法跳转、通知静默；
- PostgreSQL 集成测试覆盖租户隔离、并发去重、严重度升级、乐观状态转换；
- Worker 单测覆盖重跑幂等、未命中、数据不足、通知分级；
- 四包 test/typecheck/lint/coverage 与依赖审计继续作为交付门禁。

## 8. 复用纪律

B2 只复用现有 job/outbox、钉钉网关接口和 B1 指标函数，不需要搬 ContentRadar 源码。进入 B7 工作流、B8 知识库/素材拆片前，必须先查 Claude 历史调研、`docs/23-开发协作规范.md` 复用清单和对应既有源码；能复用的形态、方法或代码不得重新造一套。
