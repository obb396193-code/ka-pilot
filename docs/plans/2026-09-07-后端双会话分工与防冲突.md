## 3. 迁移编号与顺序

- 依赖核对（已查）：R-014 改的表 accounts/tasks/workflow_runs/changesets/report_configs 全部在 001/008 已建，**015 不依赖 013/014**；R-016 的表只依赖 001 基表。
- 编号固定：013 R-011、014 R-012、015 R-014、016 R-015、017 R-016。两边各自迁移里**只加自己的列**，同表不同列不冲突。
- 运行顺序：node-pg-migrate `checkOrder:true`。测试库每次重建，编号有缺口无所谓；**内测沙箱只从 main 按编号连续部署**——015 落 main 早于 013/014 时，沙箱先部署到 012，等 013/014 落了再一起升，不跳号部署。arch 在门禁清单里记"沙箱已升到哪一号"。
- 两边迁移都必须 up/down/up 可回放、down 拒有损；真 PG 用例必跑。

## 4. 测试与机器

- 测试库：be `ka_be_*_test`，be2 `ka_be2_*_test`，都在 55432 那个容器；禁用共享 `ka` 库。

## 5. 节奏与合流

- 两边都是"子批交付 → 回执 → 停手等 ✅"。be 回执 P-xxx，be2 回执 Q-xxx。
- 交审前必须 `git merge main`（含对方已合的批），冲突在自己分支解掉再交；arch 合流只解 docs/relay 的 union 冲突，代码冲突一律打回给后交的一方。
- 合流顺序：先到先合；同一小时内两边都到，先合改动少的。
- 契约缺口：谁发现谁写 inbox-arch，arch 裁完写进 api.md 的追加节，两边各自读，不互相传话。
