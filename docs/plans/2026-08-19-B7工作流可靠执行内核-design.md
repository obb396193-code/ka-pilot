## 1. 目标

在不修改冻结契约、不触碰前端、不编造 Multica/OS 协议的前提下，完成工作流以后不会白做的可靠执行内核：

- 统一描述数据、计算、Agent、执行、协作、控制六类业务节点；
- 以 Capability Registry 约束节点能做什么，禁止任意 Shell、SQL、URL 和动态代码；
- 严格校验并编译 React Flow 兼容图，拒绝环路、孤岛、坏引用和越权能力；
- 草稿校验、模拟、发布、固定版本运行各自有明确边界；
- 运行具备节点状态、事件回放、幂等、有限重试、暂停恢复、确认等待和 UNKNOWN 对账语义；
- 复用 B1 队列、B2 规则/工作项、B3 变更集、B5 Agent 和 B6 数据事实，不建立第二套执行系统。

## 2. 用户实际怎么使用

```text
官方模板 / 复制团队流程 / Agent 生成草稿 / 用户从空白创建
                         │
                         ▼
                 画布编辑节点和参数
                         │
                         ▼
      校验（图结构、参数、能力、权限、确认门、数据依赖）
                         │
                         ▼
               模拟运行（绝不产生媒体写入）
                         │
                         ▼
                 发布不可变版本
                         │
                         ▼
          手动、规则或定时入口发起一次运行
                         │
                         ▼
     运行中心查看节点进度、等待确认、重试、暂停和恢复
                         │
                         ▼
       结果、失败原因、执行证据和后续效果进入时间线
```

模板和用户自建流程使用同一 `workflow_definition/version` 模型。复制模板只是创建新 definition 和 draft version，不建立第二套模板表。

## 3. 当前契约能承载什么

现有表已经提供：

- `workflow_definitions`：流程身份、归属和模板类型；
- `workflow_versions`：不可变图、参数 Schema、草稿/发布态；
- `workflow_runs`：固定版本、发起人、凭证所有者和运行状态；
- `workflow_run_events`：节点事件和安全详情；
- `jobs`：lease、心跳、有限重试和凭证所有者冻结。

它们足以承载内部内核，但尚未冻结公开图 Schema、节点状态 DTO、确认/恢复 API、事件序号和触发幂等字段。本批因此：

- 可以实现领域模型、Repository、Worker Handler 和内部端口；
- 可以使用现有 JSONB/事件表保存内部安全事件；
- 不新增字段、迁移、公开 API 或前端 DTO；
- 所有缺口集中写入 arch 信箱，由 Claude/arch 冻结后再接 Web。

## 5. Capability Registry

### 5.1 定义

每个能力必须注册：

- 稳定 `id` 与 `version`；
- 六类节点之一：`data|compute|agent|action|collaboration|control`；
- 风险模式：`read|preview|execute`；
- 严格输入/输出 Schema；
- 所需权限和可用运行场景；
- 超时、最大尝试次数和是否允许模拟；
- 幂等作用域与冲突键生成器；
- 真实调用端口。

图里只保存能力 ID、版本和结构化绑定，不保存任意函数、表达式、命令、URL 或凭证。

### 5.2 与 Agent 共用

B5 已有 Agent operation capability。本批抽出公共能力元数据与注册校验，Agent 适配层继续只暴露 `read|preview`：

- `execute` 能力永远不能直接进入模型工具列表；
- Agent、页面按钮和工作流节点最终解析同一 registry entry；
- 不在本批重写 B5 Runtime，只做兼容适配并保持原测试全绿。

### 5.3 媒体写操作红线

本项目红线优先于 PRD 中未来的自动自治设想：任何媒体写操作都必须先形成 B3 变更集和 dry-run 预览，并等待明确确认。工作流的 action 节点只负责：

1. 生成或读取预览；
2. 写入 `waiting_confirmation` 事件；
3. 确认后调用 B3 执行端口；
4. 歧义结果转 `unknown`，先只读对账，禁止盲目重试。

## 6. 图模型与编译

### 6.1 内部版本

内部图版本为 `b7-internal-v1`。图保持 React Flow 可映射的 `nodes+edges`，但业务数据使用自己的严格字段，不让画布坐标进入执行语义。

节点包含：

- `id`：安全、唯一、有限长；
- `kind`：六类枚举；
- `capability`：固定 ID + version；
- `inputs`：只允许 literal、workflow parameter、上游 node output 三种绑定；
- `config`：有限重试、超时等受限覆盖；
- `ui`：可选展示信息，编译和指纹时剔除。

边只表达执行依赖。第一版只允许 DAG，不开放自由循环；确需轮询或重复时以后增加有最大次数的受控 control capability，避免死循环。

### 6.2 校验规则

- 最大 100 节点、200 边；
- 节点/边 ID 唯一，边端点必须存在；
- 不允许自环、环路和不可达孤岛；
- capability 必须存在且版本一致；
- node kind 必须与 capability kind 一致；
- 输出引用必须指向上游依赖；
- 参数、literal 和输出绑定必须与输入 Schema 匹配；
- action 节点必须存在确认策略；
- Agent 节点只能得到 registry 中允许的 read/preview 能力；
- 编译输出稳定拓扑序和 SHA-256 指纹。

## 7. 模拟、发布与版本

### 7.1 模拟

SimulationRunner 只允许：

- data/read；
- compute；
- Agent 的结构化草稿/判断；
- action 的 preview；
- collaboration/control 的计划结果。

任何 execute 调用在模拟态都 fail-closed。模拟结果逐节点记录 `ready|blocked|missing_data|permission_denied|would_wait_confirmation`，不伪装成真实执行成功。

### 7.2 发布

- 只允许通过校验和模拟门的 draft 发布；
- Repository 对 definition 加事务 advisory lock，递增版本避免并发重号；
- published graph 以后不可修改；
- 运行必须绑定 `version_id`，不读取“当前最新版本”；
- 稳定指纹用于检测发布后内容漂移。

## 8. 可靠运行状态机

### 8.1 Run 状态

内部状态：

```text
queued → running ─┬→ waiting_confirmation → running
                  ├→ paused → running
                  ├→ succeeded
                  ├→ failed
                  ├→ unknown
                  └→ cancelled
```

### 8.2 Node 状态

```text
pending → ready → running ─┬→ succeeded
                           ├→ retry_wait → ready
                           ├→ waiting_confirmation → ready
                           ├→ skipped
                           ├→ failed
                           └→ unknown
```

事件流是本批节点进度的真相：Runner 从 `workflow_run_events` 按递增 ID 回放并重建状态。现有表缺每 Run 顺序号，因此 Repository 必须在事务内串行追加事件；公开重连/分页 DTO 等契约后再定。

### 8.3 一次推进一个安全边界

Handler 每次运行到以下任一条件即停：

- 全部节点完成；
- 遇到确认、暂停、延时或 UNKNOWN；
- 达到单次最大步骤/时间预算；
- 发生永久失败。

需要继续时重新入队；状态从事件重建，不依赖进程内存。

## 9. 幂等、冲突、重试和恢复

- 节点调用幂等键：`runId + nodeId + attempt + capabilityVersion + inputHash`；
- 同一输入重放必须返回已有结果或明确冲突，不能再次产生副作用；
- retry 只用于能力声明允许且被分类为 retryable 的失败；
- execute 歧义超时直接 UNKNOWN，不进入普通 retry；
- action 冲突键由能力定义生成，最终接 B3 同账户/对象锁；本批只提供端口，不猜媒体层级；
- lease 过期后可重入，Runner 通过事件回放跳过已成功节点；
- 所有日志只保存安全摘要、对象引用和受限 raw ref，不保存 token、AK、PAT、完整模型提示词或外部回执原文。

## 11. “为什么没运行”

第一版输出结构化 reason code，不先写自然语言文案：

- `trigger_not_received`
- `data_not_ready`
- `insufficient_sample`
- `cooldown_active`
- `daily_limit_reached`
- `conflict_active`
- `permission_denied`
- `waiting_confirmation`
- `capability_unavailable`
- `version_invalid`

B2 规则解释和 B7 运行阻塞原因以后由公开 API 统一展示，但本批不发明 DTO。

## 12. 错误处理

- 坏图、坏参数、未知能力、版本漂移：发布/运行前拒绝；
- 权限与凭证缺失：`blocked_auth`/`permission_denied`，不换他人身份；
- 数据缺失：结构化 blocked，不把缺失当 0；
- retryable 外部失败：按能力上限和 Worker 退避重试；
- permanent 失败：终止受影响分支并按控制语义决定整 Run 失败；
- ambiguous execute：UNKNOWN，必须对账；
- 事件或状态持久化失败：不得继续调用下一节点。

## 13. 测试策略

- Domain：严格图 Schema、DAG、绑定、能力版本、权限、发布指纹、状态回放、下一节点选择、reason code；
- DB：definitions/versions/runs/events 的 workspace 隔离、并发版本、发布不可变、事件顺序和凭证所有者冻结；
- Worker：模拟不写、成功 DAG、确认暂停/恢复、有限重试、永久失败、UNKNOWN、lease 重入、幂等调用；
- B5 回归：Agent 仍只能看到 read/preview capability；
- 全量：四包 tests、coverage、typecheck、lint、audit、复杂度、迁移 replay 和冻结契约 diff。

## 14. 明确不做

- 不修改 `packages/contract/` 或数据库迁移；
- 不做 React Flow 页面、模板商店 UI 或公开 API；
- 不注册未冻结的生产 `job_type`；
- 不接真实 Multica/OS、启航写接口或 Secret 服务；
- 不开放任意 Shell、SQL、HTTP、Python、社区插件节点；
- 不实现无限循环、动态代码表达式或分布式图调度；
- 不将未来“自动执行”用于绕过媒体写操作确认红线；
- 不在本批创建知识库表；B8a 在 B7a 完成后单独设计、提交和审查。

## 15. 完成标准

- 图和能力定义严格、可版本化、可稳定编译；
- 模拟态技术上无法调用 execute；
- 运行绑定固定版本，可从事件恢复且不重复成功节点；
- 确认、暂停、重试、失败和 UNKNOWN 均有可测试状态；
- Agent/page/workflow 共用能力元数据，Agent 直写红线不退化；
- 新代码行覆盖率不低于 80%，全仓门禁不下降；
- 契约差异、状态、证据和 Claude 必审项全部留痕。
