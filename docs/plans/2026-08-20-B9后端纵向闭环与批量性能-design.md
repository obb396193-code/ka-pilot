# B9 后端纵向闭环与 Canonical 批量性能设计

> 日期：2026-08-20
>
> 状态：老板已批准方案 A；本文定义契约无关的集成验证与内部性能优化边界，不是公开 API、生产 Job 或奇航协议定稿。
>
> 基线：`be/b8a` / `3d90bed`

## 1. 本批目标

B1-B8 已分别具备取数、Raw、Canonical、质量、语义查询、规则扫描、工作项和报告事实等后端内核，但尚缺一条使用真实 PostgreSQL 验证组件兼容性的纵向证据；Canonical 当前还会按每行分别取配置、历史值并写入，合成基线暴露约 `3N+4` 次端口调用。

B9 只做两件事：

1. 使用真实 PostgreSQL 与确定性假奇航响应，打通 `奇航取数 → Raw → Canonical → 数据质量 → 语义查询 → 规则扫描 → 工作项 → 报告事实` 的集成闭环；
2. 将 Canonical 的配置、历史消耗和 Upsert 改成有界批处理，并以 100、1000、5000 行验证正确性、资源边界和查询计划。

## 2. 方案选择

### 方案 A：集成测试闭环 + 内部批量端口（已批准）

- 不新增生产 Job 类型、触发器或公开 DTO；
- 不假设真实奇航、Multica/OS 协议；
- 复用现有生产 Repository/Handler，用测试适配器补齐尚未冻结的规则候选入口；
- 优化 CanonicalStore 内部端口，保持现有 Job 状态机和下游派发语义。

优点是能尽早发现真实 PostgreSQL 下的组件断点和 N+1 性能问题，又不会与 Claude 后续契约冲突。

### 未选方案

- **同时注册规则/报告生产 Job**：更接近运行态，但需要新 job payload、trigger、输出存储和失败恢复契约，当前不应替 arch 拍板。
- **直接联调真实奇航**：需要内网身份、网络和正式样本；本批不能把未取得的通路当成依赖。
- **只做 Canonical 批量化**：改动较小，但不能证明各内核组合后语义一致。

## 3. 纵向闭环边界

### 3.1 真实组件

集成场景必须使用：

- 当前迁移建立的真实 PostgreSQL 表；
- 生产 Raw、Canonical、质量、语义查询、规则引擎、工作项和报告事实实现；
- 现有确定性 Job ID、workspace 隔离和幂等语义；
- 与生产相同的数据归一化和缺数判定。

### 3.2 测试适配器

只允许测试侧提供：

- 假奇航 QueryPort：返回固定、脱敏的账户与指标行；
- 规则候选适配器：候选事实必须读取已落库 Canonical/语义查询结果，不能在内存中另造一份指标真相；
- 无外发副作用的告警接收器。

这些适配器不进入生产 Runtime，也不构成未来公开协议。

### 3.3 闭环断言

至少覆盖：

1. Full ETL 只有 Raw 全部成功后才派生确定性 Canonical Job；
2. Canonical 正确合并渠道系数、考核价、RTA 与历史消耗，并派生质量 Job；
3. 数据质量状态与语义查询读取同一份 Canonical 真相；
4. 规则命中后只生成当前 workspace 的工作项；不命中不制造工作项；
5. 报告事实与语义查询口径一致，保留快照时间与数据截止时间；
6. 全链重复执行不重复 Raw、Canonical、Job 或工作项；
7. 缺少配置、质量失败、规则不命中、写入中断和跨 workspace 访问均 fail-closed。

## 4. Canonical 批量端口

### 4.1 端口形态

CanonicalStore 从逐行方法收敛为三类有界批量能力：

```text
loadEffectiveSettingsBatch(workspaceId, keys[])
loadHistoricalSpendBatch(workspaceId, keys[])
upsertCanonicalBatch(records[])
```

其中 key 至少包含 `accountId + ds`。Repository 返回结果必须可按复合键精确映射；缺行、重复行、跨 workspace 行一律拒绝，不能把缺失配置默认为零。

### 4.2 分批与事务

- 默认 chunk size 为 250，可由构造参数调整，但必须是安全正整数并设硬上限；
- 每个 chunk 依次执行配置批量读取、历史批量读取、Canonical 批量 Upsert；
- 单条批量 SQL 原子；不把 5000 行放进一个长事务；
- 后续 chunk 失败时 Job 整体失败，已成功 chunk 可保留；依靠确定性键与 Upsert 在重试时收敛；
- Job 只有全部 chunk 完成后才派生质量 Job。

该语义与原逐行实现允许“已写前缀后失败”的现实一致，但将重放边界从单行扩大到单 chunk，且不新增跨表分布式事务假象。

### 4.3 SQL 约束

- 批量输入使用参数化 JSON recordset、数组或等价安全方案，禁止字符串拼 SQL；
- 查询必须显式携带 workspace 约束；
- Upsert 冲突键和更新字段保持原实现一致；
- 大输入由应用 chunking 控制，避免 PostgreSQL 参数上限、SQL 文本膨胀和内存尖峰；
- 对批量查询记录 `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`，但不把本机数字冒充生产 SLA。

## 5. 性能验收

### 5.1 规模

使用脱敏合成数据分别运行：

- 100 行；
- 1000 行；
- 5000 行。

### 5.2 指标

记录：

- 端到端耗时与 Canonical 阶段耗时；
- Store 方法调用次数和实际 SQL 次数；
- 每阶段行数、失败位置和重试结果；
- 批量查询执行计划、buffer 命中与是否出现明显全表扫描；
- Node 和 PostgreSQL 版本、机器环境与是否预热。

### 5.3 门槛

- 业务结果与逐行基线一致；
- 端口调用量从约 `3N+4` 降到约 `1+3×ceil(N/chunkSize)` 加固定 Job/阶段开销；
- 5000 行不得触发既有 Qihang/ETL 资源上限绕过；
- 重跑后记录数和派生对象数稳定；
- 不设未经真实生产环境验证的毫秒级 SLA。

## 6. 错误与安全

- 假数据不得包含真实账户 ID、账户昵称、消耗或考核价；
- 测试日志不得记录凭证、奇航原始身份和完整异常 payload；
- 单个批次返回缺行或重复复合键时整个 Canonical Job 失败，不静默跳过；
- 跨 workspace 数据即使主键相同也不得被映射；
- 规则扫描与报告仅为只读验证，不执行媒体写操作；
- 本批不绕过 Changeset、preview、确认门和现有权限层。

## 7. 本批明确不做

- 不新增或修改公开 API/Schema；
- 不新增迁移，除非实现证明现有索引无法支持且先单独回报；
- 不注册生产规则扫描、报告或知识库 Job；
- 不实现真实奇航、Multica、OS、钉钉或模型 Provider 联调；
- 不补知识库数据库/API/前端，不补 React Flow 工作流前端；
- 不修改 Claude `fe/f001` 工作区；
- 不把集成测试适配器包装成生产服务。

## 8. 完成定义

1. 真实 PG 纵向集成测试覆盖成功、幂等、失败恢复和租户隔离；
2. Canonical 批量端口替代逐行 N+1，原有功能测试保持通过；
3. 100/1000/5000 行基准可重复运行并生成真实证据；
4. 四包 test/typecheck/lint/audit、覆盖率和复杂度门禁通过；
5. 设计、实施、质量、性能和 Claude 审查入口均有留痕；
6. 分支不含真实公司数据、凭证、前端改动或未冻结公开契约。
