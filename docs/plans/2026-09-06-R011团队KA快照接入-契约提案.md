## 3. 两种存储方案

| 方案 | 优点 | 代价/风险 | 本提案建议 |
|---|---|---|---|
| A：canonical 保持当前投影；staging 留不可变 run 数据；发布事务替换声明日期；按日 head 指向完成 run | 保持账户三键、现有列表/报表 SQL 可渐进复用；不另造指标模型 | 所有团队读必须校验 source/head；publish 会写 canonical；旧快照保存在 staging/archive，而非 canonical 多版本 | **推荐**，须同时接读侧，不只加列 |
| B：独立 team_account_metrics_daily，主键含 run_id；按日 head 切换 | 团队/个人物理隔离；发布只改 head，较少大批 canonical 改写 | 每个列表/报表/查询须新增团队指标读取分支或受控统一 view，容易遗漏；多版本存储/清理复杂 | 若实测 A 发布事务耗时/锁不达标，优先选 B，不靠放松原子性上线 |

不选“逐页改 canonical，最后改 ready”：上一 active snapshot 仍可读时已经被新页覆盖，失败无法保旧。也不只改一个 workspace active_run_id：run 若仅覆盖近几天，会错误隐藏上月数据。发布单位建议是 workspace+source+ds，多日期一次原子切换；未声明日期的 head 不动。

## 5. Adapter 与源一致性证明

候选内部契约（不是新公开 API）：

- `manifest`：受信 source binding、覆盖媒体/日期、不可变 source snapshot identity（或带版本的完整导出对象）、schema/template/metric version、预期页/行/账户集合或权威库存证明、真实 dataAsOf/timezone/dayCut、coverage 状态。
- `page`：同 manifest identity、稳定游标上下界/pageNo、行数/bytes、终止信号、truncation/clamp；强类型 rows，null 保留，present-invalid 拒绝。内部本地 runId/page hash 只证明本地内容，**不冒充上游 snapshotId/dataAsOf**。
- 单页 row/byte 守卫继续沿用 2k/10k 硬上限疑点及 exact16MB fail-closed；跨页总体另设部署可配置有限预算。固定模板生成 SQL，不接受浏览器 SQL/URL/limit/secretRef。
- 所有页需来自同一不可变快照。仅相同 count、相同 schema version、相同响应时间、前后两次样本相同，都不算完整证明。可接受未来实证路径：带 snapshot pin 的查询；不可变版本化导出；或整个结果在一个有声明一致性保证的 source statement 内取齐且低于边界。**当前均无足够代码/实测证据可声称已支持分页 pinning。**
- sourceRowsComplete 与 inventoryComplete 分开。源事实行全读完，不等于无消耗账户也全在表中。完整账户库存缺失时 coverage=unknown；首版不把它 publish 为 ready。
- unknown lineage/coverage 可落 staging 和 run 诊断态，标待补证；不替换上一 completed。present-invalid/越范围/重复账户日/版本漂移/截断是失败，而非 unknown。

### 需 OS 最小只读补证（请 arch 转其既有追问渠道）

只需回答能否在**同一个固定不可变数据版本**枚举账户库存和账户日全部页，并说明实际字段/调用入口；若不能，是否可提供版本化完整导出或单 statement 的一致快照数据集。请区分 schema version 与 data revision，给无凭证 envelope/版本含义、完整性/终止证明、空日与未刷新判据；不要回传 token/签名URL。已有服务 ACL/稳定域名/同日同户对平仍是独立部署硬门，不在这里增加个人凭证门。

## 6. Job 链与事务边界

1. **team_sync_run**：服务端配置解析 active team/binding/version/范围；credential_owner_user_id=NULL，使用团队 reader secret，只在调用时解析，不进 payload。确定性 key 至少含 workspace、source、配置版本、调度 slot、覆盖范围；cadence 外置。锁 state 建 run、固化 base publication revision 和 manifest 摘要，初始页 job 与 run 在同一短事务创建。
2. **team_sync_page**：claim 现有 Job lease；出事务请求源；回来后短事务锁并验证 job token/有效租约、run、绑定仍有效。校验 page 与 manifest，写 staging/page receipt，并在同事务写下页或 publish outbox。重复 receipt 同 hash 返回既有结果，冲突不同 hash 失败；staging 不触可见 canonical/账户/任务。
3. **team_sync_publish**：无网络调用；锁顺序统一 workspace→state→run→job，校验 lease/token、配置、base revision、连续页、总数/唯一键/声明日期/库存/lineage。预校验不能代替锁内检查；validated 后 staging 冻结不可追加。
4. **原子事务**：建/更新团队 source-owned 主表元数据→替换声明日期的 canonical 行→更新相应 day heads→run completed/state revision+1→本地 publish job/outbox 终态。任何失败全部 rollback；没有先 commit metrics 再改 head 的阶段。FK顺序先 accounts，再 canonical。
5. 同时两 run 基于同一 base revision：第一个完成发布后，第二个 CAS 不符，标 superseded、不自动覆盖。若需要继续，重新调度/重新验证，不把旧快照当新 run 强发。
6. 进程在 COMMIT 后但 ACK 前崩溃：重试读 completed + publication revision，直接返回幂等完成，不再删除/插入；expired lease 的旧 executor 永不发布。

publish 在受控短事务下做批量 SQL；不得在事务中下载/等模型。总量超预算或 statement/lock timeout 则 rollback 保旧，不逐页 commit 图快。必须压测真实PG发布规模与并发只读；若无法满足预算，选 B 的版本指针方案，不称 A 已在线低锁。

## 7. 读取、血缘与就绪闭环

- **普通 team query**：保留 mode=ka_data/authority，改由 `TeamSnapshotDataSource` 读本地已发布 KA 投影；不调用 live reader 当自动 fallback。个人 PlatformDataSource 不受影响。live KA 仅同步 adapter 或现有管理员显式诊断路径。运行期开关关闭的行为由 arch 明确：建议关闭 KA 即拒新的团队查询/同步，不借缓存绕过权限开关。
- **RR/RO**：一请求的 metrics、count、tasks、lineage、heads 在同一数据库快照，跨日看到一次 publish 前或后，不混半次发布。每行 source_kind/run 与该日 head 一致；缺 head/范围不覆盖→partial，不读 staging。
- **历史范围**：只更新声明日期 heads，旧日期仍可读其旧 completed run。不能只用 workspace 的 last_completed_run_id 过滤全部历史。多日混合来源版本需显式复合 provenance，而不是任选一个源版本或 latest timestamp。
- 建议 arch 冻结 optional lineage snapshot 元数据（例如本地 publicationRevision 与按日 upstream version 摘要），明确它与 datasetVersion 的区别；单一源版本才可原样给 datasetVersion，多源版本无新合同前 null+partial，不能造一个 hash 冒充上游版本。
- **dataAsOf** 来自源 manifest/真实行刷新字段，不能用 published_at/computed_at/now() 冒充。多个覆盖日取保守最旧更新时间或返回按日freshness（请arch明确）；published_at只是产品发布时刻。
- **readiness**：personal 保留既有个人 full/grant逻辑；team 只看批准 workspace 的 completed heads/coverage/真实freshness。首次无完整快照不ready；已完成快照在下一run失败后继续可读，标同步失败/按真实时间stale，不永久置partial。合法空数据需有完整空manifest，显示empty；空响应但无证明仍unknown。
- **列表不能漏接**：accounts/tasks/work-items repositories 同RR中走team readiness；accounts/tasks的selectedSource候选增加ka_data枚举。工作项对象源保持platform，指标snapshot/ready另算；team仍排除双null个人工作项，changeset和所有媒体写仍403。
- **字段缺失独立于同步完成**：run完成不代表每项业务指标都有数；missing字段保持三态，未有预算/考核时不可判断，不因initialFullComplete=true而填0。

## 8. 保留、恢复与迁移边界

- staging 在完成后作为 immutable已发布内容留存（可后续迁入同结构archive，但首次不造额外存储系统）；任何 active day head 引用的 run/page/staging 不能清理。
- 候选默认保留至少最近两个 completed run；失败/废弃run按配置天数清理。被report/settlement/work-item evidence明确引用的版本必须pin，不能按年龄删除。具体保留天数由arch/部署预算定，不硬编码业务承诺。
- 清理 job同样按workspace/run受限、分页短事务、FK/引用复核，不能删除“最近N之外但仍支撑历史日期”的run。个人行完全不在清理范围。
- 恢复操作先只提供服务端维护命令提案：选历史完整run作为新publish意图，重新CAS/coverage校验；不修改旧run审计、不自动回退源，不开团队管理UI或普通浏览器写API。
- 013 up先审计已有team canonical与任务关系：来源不明的旧行不能批量标为ka_data/ready；隔离保留或拒迁移待arch处理。个人行明确source=platform且snapshot为空。
- down不能默默丢已发布团队数据；候选要求存在team运行/快照数据时拒绝自动down，走备份/批准维护步骤。空库up/down/up、旧个人数据不变必须真实PG验证。
