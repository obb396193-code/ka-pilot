# Codex 对 PRD v1.1 的复核意见

> 日期：2026-08-18
> 复核对象：`docs/20-PRD-v1.md`
> 需求基线：`docs/14-老板需求追踪总表.md`（只取老板连续对话中的 126 条原始需求）
> 结论：**有条件不通过。完成度高，但存在原始需求缺失、直接冲突和 Schema/部署架构硬伤，修正前不适合作为“开发唯一需求依据”。**

## 一、总判断

这份 PRD 的优点很明显：已经不是概念稿，而是接近可开发规格；工作台、任务、数据、规则诊断、变更集、T+1 回收、自助报表、Agent 上下文、报告与数据运维写得具体，安全与数据准确意识也强。

问题不在“写得不细”，而在三个层面：

1. **后来的方案覆盖了老板原始要求**：最典型是老板明确要扣子/Dify 式自由工作流，PRD 改成“模板商店，不做画布”；
2. **目标形态和技术拓扑互相打架**：老板要求独立消息网关，PRD 却把 Web、API、Cron、Agent、钉钉 Stream、Chromium 和 Multica 全塞进一个 FaaS 进程；
3. **功能写进正文但数据模型没承接**：任务字段、OS 对话、工作流、钉钉入站、商品素材、结算模板、公共资产等缺核心表，直接开工会在中途反复改库。

### 126 条原始需求覆盖结果

| 结果 | 数量 | 占比 | 定义 |
|---|---:|---:|---|
| 充分覆盖 | 65 | 51.6% | PRD 有明确页面/流程/规格承接 |
| 部分覆盖 | 41 | 32.5% | 有方向，但关键交互、对象、字段或闭环缺失 |
| 未覆盖 | 8 | 6.3% | PRD 没有对应功能 |
| 直接冲突 | 9 | 7.1% | PRD 明确采用了与老板原话相反的方案 |
| PRD 外的原型交付项 | 3 | 2.4% | 已有画册类产物，不属于本 PRD 的产品功能 |

这组数量是需求审计判断，不是精确研发工时。它说明：**大方向覆盖较广，但不能据此说“需求都实现了”或“可以无条件开工”。**

### 为什么与 arch 的“108 条设计覆盖”不同

两份对照不是在回答同一个问题：

- arch 的统计以“在 PRD、21 号功能清单或其他规划文档中出现过”为覆盖，P2 路线图、占位方案和一句方向描述也可计入；
- 本复核只审 `docs/20-PRD-v1.md` 能否成为**开发唯一依据**。只有页面/流程、业务对象、关键状态或 Schema、权限安全和验收闭环足够明确，才计“充分覆盖”；只写方向而无法据此稳定开发的计“部分覆盖”；
- arch 在本复核进行中补入了任务 RTA 等字段和“新建对话默认清空”。本表已按最新磁盘版本重新校准，其中 REQ-079 已由缺失改为充分覆盖；REQ-024 因仍缺任务预算及参数版本模型，继续计部分覆盖。

因此，“108 条”可以理解为**需求被设计材料提到的广度**，“65 条”是**当前 PRD 达到开发闭环的深度**。两份审查对核心矛盾的判断基本一致：工作流画布、钉钉群能力、独立消息网关、公共资产治理、素材拆解和卡片确认仍需裁决或补规格。

## 二、同意

以下部分方向正确，可保留为 PRD 主干：

1. **产品不是聊天壳**：首页为工作台和行动队列，Agent 是全局抽屉与页面助手，符合老板要求；
2. **投放任务作为主线对象**：任务连接账户、数据、素材、操作与报告，方向正确；
3. **数据能力扎实**：双口径、数据健康、Gap、盯盘、自助报表、Agent 做表基本覆盖原始需求；
4. **优化师闭环完整**：异常 → 证据 → 建议 → 变更集 → dry-run → 确认 → 执行 → T+1 回收，是 PRD 最成熟的一段；
5. **工作项与派发**：带证据快照和回链，而不是再造普通 Todo，符合业务要求；
6. **策略与自动化概念已分开**：策略分析回答“什么版位/投法有效”，规则回答“何时触发”，边界基本正确；
7. **报告与结算方向正确**：日报、周报、复盘、结算和模板版本已有承接；
8. **基建管理主路径正确**：B 主（平台托管 Multica 对话）+ A 兜底（复制提示词）已进入页面；
9. **Agent 交互正确**：页面上下文、勾选对象、后台 Agent、结构化输出和确定性计算分层合理；
10. **数据运维补充值得保留**：回灌、重算、对平、缺数抑制、ETL 监控、业务日历都是正式产品必须有的底座。

## 五、Schema 终版意见

### 5.1 当前 Schema 的硬问题

| 对象 | 问题 | 必须修改 |
|---|---|---|
| 多租户 | 绝大多数表无 `workspace_id/tenant_id` | 所有业务表带租户键；增加 workspace、member、role、resource grant |
| 账户与任务 | `accounts.task_id` 是单值，无法表达历史/多任务关系 | 拆 `task_accounts(task_id, account_id, valid_from, valid_to, role)` |
| 任务 | 缺预算、RTA、版位、投法、考核字段和扩展信息 | 扩 `tasks`；可变参数进入 `task_parameter_versions` |
| 日指标 | `account_metrics_daily` 以 `source` 做 PK，但正文又要求字段级合并，查询容易双计 | raw 表与 canonical 表分离；canonical 一户一日一行，字段来源单独记录 |
| 账户结构 | campaign/unit/creative 混一张 level 表，弱类型、弱外键 | 分层表或 `ad_entities(parent_id,type)`+类型约束；指标表引用稳定实体 ID |
| 变更集 | 当前一行同时是 header 和 field item，无法稳定表达批量/部分成功 | 拆 `changesets`、`changeset_items`、`execution_runs`、`execution_events` |
| 权限 | role 只放 users 一列，无法表达负责人/代管/任务可见范围 | workspace role + resource relation + action permission |
| 敏感凭证 | `idealab_ak_ref` 语义不明 | 只存 secret reference，不存明文；区分 user credential 与 service credential |

### 5.2 正文已经要求、Schema 却缺的表

必须在契约阶段补齐：

- 数据运维：`etl_runs`、`backfill_jobs`、`ingestion_batches`、`data_quality_checks`、`data_revision_jobs`；
- 时间和值守：`business_calendar`、`duty_roster`、`duty_shifts`；
- 分区保留：日/小时指标按日期分区，定义 retention/rollup job，不只写一句“90 天降采样”；
- What-if：`changesets` 增加 `simulation_status/confidence/model_version/assumptions`，预测明细独立 `changeset_simulations`；
- OS/Multica：`multica_threads`、`account_thread_bindings`、`agent_runs`、`agent_run_events`、`scheduled_infra_jobs`；
- 工作流：`workflow_definitions`、`workflow_versions`、`workflow_nodes`、`workflow_edges`、`workflow_runs`、`workflow_run_events`；
- 钉钉：`dingtalk_connections`、`dingtalk_identity_mappings`、`dingtalk_subscriptions`、`inbound_events`、`outbound_messages`、`callback_idempotency`；
- 商品素材：`products`、`materials`、`product_material_relations`、`material_lineage`、`design_requests`；
- 报表结算：`report_definitions/versions`、`settlement_templates/field_mappings/runs`；
- Agent 对话：`agent_sessions`、`agent_messages`、`agent_context_items`，用于新建对话清空和显式对象上下文；
- 公共资产：统一 `assets`/`asset_versions`/`asset_dependencies`/`asset_validations`，让报表、工作流、策略、对象组共用生命周期。

### 5.3 B1 必须拆

v1.1 把“契约、Schema、90 天回灌、增量 ETL、语义层、计算层、数据大盘、维度透视、备份恢复”全部塞进 B1，风险过大。建议仍属于一个数据脊柱里程碑，但拆成三个可独立验收的工程子批：

1. **B1a 契约与存储**：PostgreSQL、迁移、租户/权限、原始落库、ETL Run；
2. **B1b 回灌与口径**：90 天 backfill、canonical 合并、指标计算、对平与重算；
3. **B1c 数据服务与页面**：语义层 API、大盘、透视、数据健康。

SQLite 只能用于本地开发和 mock，不应放在 daily FaaS 承载真实历史数据。RDS 未到位时，B1 可以写代码和测契约，但不能宣称真实数据闭环验收完成。

## 六、部署架构意见

### 6.1 不同意“一台 FaaS 一个进程扛全部”

Next.js SSR、API、Cron、长耗时 Agent、钉钉 Stream、Chromium 渲染放在同一进程，会出现：

- Web 扩容后 Cron/Stream 重复运行；
- Agent/Chromium 占满内存拖死用户请求；
- 发布 Web 导致钉钉长连接和长任务同时中断；
- 无法分别限流、重启、扩容和审计；
- 直接违背老板“独立共享消息网关”的原始要求。

建议同一 monorepo、共享合同和数据库，但拆成三个部署单元：

```text
Web/API FaaS
  ├─ 页面、查询 API、用户操作、权限校验
  └─ 只投递长任务，不直接跑 Agent/Chromium

Worker/Scheduler FaaS
  ├─ ETL、规则扫描、T+1、backfill、Agent Runtime
  └─ DB lease/幂等保证单实例任务语义

DingTalk Gateway FaaS
  ├─ Stream、入站身份/意图、卡片回调
  └─ 推送、模板渲染、重试与 Multica 路由
```

若 FaaS 平台不支持队列，先用 PostgreSQL job/outbox 表实现；不能靠每个进程内 `node-cron` 自己认为只有一个实例。

### 6.2 LLM 通路需改成 Provider 抽象

PRD 的“Claude Agent SDK → IdeaLab Anthropic 兼容端点，已确认 Claude 可用”已经落后于台账 #117：当前免费内部 AK 只确认 Qwen，Claude 需要另申请或走 Anthropic 官方 API。应定义：

```text
AgentRuntime（唯一一套）
  └─ ModelProvider
      ├─ IdeaLab / OpenAI-compatible
      ├─ Anthropic official
      └─ 其他兼容网关
```

这不等于做多个 Agent Runtime；仍是 Claude Agent SDK + 一套运行时，只把模型端点、凭证与能力做配置化。若某兼容模型不能满足 SDK 协议，要在契约实测后明确降级，不可在 PRD 中提前写“均可切”。

## 七、导航意见

### 7.1 先撤销“定稿”

老板原始要求是“全部功能铺开后再定一级导航”。当前仍有 17 条缺失/冲突需求，故本轮只能给候选建议，不能替老板拍板。

### 7.2 条件性建议

在补回自由工作流后，一级导航建议为：

1. 工作台
2. 投放任务
3. 数据分析
4. 账户资源
5. 商品素材
6. 自动化
7. 报告

理由：自动化/工作流是老板明确要求用户可创建的核心生产工具，不应藏进“更多”；钉钉中心主要是连接与推送配置，频次低于自动化，应放“更多/集成管理”；知识库、治理后台和设置同样进“更多”；Agent 保持全局抽屉；基建管理继续在账户资源内独立 Tab，不升一级。

如果后续证实钉钉连接/群配置是普通用户高频任务，再把钉钉中心提级；当前没有证据支持它占一级导航。

## 八、补充与最终结论

### 开工前必须修正的六项

1. 恢复工作流自由画布、个人工作流、公共池和 Agent 编排能力；
