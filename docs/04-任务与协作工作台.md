# 任务与协作工作台（需求）

> 建立：2026-08-13，来源：老板口述
> 定位：这条需求把产品从"看数据的工具"变成"部门协作的载体"。**战略权重高于任何看板功能。**

## 1. 需求原文

> 还有个任务工作台、待办工作台。可以从上级看到啥数据后直接分发下去，别的工作台之类的就可以看见，也可以维护自己的。

## 2. 我的理解

三层能力：

| 能力 | 说明 |
|---|---|
| **分发** | 上级（运营/KA 负责人）在自己视图里看到问题，**当场派下去**，不用切工具、不用发群、不用口头交代 |
| **接收** | 下级（优化师）在自己工作台看到"派给我的"，和系统自动生成的诊断建议混在同一个队列里 |
| **自建** | 每个人也能维护自己的待办，不只是被动接活 |

关键点：**分发的东西带着数据上下文**。派的不是一句"你看下这个户"，而是"这个户、这个问题、这些证据数字、建议这么做"——链接回它被发现的那个视图。这是它和钉钉群、Excel 派活的根本差别。

## 3. 为什么这条需求战略权重最高

**它让上级有理由每天打开产品。** 纯看板对 KA 负责人是"看一眼就走"，一周可能开两次。有了分发，产品变成他行使管理动作的入口——看到问题、点一下派下去、看到回执。**这是从"信息工具"到"管理工具"的跃迁，也是产品在组织里扎根的方式。**

**它给横向推广提供了天然通路。** 别的渠道优化师被派了活，就得进来看；进来了就会顺手用别的功能。比单纯"求你来试试"有效得多。

**它让 AI 提效有了可举证的闭环**：派发 → 处理 → 效果回收，全程留痕。更高层那屏的"AI 提效成果"数据从这里来。

## 4. 与自动诊断的关系：同一个队列，两个来源

优化师工作台**只有一个队列**，条目有两种来源：

| 来源 | 谁产生 | 特征 |
|---|---|---|
| 系统诊断 | 规则引擎 / agent | 自动、批量、有证据、可能误报 |
| 人工派发 | 上级或同事 | 少量、明确、带人际权重、不能忽略 |

**不能做成两个 tab。** 优化师早上只想看"今天我要干什么"，不想在两个列表之间对照。统一队列、来源打标、优先级混排。

## 5. 数据模型要点（先记，实现时用）

一个"工作项"（work item）应包含：

- 标识：ID、创建时间、来源（系统诊断 / 人工派发 / 自建）
- 对象：关联的账户 / 任务 / 计划，以及所属渠道
- 证据：触发规则、关键指标快照（**必须存快照**，否则三天后回看数字已变，无法复盘）
- 建议：建议动作 + 参数 + 依据
- 流转：创建人 → 指派人 → 当前处理人，历史流转记录
- 状态：待处理 / 进行中 / 已处理 / 已忽略（**必须填原因**）/ 已失效
- 结果：实际执行了什么动作、T+1 效果回收结论
- 可见性：谁能看到这一条（挂在权限模型上）

**忽略必须留痕并给理由**，两个用途：不重复弹同一条；反过来给规则引擎反馈——某条规则被大量忽略，说明规则本身有问题。

## 6. 必须避开的坑

1. **别做成又一个待办系统。** 公司里已经有钉钉待办、Aone、Multica issue。我们的工作项能立足，靠的是**它自带投放数据上下文和执行入口**，不是任务管理功能本身。做成通用 todo 就死。
2. **别让它变成派活考核台。** 与 03 文档 §4 同一个风险：一旦优化师觉得"派给我的都在被计时排名"，抵制的是整个产品。原则不变——**对个人只呈现帮助，对上层只呈现聚合**。
3. **分发不能强制。** 优化师要能"驳回/说明情况"，且驳回意见要回到派发人那里。单向下压的工具没人爱用。
4. **是否复用 Multica 的 issue 做底座**——待验证的架构问题。若能复用，我们不必造任务系统，还天然与技术侧体系集成（博弈上更容易被接受）；但会绑定在 Multica 上、离不开。已列入探针 B 第 15 问。
