# 产品功能清单（v0.1 草案）

> 建立：2026-08-14　状态：**待老板审**
> 本文档 = 功能优先级 + 页面流程 + 角色权限，审完后作为开发依据。
> 原则：**阶段一做最小闭环**，不贪全。功能按 ROI 排，能用的先上。

## 1. 功能全景（按优先级排）

### P0：阶段一必须有（最小闭环 = 老板自己用，省 ≥1h/天）

| # | 功能 | 说明 | 用户价值 |
|---|---|---|---|
| F1 | **自动数据拉取** | 定时从启航 get_data 拉账户/广告数据，按 userId 分人拉，落库 | 不用每天手工导表 |
| F2 | **任务维度聚合** | 按 task_id/biz_name 自动分组聚合，替代手工透视 | 打开就看到按任务分好的数据 |
| F3 | **异常自动标注** | 超成本、消耗断崖、0曝光、Gap 异常——规则引擎自动标红 | 不用逐个排查 |
| F4 | **诊断建议生成** | 基于数据+规则生成"这个户该动什么"的建议（可自定义策略） | 判断有依据，不用全靠经验 |
| F5 | **今日待处理队列** | 优化师首屏：哪个户→为什么→建议→执行入口（四件套） | 早上打开就知道今天干什么 |
| F6 | **BUC 登录** | 公司域账号登录，每人看到自己的数据范围 | 多人可用，权限隔离 |

### P1：阶段二（团队用起来）

| # | 功能 | 说明 | 用户价值 |
|---|---|---|---|
| F7 | **任务工作台** | 上级看到问题→一键派发→下级看到→处理→回执 | 从信息工具→管理工具 |
| F8 | **效果回收** | 改完账户后 T+1 自动回来告诉你"生效没有" | agent 与脚本的分水岭 |
| F9 | **运营视图** | 任务达成率、Gap 归因、跨渠道对比 | 运营一眼看清 |
| F10 | **负责人视图** | 各渠道效率排名、风险清单、资源建议 | 决策有据 |
| F11 | **钉钉推送** | 早报、异常预警、派活通知发到钉钉群 | 零安装触达 |
| F12 | **策略配置** | 每个优化师可自定义诊断规则和阈值 | 因人而异的策略 |

### P2：阶段三（全部门平台）

| # | 功能 | 说明 | 用户价值 |
|---|---|---|---|
| F13 | **更高层视图** | 核心目标进度、AI 提效成果、需拍板的事 | AI Native 交差 |
| F14 | **跨渠道** | 接入抖音/腾讯/百度数据 | 全渠道统一 |
| F15 | **写操作执行** | 改价/下线/调预算经 agent 执行，带确认门 | 闭环 |

## 3. 数据流设计

### 3.1 数据拉取流程

```
定时任务（每日凌晨 + 每 4 小时）
  → 拉账户列表（get_data resource=account，按配置的 userId 列表）
  → 拉账户实时数据（get_data resource=account_realtime）
  → 拉广告实时数据（get_data resource=ad_realtime）
  → 落库（保留 _data_source 字段标记口径）
  → 启动诊断引擎（规则匹配 → 生成工作项）
```

### 3.2 诊断引擎逻辑（insights.py 移植 + 扩展）

| 规则 | 条件 | 优先级 | 建议动作 |
|---|---|---|---|
| 超成本起量 | real_cpa > 考核价 × 1.2 且消耗 > 3000 | P0 | 检查素材/出价，建议降价或暂停 |
| 超成本 | real_cpa > 考核价 × 1.2 | P1 | 建议调整出价或时段 |
| 0 曝光 | 曝光 < 3000（72h） | P0 | 检查定向/出价/审核状态 |
| 消耗断崖 | 日消耗环比下降 > 30% | P1 | 排查原因（素材衰退/竞争/平台调整） |
| 高消耗零转化 | 消耗 > 100 且真实转化 = 0 | P1 | 建议暂停或检查转化回传 |
| 优质可扩量 | real_cpa ≤ 考核价 且消耗排名前 30% | 机会 | 建议复制/扩预算 |
| Gap 异常 | 账面转化 vs 真实转化差距 > 30% | P1 | 排查归因口径问题 |

### 3.3 多用户数据隔离

```
BUC 登录 → 拿到 userId（工号）
  → 调 get_data 时传入该 userId → 启航返回该用户有权限的账户
  → 我们的库按 userId 建索引 → 查询时 WHERE user_id = ?
  → 每个用户只看到自己的数据
```

**关键**：不需要自己维护权限表——启航接口已经按 userId 做了权限过滤。我们只需要把 BUC 拿到的 userId 传进去。

## 4. 技术架构

```
┌─ 前端（Next.js，托管在 FaaS）
│   ├─ BUC 登录（NextAuth.js）
│   ├─ 四角色视图（阶段一只做优化师）
│   └─ 调后端 API
│
├─ 后端 API（Node.js / Koa，托管在 FaaS）
│   ├─ GET /api/accounts?userId=xxx → 调 get_data 返回账户数据
│   ├─ GET /api/dashboard?userId=xxx → 聚合后的大盘数据
│   ├─ GET /api/alerts?userId=xxx → 异常列表
│   ├─ POST /api/work-items/:id/resolve → 标记处理
│   └─ POST /api/work-items/:id/ignore → 标记忽略
│
├─ 定时任务（进程内 node-cron）
│   ├─ 每日凌晨：全量拉取 + 诊断
│   └─ 每 4 小时：增量拉取当日数据
│
├─ 数据库（阿里云 RDS MySQL）
│   ├─ accounts（账户基础信息）
│   ├─ daily_metrics（每日指标快照）
│   ├─ ad_metrics（广告级指标）
│   ├─ alerts（诊断结果/工作项）
│   └─ users（BUC 用户信息缓存）
│
└─ 钉钉推送（阶段二）
    └─ 复用现有网关的 dingtalk.js
```
