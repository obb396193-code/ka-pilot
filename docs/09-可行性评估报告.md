# 可行性评估报告（OS 回收 · 原文存档）

> 来源：OS 2026-08-13 输出《外部可视化平台对接 Multica + 快手广告 Skill 体系》
> **这是当前关于"外部如何对接"的权威事实版，分析结论见 `docs/05-落地路径与鉴权.md` §7。**

## 一、Multica 对外接口能力

1. **HTTP API/SDK/OpenAPI**：后端必然有 HTTP API（CLI 只是客户端，`--server-url` 指向 `http://julang-agent.alibaba-inc.com/multica`，`setup self-host --help` 确认 CLI→HTTP 架构），但**没找到公开 OpenAPI spec 或 SDK**。需问平台团队。
2. **非交互登录/服务账号**：**已确认支持**。两种 PAT：`mul_...`（用户级）和 `mcn_...`（**Cloud Node PAT，专门给机器/服务身份的非交互凭证**）。来源：`multica login --help`。
3. **短期凭证/委托授权**：`mcn_` 是**长期**机器凭证（已确认）；refresh-token、短期凭证、impersonate 委托授权未找到，**无法确认**。
4. **写操作是否必须跑在 agent 沙箱**：合理推断不必须——`--workspace-id/--server-url` 均可从命令行/环境变量传，`multica daemon start` 理论上任何机器可跑。
5. **Webhook 触发（已确认）**：`multica autopilot trigger-add --kind webhook` 生成无鉴权端点 `POST /api/webhooks/autopilots/{token}`，两种模式：`create_issue`（建 issue）和 `run_only`（不建 issue）。

## 二、外部可视化平台调用方式逐项判断

| 问题 | 判断 | 依据 |
|---|---|---|
| HTTP 请求查数并同步拿结果 | **不支持同步，支持异步** | 只能 webhook 异步触发 + 轮询，无同步结构化 API |
| 触发批量调价并拿执行状态 | **异步可行，但会卡在确认门** | preview/execute 强制用户确认，除非 prompt 明示跳过（＝绕开安全设计） |
| kuaishou-cli 脱离沙箱独立调用 | **不支持** | CLI 不持有真实 token（占位符），真 token 由本地 MITM 代理 + 奇航平台服务端动态注入，链路在阿里内网，公网不可达 |
| 传参同步拿结构化结果的正式接口 | **不支持** | 现有通路全是异步模型，返回是 agent 自由文本，非固定 schema |
| cloud-cli Open API 被外部后端直调 | 技术可行但受网络策略限制 | `/open-api/v1/` 支持 Bearer/X-API-Key，端口 58596 绑 0.0.0.0，容器网络策略能否放行不确定；port-mapping 是临时公网 URL，沙箱一关就失效 |
| webhook body 能否作参数注入 agent 上下文 | **无法确认** | run 记录有 `trigger_payload` 字段（设计上预留），但实测采样全 None |

## 三、kuaishou-cli 完整能力（已确认）

- 已封装 **17 个 MAPI endpoint**（账户信息/余额/预算、计划/广告组/创意增删改查、素材上传、原生广告授权等）；`--output {json,table,raw}`（默认 json）、`--input/-f` 传 JSON、**`--dry-run` 预览**。
- **鉴权＝沙箱代理注入式**：CLI 不落地真实 token。链路 `CLI → 本机 MITM 代理(18082) → 奇航代理 → 快手 MAPI`；身份来自 `JULANG_OS_USER_IDENTITY` / `MOZI_USER_ID` 环境变量。
- 无服务端异步任务机制，操作同步阻塞；批量靠本地分批（改价 50/批、上下线 10/批）+ 少量重试。
- README 提到 raw 透传子命令，**代码里实际没实现**——文档与代码有出入。
- **Skill 只是"说明书"，不是调用 CLI 的必经网关**：实测跑了未被任何 SKILL.md 覆盖的只读命令，成功。
- 无独立 JSON Schema，`connectors/*.md` 字段表是人读版 schema；测试用例仅 `ks-create-ad-script`（46 项）和 a1（29 项）有。

## 四、批量/幂等/审计现状

- 分批+重试代码层面已实现；退避是固定间隔递增，非严格指数退避。
- **无请求级幂等键**：改价/下线/改时段媒体接口本身有一定幂等性，但**创建广告不幂等，重复调用会重复创建**。
- **确认门是流程约束，不是代码强制拦截——关键风险点**：绕过 agent 直接调 CLI，确认门形同虚设。
- 审计有 `~/.claude/audit/audit.jsonl` 记录工具调用，但无专门广告操作审计，也没确认执行结果自动写回 Multica issue。

## 六、可行性结论（OS 原判）

**A. 现在能直接做的**
1. 外部 Web 应用 POST autopilot webhook 触发 agent 查数/操作，轮询 autopilot runs 拿结果——不用装 CLI、不用进内网。
2. 只读数据展示（触发 agent 跑 unit list / account info，解析结果）。
3. 用 `mcn_` Cloud Node PAT 在内网机器独立跑 Multica issue CRUD。
4. 所有写操作支持 `--dry-run`，可做前端预览。

**B. 缺但可申请的最小能力**
1. `trigger_payload` 传参能力正式化（目前实测为空）。
2. Multica 对外 HTTP API/OpenAPI 文档。
3. raw 透传子命令真正实现。
4. 奇航代理独立 API Key/OAuth，让查数不用绕沙箱。

**C. 被安全机制明确禁止的**
1. 快手真实 token 提不出沙箱——设计上就不落盘。
2. 绕过确认门直接下发写操作——这是主动破坏安全设计，不是能力缺失。
3. 沙箱出网流量绕开 MITM 审计——做不到。
4. 公网直连 cloud-cli 端口——容器网络策略会挡；port-mapping 是临时方案。

**D. 推荐最小架构**：外部 Web 应用 → POST webhook → Multica 派发 agent → agent 跑 kuaishou-cli → 结果写 issue comment → 外部应用用 `mcn_` PAT 轮询 issue/runs 拿结果展示。写操作设计成**"两次 webhook 调用"**（预览 + 确认执行）以保留确认门。

**E. 只读 Demo 打通 1-3 个接口**：autopilot webhook 触发（必须）、runs 查询取结果（必须）、trigger_payload 传参（强烈建议）。预计在有 workspace 的 `mcn_` PAT + 配好 autopilot 前提下 **1-2 天跑通只读 demo**。
