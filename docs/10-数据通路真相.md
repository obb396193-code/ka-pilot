> **可信度说明**：本页核心结论全部来自代码原文摘录，可信度高；但注意 §5——另一会话的 OS 与 09 报告存在信息冲突，凡冲突处以代码原文为准、以实读文件为最终权威。

## 0. 名称校正

- 当前通用安装入口名称是 `rta-data-queryer-daemon` 1.0.4；它是守护技能，实际安装的业务查询技能为 `rta-data-queryer` 1.0.4。
- 本页最初实读和 2026-08-20 OS 真请求使用的是 `ks-data-queryer` 1.0.2，即快手定制实现。它与通用包共享四类 connector 和 `get_data` endpoint，但增加了默认媒体 `KUAISHOU`、502/503/504/网络超时重试及 `insights.py` 等差异。
- `qihang-monitor` v1.0.2 是监控守护技能；其业务包内 Skill 名为 `ad-hourly-monitor`，明确依赖 `rta-data-queryer`，不是新的底层数据源。
- 因此本文接口协议结论同时适用于已核的 rta/ks 两个变体；具体重试、默认媒体和分析脚本等实现行为必须按版本分别判断。

## 1. ★真相：数据根本不在快手 MAPI，在奇航平台

`ks-data-queryer` 的全部连接器指向同一个端点：

```
GET https://qh.alibaba-inc.com/qihang/api/rta_auto/tmp/get_data
  ?resource=account|account_offline|account_realtime|ad_realtime
  &userId=<从环境变量读>&media=KUAISHOU&...
```

- 这条请求链由奇航接口直接返回，不是 agent 在请求时另调 DataWorks/FBI 拼接。
- **接口调用链里没有 DataWorks/FBI，不等于字段业务血缘一定与 BI 无关。** `account_real_conversion` 是否与 BI 同源/等价不能只靠客户端源码判断，必须用业务口径确认和逐日对平验证。

**这对架构是简化**：真正要对接的介质不是快手官方、不是 Multica、不是 FBI——是**奇航平台的一个 HTTP GET 接口**。它已经有现成字段：账户列表、离线结算口径、账户实时、广告实时。

## 2. ★conv_real 真相（第一优先问题，答案到手）

| 层级 | 字段名 | 含义 |
|---|---|---|
| 账户实时 | `account_real_conversion` / `account_cpa` | 真实转化数 / 真实转化成本（有真实转化才返回） |
| 广告实时 | `ad_real_conversion_h` / `ad_real_cpa_h` | 同上，广告级 |
| 离线结算 | `newaac_uv_attrib_install` | **仅 biz_name=CVR 时含义明确＝转化 UV**；其他业务线"语义待定"（文档原话） |

源码只能确认字段由奇航响应按行返回，**不能仅凭请求代码证明其上游业务血缘**。当前产品先按已确认的奇航字段取数；BI 后台保留为备用/增强数据源。两者是否同源、能否互换，进入正式结算前必须逐字段、逐数据日对平，不在此文档中凭推断定案。

## 3. 鉴权真相：没有 token，是裸的 userId（老板拍板放行，不再设障）

代码原文（ks_common.py）：

```python
ENV_JULANG_OS_USER_IDENTITY = "JULANG_OS_USER_IDENTITY"
ENV_MOZI_USER_ID = "MOZI_USER_ID"
# 无 API Key / Token / 签名机制，纯粹把身份字符串当 query 参数传给服务端
```

**老板 2026-08-13 拍板：不用在乎数据合规问题，只要能做到拿到数据就行。** 一期取数走这条通道，不设额外障碍（本质是在自动化老板自己工作范围的取数）。长期议题（服务身份、二期部门推广、身份归属）作为路线图待办归档，不再每次讨论。

## 4. 数据能力边界（代码确认）

| 项 | 结论 |
|---|---|
| 维度 | 账户、广告（ad_id）；**无计划/单元/创意独立连接器** |
| 时间粒度 | 日（ds）；广告实时 `hh` 已实测为 0..hh 含的累计快照，相邻快照可差分小时窗口 |
| 分批 | 账户 50/批、广告 80/批（可改），自动翻页 |
| 重试 | 仅 502/503/504 重试 3 次、2s 起指数退避；**鉴权失败直接抛出不重试** |
| 频控 | 无主动限速 |
| 新鲜度 | 当天 realtime 已实测为分钟级，并带 `last_sync_time`；offline 本次 D-1 空、D-2 命中，属批量结算分区且产出时间会波动，禁止硬编码 T-1/T-2 |
| 回溯上限 | 代码无限制，服务端未知（须实跑试探）；数组响应无分页外壳，全范围广告查询出现疑似固定行数截断 |

**工程注意**：`resolve_user_identity()` 还支持隐藏 CLI 参数 `--user-identity/-u`——说明服务端按 userId 校验权限，**同一接口换 userId 就是换数据范围**。这既是风险也是钥匙：搞清楚 userId 的权限体系 = 搞清楚谁能看哪些户（03/05 文档的数据可见范围问题可能直接在此解决）。

## 5. ⚠️信息冲突登记：两个 OS 会话说法不一致

| 主题 | 09 报告（前一会话） | 本轮（另一会话） | 处置 |
|---|---|---|---|
| `mcn_` Cloud Node PAT | "已确认支持，长期机器凭证" | **"在我可查范围内不存在"**（multica auth 只有 logout/status） | **存疑待证**：以实读文件为准，不写进任何架构依赖 |
| 奇航代理独立 API Key/OAuth | "缺但能申请" | "查不到被提出过的证据" | 视为不存在，不等待 |

**教训（进红线）**：跨会话的 agent 汇报会互相矛盾，且都会在"演示已确认"的包装下出现。**能拿到文件就逐行读文件，文件才是权威；拿不到就问关键事实；问不到的就标"未证实"，绝不把任何一条 agent 的话当既定事实进架构。**

## 7. 2026-08-20 真实执行补充

- `account_realtime` / `ad_realtime` 已用当天 `ds` 命中，`last_sync_time` 证明当次为分钟级新鲜；因此实时监控不能被描述成 T-2 延迟。
- `account_offline` 当次 D-1 为空、D-2 命中；这只说明当时最新结算分区，不是固定 SLA。产品应动态向前探测最新已产出分区，并展示实际结算数据日。
- 页面、报表和 Agent 回答必须携带 `口径 + 数据日 + 更新时间/最新同步时间`，避免把实时数用于结算，或把离线延迟误写成实时延迟。
- 本轮没有用历史 `ds` 执行 realtime。最新版 `rta-data-queryer` 的补洞代码与 `ad-hourly-monitor` 的今日/昨日同比流程都会这样请求，说明是官方 Skill 的实现预期；服务端实际支持范围仍待下一轮真实探针。
- 当前一期优先走奇航 `get_data`；BI 后台作为备用/增强路径保留。如果奇航在产品 Worker/FaaS 通路联调失败，再切换或并行验证 BI，不提前把未接通的 BI 设计成主依赖。

## 8. 2026-08-20 第二轮真实执行补充

- `ad_realtime` 的 hh 累计语义、相邻快照单调关系和较早时点整行省略已实证；返回字段本轮不含 null，但不能据此删除动态 Schema 防护。
- `account_offline` 跨日区间含首尾且带 ds；同一成熟日跨日与单日逐行一致。可以用于功能测试，但生产是否改为跨日批量仍需响应上限验证。
- D-1 在同一天下午由空转非空，证明离线重查必须贯穿日内；一次空只能记 `not_observed`，一次非空只能记 `observed_unverified`。
- 平台没有分区完成标记，产品不能显示“奇航已完整产出”；只能展示最后观测时间、行数/指纹变化和本产品稳定性判断。
- 无过滤广告实时疑似固定行数截断。所有生产 `ad_realtime` 必须带 accountIds/adIds；单账户或分片结果恰好命中边界时阻断归因，等待进一步拆分或人工确认。
