## 阶段 0 ｜ 立项与可行性（08-13）

**做了什么**：确定产品形态（多用户登录系统，CLI 鉴权走 OS/Multica）；架构主干定为"异步 ETL 落自有库"；找到 a1 faas 是内网落地主路径；解开 `mcn_` 令牌之谜。

**方法**
- 先问硬边界再设计：第一轮就问内网 OS agent"token 能不能借"。OS 拒绝，我们认同并写成原则——**产品用自己的身份，不借任何人凭证**。这条原则后面挡掉了至少三次"先借个 token 跑通"的诱惑。
- 冲突登记不猜：两个 OS 会话对 `mcn_` 是否存在给出矛盾答案（#57）。做法是登记冲突、写清各自查了什么面，第三轮让 OS 实测 `multica login --help` 才定案——两个会话都没撒谎，查的子命令不同。
- 找内部先例：发现部门业务侧已有人做出能调 OS 查数的产品（#28），以及老板自己已有钉钉↔OS 网关（#33）。**先例 = 可行性证明 + 可复用资产**。

**坑**：一开始以为"鉴权全在 OS 手里"（#9 推翻）。文档读出来的架构和实测出来的架构不一样。

**教训**：可行性阶段的产出不是 PPT，是一份"内网 OS 实证总账"（`docs/19`），每条标证据等级（真实执行 / 源码实读 / 平台文档 / 合理推断 / 未证）。后面所有设计只允许引用前三级。

## 阶段 1 ｜ 数据通路真相（08-14）

**做了什么**：实读 ks-data-queryer / kuaishou-cli / qihang-cli / rta-data-queryer 五份源码；发现奇航 `get_data` 是裸 `userId` query 参数、无 token 无签名；`account list-by-user` 无 token 直连账户归属；FaaS 到奇航和私有数仓两个域名实测都通。

**方法**：**读代码不读说明**。SKILL.md 写的是给 agent 看的用法，client.py 里才是真实的 URL、参数、超时和错误处理。读完直接得出"最硬的两块骨头（账户归属+可见范围）已有现成 API"（#67）。

**教训**：交互模式在这天定型——**外网设计+编码，内网 OS agent 部署+测试+运维，老板中转**。所有内网事实都要 OS "贴命令和原始输出（凭证打码保留字段名）"。

## 阶段 2 ｜ 功能全景 → PRD v1.6 冻结（08-17～18）

**做了什么**：老板拍板"不分排期，一次规划完整版"；功能全景 v1→v2；八路 sub agent 并行审查（#98）→ 老板分两批处置 → PRD v1.0；二轮查漏 → v1.1；REQ 126 条基线对照；Codex 复核 R-003/R-004 → v1.2～v1.5；v1.6 冻结 + 验收基线总档（105 条）。

**方法**
- 多角度审查用"八路 sub agent 各带一个视角，不局限现有上下文"，回收后**由老板逐条处置**而不是 agent 自己合并——决策权留给人。
- 交叉复核用另一家模型（Codex）；每轮修完用 **grep 验证清零**（"充值提审"等被废术语全仓搜到 0 才算清）。
- 参考件消化要"抽口径"不"抄结构"：KA 日报规范 v2.0（#110）抽出 12 模块字段；老板澄清 `/1.09` 是返点折算系数不是税（#111）——**一个系数口径错了整套 CPA 都错**。

**坑**：术语反复（同一概念三种叫法）导致审查意见互相打架；解法是术语表 + grep 清零。

## 阶段 3 ｜ 开工三件套（08-18～19）

**做了什么**：`docs/23-开发协作规范.md`（信箱 `docs/relay/inbox-*.md` / 台账 / SHA 逐条审计 / 路径限定 commit / 不 push）；契约包 `packages/contract/{schema.sql, api.md, metrics.md, fixtures/}` 作为**唯一出口**；契约 v1.1 九条裁决（多租户主键、账户三键、鉴权失败业务码等）；分工 arch/be/fe/OS。

**方法**

## 阶段 4 ｜ 后端高速批次 B1–B22（08-19～21）

**做了什么**：Codex 三天完成 B1a/B1b/B1c 数据层、B2 队列、B3 安全执行、B4 任务经营、B5 Agent 运行时（Claude Agent SDK + CCSwitch 式网关）、B6 报表、B7 工作流、B8 知识库、B9–B11 真实奇航适配与小时监控、B12–B18 素材域、B19 结算、B20 资产治理、B21 未触发诊断、B22 IdeaLab ASR。台账一天最多 82 条（08-20）。

**方法**
- 每批固定流水：设计（老板批方案 A/B）→ 逐文件 TDD 实施计划 → Task 1..n → 全量质量门禁（四包测试/覆盖率/复杂度/audit）→ `P-0xx` 交审入口 + 回填 SHA。
- **OS 只读探针驱动修 bug**：五轮探针每轮只测一件事，真实响应改了五个"文档说的"：日期要 `YYYYMMDD`、离线分区 D-1 空 D-2 才有、`hh` 0..24 且 25 静默钳制、无过滤 2000 行静默截断、素材 CDN 返 `application/octet-stream`、ASR 只收 16k 单声道 WAV。**每一条都是"文档 vs 实测"的差**。
- 自审批次（#184–#193）：B1–B8 做完后 Codex 自己多角度审出 14 个 P0，修 6 个、8 个抛给 arch 裁决——**实现方自审 + 架构方裁决**分层。

**坑**
- Docker 磁盘 99% → PG 门禁跑不了（#227/#230）；真 PG 门禁不能用"上次的快照"代替。
- 后端交付快到审查跟不上：31 条 P-0xx 全部 ⏳ 无人独立审计，一直堆到 09-04。

**教训**：实现速度不是瓶颈，**审查带宽是**。没有独立审查的交付 = 未审基线，后面要整批回补。

**坑**

**教训**：角色可以合并，**审查权不能合并**。一个会话自己交付自己审，等于没审。

## 给文章的钩子（观点，待验证）

1. **Harness >> 模型**：同一个 Codex，有契约+信箱+台账时三天 300 条交付可审；没有独立审查时 16 天产出变"未审基线"。
2. **内网 agent 是传感器不是执行器**：五轮只读探针改掉五条"文档说的"，比任何设计评审都有效。
3. **契约先行在多 agent 下是唯一的协调语言**：字段名、状态机、错误码谁都不发明，才能让三个模型并行不打架。
4. **审查权不能和实现权合一**——这是人类组织里的老规矩，在 agent 团队里同样成立，而且失效更快。

### 坑：多工作树共用 node_modules 会"串包"（2026-09-06）

- 现象：arch 在隔离工作树复跑 be/r009，worker 2 个测试失败 + tsc 报缺 `channelCoefficientOp`——这个字段只在 be/r010 才有。
- 原因：为省一次 npm install，把 `apps/worker/node_modules` 整目录软链到 Codex 工作树；里面 `@ka/domain -> ../../../../packages/domain` 是相对链，按软链**真实位置**解析，落到了 Codex 工作树（已切到 be/r010）的源码。
- 修法：node_modules 建成真目录，第三方包逐个软链过去，`@ka/*` 单独指回本工作树的 packages。原则：**workspace 内部包永远指自己这棵树**。
- 教训：门禁失败先问"跑的是不是我这棵树的代码"，再查代码。
