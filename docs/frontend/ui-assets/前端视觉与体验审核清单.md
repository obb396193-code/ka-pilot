# 前端视觉与体验审核清单

> 用途：前端完成一个组件、页面或批次后，用同一套证据审核数据、内容、美观、排版、布局、动画、交互、响应式和可访问性。
> 依据：`frontend-product-standard.md`、当前 PRD/契约、`apps/web/AGENTS.md`、W3C APG、Vercel Web Interface Guidelines 和本项目数据/写操作红线。
> 原则：规范是推荐基线，不是僵硬审美答案；真实页面若不好看或不好用，可以调整 token，但必须留下跨页面、跨主题和跨视口的验证证据。

## 1. 审核输出

每次审核复制本文件中的“审核报告模板”，保存为：

```text
docs/frontend/ui-assets/reviews/YYYY-MM-DD-<页面或批次>-frontend-review.md
```

审核只允许三种结论：

- **通过**：质量 P0=0、未批准 P1=0，核心状态和证据齐全，视觉/内容没有明显短板。
- **有条件通过**：P0=0；存在已明确负责人、截止条件和影响范围的 P1/P2，不阻断当前验证环境。
- **不通过**：存在任一 P0，或关键证据缺失到无法判断数据/权限/写操作/核心体验。

视觉评分不能抵消 P0/P1。例如页面很漂亮，但数字算错或越权，仍然是不通过。

## 2. 问题等级

| 等级 | 定义 | 例子 | 处置 |
|---|---|---|---|
| 质量 P0 | 会造成错误决策、越权、敏感泄露、错误写入或核心不可用 | CPA/达成率算错；无权限仍看到数据；写操作无确认；密钥进浏览器；核心路由白屏 | 禁止合并/上线，必须先修 |
| 质量 P1 | 关键体验严重受损但未直接造成越权/错误写入 | 移动端不可用；错误态缺失；键盘无法完成主流程；图表明显误导；无法追踪错误 | 本批次关闭；延期必须明确批准 |
| 质量 P2 | 局部一致性、边界态或视觉质量问题 | 间距不齐；次要文案不清；少量长文本溢出；非核心动画生硬 | 进入整改清单并复审 |

报告中必须写“质量 P0/P1/P2”，不要与产品优先级或业务告警级别混用。

## 3. 审核前必须拿到的证据

- [ ] 页面/组件名称、路由、commit SHA、负责人。
- [ ] 对应 PRD、契约版本、权限角色和业务口径来源。
- [ ] 使用的第三方组件来源、官方 URL、许可证、ref/hash、本地路径和修改说明。
- [ ] 1440、1366、390 三档截图；必要时补 1024/平板。
- [ ] light、dark 和本批次涉及的 tweakcn preset。
- [ ] normal、loading、empty、partial、stale、error、no-permission、disabled；不适用的状态写理由。
- [ ] 最大数字、零、null、负数、超长中文/英文、无空格长串。
- [ ] 关键交互录像或 Playwright trace：筛选、分页、下钻、弹窗、写操作确认、失败重试。
- [ ] Tab/Shift+Tab、Enter/Space、Escape、方向键、焦点回收和 reduced motion 结果。
- [ ] TypeScript、lint、production build、console、视觉回归和核心测试结果。

缺少 PRD/契约、权限、真实状态或写操作证据时，不能只凭静态截图签字。

## 4. 审核顺序

严格按以下顺序，前一层有 P0 时可以停止美化审核并先返修：

1. 契约、权限、数据与写操作。
2. 页面状态和错误恢复。
3. 信息架构与内容。
4. 文字、数字和日期格式。
5. 布局、留白、密度和响应式。
6. 颜色、主题、组件一致性与美观。
7. 交互、动画和反馈。
8. 键盘、焦点、读屏与触控。
9. 性能、console、来源和许可证。

## 5. 硬门禁检查

### 5.1 数据、指标与内容真实性

- [ ] 页面字段、筛选、排序、分页、导出与契约一致。
- [ ] CPA、达成率、Gap、环比、目标状态来自 domain/API，前端没有自行重算。
- [ ] 单位、币种、时区、业务日、更新时间、数据来源和比较基线可追溯。
- [ ] `0`、`null`、无数据、部分数据、过期、无权限没有混为一谈。
- [ ] 图表、KPI、表格和导出的筛选上下文一致。
- [ ] 示例/脱敏数据有明显标识，不冒充真实线上结果。
- [ ] 页面文案没有把目标、计划或待验证能力写成已经上线/已经验证。

### 5.2 权限、安全与写操作

- [ ] 权限和数据范围由服务端控制，不只是在前端隐藏按钮。
- [ ] 浏览器 bundle、HTML、URL、localStorage 和日志无长期 token、密钥、服务凭证和敏感 userId。
- [ ] 媒体写操作有预览、明确影响范围、二次确认、幂等/防重放、结果和审计记录。
- [ ] stale/partial/no-permission 状态下高风险动作被禁用或有额外确认。
- [ ] 用户输入、Markdown/HTML、链接和文件名经过安全处理；没有不可信 `dangerouslySetInnerHTML`。
- [ ] 错误采集、截图和日志没有真实账户昵称、账户 ID、消耗、考核价和内部人名。

### 5.3 状态与错误恢复

- [ ] 首次加载与局部刷新有不同反馈，不用整页闪烁掩盖更新。
- [ ] 空态解释为什么为空，并提供合适下一步；无权限不用空态伪装。
- [ ] 错误态说明问题、下一步、重试和问题编号。
- [ ] 重试保留安全的筛选和用户输入；不会重复提交写操作。
- [ ] 部分成功明确哪些成功、哪些失败，不能用一个绿色 toast 概括。
- [ ] Error Boundary/路由异常不会让整个应用永久白屏。

## 6. 内容与信息层级审核

- [ ] 打开页面 3–5 秒内能看懂：当前范围、数据是否健康、最重要结论和下一步。
- [ ] 页面顺序符合“结论与健康 → KPI → 筛选 → 趋势证据 → 明细下钻 → 动作”。
- [ ] 一页一个主标题；区块标题描述问题或对象，不写“模块一”“图表 1”。
- [ ] KPI 只保留当前决策最重要的 4–6 个；次要指标进入详情或可配置区。
- [ ] 按钮使用具体动作，如“创建监控任务”“确认调整预算”，不滥用“确定”“继续”。
- [ ] 错误、警告、状态和空态文案准确、简短、可行动。
- [ ] 同一概念全站叫法一致；账户/计划/任务/产品等业务实体不混称。
- [ ] AI 建议与事实数据有视觉和文案区分；引用、置信度、未知和写操作确认可见。

## 7. 文字与数字格式审核

### 7.1 字体与文字

- [ ] 字体角色清楚：页面标题、区块标题、正文、标签、辅助信息不靠随意字号堆叠。
- [ ] 字体、字号、粗细、行高来自语义 token；无大量局部 magic number。
- [ ] 中文正文和长说明行长可读；标题换行自然，不出现孤零零单字或大段全宽文本。
- [ ] 12px 仅用于确有密度需求的辅助/表格信息；核心内容没有为了塞下而无限缩小。
- [ ] 超长账户名、英文 URL、数字串有 wrap/truncate/tooltip/详情策略。
- [ ] 图标按钮有可访问名称；图标没有替代关键状态文字。
- [ ] 加载用 `…`；错误文案包含解决路径；没有不必要的英文大写和过宽字间距。
- [ ] 字体 fallback 后层级、卡片高度和数字列仍稳定。

### 7.2 数字、金额、比例和日期

- [ ] 数字/日期统一 formatter，使用 `Intl.NumberFormat/DateTimeFormat` 或项目封装。
- [ ] 数字列使用 tabular numbers，并按小数点/单位对齐。
- [ ] 金额显示币种；百分比明确 API 口径；计数、CPA、Gap 精度符合业务决策需要。
- [ ] 总览缩写为万/亿时，tooltip/详情能看精确值；同一列没有无规则混用。
- [ ] 正负变化不只靠红绿；0 变化、无比较、无值分别表达。
- [ ] 日期/时间显示或可追溯时区和业务日；相对时间可查看绝对时间。
- [ ] 最大值、负数、0、null、极小百分比和超大金额均未破坏布局。

## 8. 布局、留白、密度与响应式审核

- [ ] 页面层、区块层、组件内部三层留白清楚；同层间距小于跨层间距。
- [ ] 视觉层级主要靠留白、字号、色阶和分组，不靠给每块都套边框/阴影。
- [ ] 核心内容在首屏有合理优先级；不是把所有卡片平均铺满。
- [ ] 栅格对齐稳定，标题、筛选、KPI、图表和表格边缘有可解释关系。
- [ ] 数据页充分使用宽屏，但正文/说明不会横跨整屏难以阅读。
- [ ] compact/default/comfortable 密度由 token 或组件 variant 控制，不是复制组件。
- [ ] 1440/1366/390 无非预期横向溢出；移动端不是桌面页面等比缩小。
- [ ] 移动端保留高频筛选、关键 KPI 和主要动作；低频内容有合理收纳。
- [ ] sticky、冻结列、弹窗、抽屉和底部操作条不遮挡焦点、内容或安全区。
- [ ] long text、最大数字、错误横幅、空态和加载骨架下布局仍稳定。

## 9. 颜色、主题、组件一致性与美观审核

- [ ] 页面符合已拍板整体气质，但没有机械复制某个 UI 官网的品牌色。
- [ ] light/dark/preset 中正文、辅助文案、边框、状态和图表均可读。
- [ ] 主色只强调关键选择与主要动作；页面没有十几个同权重高亮。
- [ ] 状态色语义一致；危险、警告、成功、信息在组件和图表中不冲突。
- [ ] 图表 palette 与页面 token 同源；系列可区分且不使用无意义彩虹色。
- [ ] 圆角、阴影、边框、图标大小和控件高度来自有限 token，不出现“每张卡都不一样”。
- [ ] 同一能力复用同一业务组件；不存在页面内临时手写的第二套按钮/筛选器/KPI。
- [ ] 页面有明确视觉焦点和节奏，不过度装饰、不过度留白，也不是表格堆砌。
- [ ] 与相邻 2–3 个页面并排时属于同一产品，而不是不同模板拼贴。

### 美观判断的调整机制

如果严格套用推荐字号、间距或颜色后实际效果不好：

1. 先说明具体问题：层级不清、太松、太挤、对比不足、数字难扫读或品牌气质不符。
2. 优先调整语义 token/variant，不在单页散改。
3. 对 Dashboard、数据表、表单/任务流至少三个典型页面复测。
4. 同时复测 1440/390、light/dark 和超长/空错态。
5. 截图对比并记录最终拍板；如形成通用改进，回写规范和 token。

## 10. 交互与动画审核

- [ ] 每个动画能回答“什么变化了/来自哪里/操作是否成功”，纯装饰有明确克制理由。
- [ ] hover/active/focus/disabled/loading 反馈完整，状态不只靠颜色。
- [ ] 动画优先 transform/opacity；无 `transition: all`；不会频繁触发布局抖动。
- [ ] 支持 `prefers-reduced-motion`；关闭动效后信息和操作不丢失。
- [ ] 动画可被点击、Escape、路由或新状态打断，不要求用户等播放完成。
- [ ] 数字动画保留最终真实文本，读屏不逐帧播报，轮询更新不会不停滚动。
- [ ] 文字动效没有用于错误、警告、权限、表格正文、长文和关键按钮标签。
- [ ] Motion Primitives/Animate UI/其他动效只按需复制，许可证、依赖和体积可追溯。
- [ ] Drawer/Dialog/Popover 进入与退出方向符合空间关系，焦点到达时内容已可操作。
- [ ] 超过 5 秒的自动装饰动效可暂停/停止/隐藏。

## 11. 图表和表格专项审核

### 图表

- [ ] 每张图只回答一个业务问题，标题、单位、时间范围和比较对象明确。
- [ ] 图形类型与数据关系匹配：趋势、比较、构成、关系、漏斗没有滥用。
- [ ] 双轴有必要性、单位和颜色清楚；没有通过缩放制造夸张趋势。
- [ ] legend、tooltip、axis、markLine/目标线和空错态在所有主题可读。
- [ ] 图表有摘要/ARIA；色觉差异用户不只靠颜色区分。
- [ ] 数据量有缩放、抽样、聚合或降级；页面不卡顿。
- [ ] 下钻和导出继承筛选、权限、时区和口径。

### 表格/Data Grid

- [ ] 静态信息使用 table 语义；只有真正需要复合交互时才用 grid。
- [ ] 排序、筛选、分页、固定列、列配置和导出边界清楚。
- [ ] 数字右对齐/小数点对齐，文本左对齐，状态列宽度稳定。
- [ ] 长文本、固定列、横向滚动和移动端有明确方案。
- [ ] 键盘操作、焦点、选择、编辑和退出符合组件语义。
- [ ] 大列表服务端分页/筛选与客户端虚拟化职责清楚。

## 12. 无障碍、触控和键盘审核

- [ ] 使用语义 HTML；动作是 button，导航是 link，表格是 table/grid 对应语义。
- [ ] 表单有 label，纯图标按钮有 `aria-label`，装饰图标对读屏隐藏。
- [ ] Tab 顺序符合阅读顺序；焦点可见；sticky/overlay 不遮挡焦点。
- [ ] Dialog/Drawer 打开后焦点正确，Escape 关闭，关闭后回到触发器。
- [ ] toast、异步验证和状态更新使用合适的 live region，不刷屏。
- [ ] 拖拽、滑动、手势有点击和键盘替代；触控目标足够大且无死区。
- [ ] 页面不禁用缩放；移动端 safe area、overscroll 和软键盘场景可用。

## 13. 性能、错误与来源审核

- [ ] production build、TypeScript、lint 和核心测试通过。
- [ ] console 无新增 error；warning 有明确处置，不把真实故障静音。
- [ ] 大列表虚拟化/分页；图表按需引入；非关键资源延迟加载。
- [ ] 图片有尺寸和 alt；关键字体有 fallback，避免明显 CLS。
- [ ] 错误上报包含 release/environment/page/correlation ID，并去除敏感字段。
- [ ] 第三方源码有官方 URL、许可证、ref/hash、本地路径和修改说明。
- [ ] Pro/Ultimate/Commons Clause/逐项待核来源没有被误发到公共 Registry 或复用仓库。

## 14. 可选视觉评分表

评分用于帮助比较和发现短板，不替代硬门禁。每项 1–5 分：

| 维度 | 分数 | 证据/说明 |
|---|---:|---|
| 信息层级与决策效率 | /5 | |
| 内容清晰与业务一致 | /5 | |
| 文字与数字可读性 | /5 | |
| 布局、留白与密度 | /5 | |
| 颜色、主题与组件一致性 | /5 | |
| 图表/表格表达 | /5 | |
| 交互反馈与动画克制 | /5 | |
| 响应式与触控 | /5 | |
| 键盘与无障碍 | /5 | |
| 状态、错误与恢复 | /5 | |
| **总分** | **/50** | |

建议解释：45–50 成熟；40–44 可用但仍需处理明显短板；35–39 有条件通过候选；低于 35 通常需要重新整理层级或组件，而不是继续局部抛光。只要存在 P0，分数再高也是不通过。

## 16. 审核者注意事项

- 不以“我个人喜欢”代替证据，要说清层级、扫读、对比、状态、任务效率或一致性问题。
- 不因组件来自知名库就默认好看、好用或适配本项目。
- 不只审桌面正常态，也不只审截图；必须实际操作和看动态状态。
- 不把某个 UI 库官网气质强行套到所有页面；项目 token 是统一层。
- 如果推荐规范确实不好看，审核者有责任提出更优 token 方案，而不是要求前端机械服从。
- 审核结束后，通用结论回写 `frontend-product-standard.md`，单页选择回写 `decisions/`。
