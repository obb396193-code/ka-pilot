# 前端交付总清单与未落地说明

> 用途：给前端 Agent 的统一交接入口，解释 UI 资产阶段已经完成什么、产品代码还要实现什么，以及上线前必须通过的安全、数据可靠性和质量门禁。
> 当前快照：2026-08-20。包安装与代码状态以实际仓库复核为准，文档中的“目录收录、源码缓存、正式准入”均不等于“已安装进产品运行时”。

## 1. 先说结论

UI 资产的**知识层、选型层、合法源码缓存层、规范层和离线展厅已经交付**；产品前端的**运行时接入、页面实现、Storybook、ECharts 正式图表层、主题 token 桥、产品级 Playwright 回归和错误上报尚未落地**。

这不是漏做同一件事，而是两层工作：

| 层 | 当前状态 | 含义 |
|---|---|---|
| UI 资产层 | 已完成 | 前端知道官方有什么、长什么样、源码在哪里、许可证是什么、同能力该怎么比较 |
| 产品实现层 | 待前端执行 | 针对具体 PRD/契约，选择资产、复制合法源码、适配业务状态、接 API、测试并上线 |

当前 UI 资产真相：17 条产品线、7,056 条逻辑资产；16 个可公开取源产品线有真实离线官方源码代表预览，React Bits Pro 只展示合法的付费锁定信息；高频隔离缓存为 73 个根资产 + 58 个依赖，共 131 个缓存记录、144 份源码文件。它们都未自动装入 `apps/web`。

## 2. “已经落地”和“还没落地”分别是什么

### 2.1 已经落地：前端可以直接使用的知识和资产

- 17 库全量能力目录、跨库能力索引和覆盖审计。
- 官方安装、修改、主题、迁移、许可证与更新规范摘要。
- 付费能力的免费替代策略，明确哪些能直接替换、哪些只能重组、哪些要先核许可证。
- 高频公开官方源码的隔离缓存、官方 URL、SHA-256、依赖与来源记录。
- 17 库真实源码比较墙：不是截图，代表组件在离线 sandbox 中真实运行。
- 前端 Agent 选型工作流、数据产品执行规范、来源隔离与质量验收规则。
- Vercel AI Elements、Kibo UI、Dice UI 正式准入；Animate UI、Motion Primitives 选择性准入。

### 2.2 尚未落地：必须在具体产品代码中完成的工程工作

| 未落地项 | 当前实证 | 到底要做什么 | 完成标志 |
|---|---|---|---|
| 具体页面选型与适配 | 缓存未进入运行仓 | 根据 PRD/契约选组件；多候选同容器对比；复制官方源码；接数据、权限和状态 | 页面使用的每个外部资产都有来源、ref/hash、修改记录并通过验收 |
| Storybook 组件展台 | 当前未安装/未配置 | 单独展示 KPI、筛选器、表格、空错态、抽屉、弹窗、Agent 对话等所有状态 | 可独立打开 stories，正常/加载/空/错/过期/无权限/禁用齐全 |
| ECharts 正式图表层 | 当前未安装；运行仓仍有 `recharts` | 建 ECharts 封装、业务模板、主题、空错态、ARIA、性能和导出规范 | 产品图表只接 domain/API 口径，并通过主题、响应式、无障碍和数据正确性验收 |
| tweakcn + Design Tokens 桥 | 主题目录已收录，机器化桥未实现 | 用语义 token 同时生成 CSS variables 和 ECharts theme | 切主题时页面组件与图表一起变化，不散落硬编码颜色 |
| 产品级 Playwright 回归 | 展厅做过浏览器 QA，但产品仓未配置测试项目 | 对核心产品页面做桌面/移动截图、关键交互、console、键盘与焦点测试 | 变更可自动发现布局、主题、交互和无障碍回归 |
| 错误上报与可观测性 | 未发现 Sentry 或等价产品集成 | 做用户可理解错误、工程异常采集、业务数据问题反馈三层通路 | 错误可追踪到版本/环境/请求，但不泄露敏感业务数据 |
| 页面状态矩阵 | 规范已经写，实际页面仍需实现 | 每个关键页面覆盖加载、空、错、过期、部分成功、无权限、禁用等状态 | 不再只有“正常有数据”的演示路径 |
| 安全与数据可靠性门禁 | 规则已定义，需随实现验收 | 权限、写操作确认、指标口径、时区、数据新鲜度、脱敏和 XSS 等逐项检查 | P0 阻断项为 0，P1 高风险均关闭或有老板批准的明确处置 |

“未落地”不等于继续无限调研 UI 库。下一步重点是前端 Agent 把上述能力接入真实页面。

## 3. ECharts 要不要把所有图表都扒下来

### 3.1 决定

要建立**官方全能力清单**，但不建议把官网所有示例源码整站镜像或一次性下载进产品仓。

理由：ECharts 是配置驱动、可按模块引入的图表引擎。官方已经提供 20 多种 series 类型以及坐标系、交互组件和主题能力；“官网有多少 demo”不等于“产品要维护多少组件”。真正对前端有用的是：

1. 记录官方全部能力，避免 Agent 不知道某种图表存在。
2. 为投放产品先做 8–10 个经过数据口径和交互约束的业务模板。
3. 只引入实际使用的 ECharts charts/components，控制包体和维护面。

官方入口：

- [ECharts Cheat Sheet：图表、坐标系与组件全清单](https://echarts.apache.org/en/cheat-sheet.html)
- [ECharts Features](https://echarts.apache.org/en/feature.html)
- [Data Transform](https://echarts.apache.org/handbook/en/concepts/data-transform/)
- [ARIA 无障碍说明](https://echarts.apache.org/handbook/en/best-practices/aria/)
- [下载与按需引入](https://echarts.apache.org/handbook/en/basics/download/)

### 3.2 官方能力清单应该记录什么

官方 series 能力包括：Bar、Line、Pie、Scatter、EffectScatter、Candlestick、Radar、Heatmap、Tree、Treemap、Sunburst、Map、Lines、Graph、Boxplot、Parallel、Gauge、Funnel、Sankey、ThemeRiver、PictorialBar、Custom。

坐标系包括 Grid、Polar、Geo、SingleAxis、Calendar；常用组件包括 Title、Legend、Tooltip、MarkPoint、MarkLine、MarkArea、Timeline、DataZoom、Brush、VisualMap、Toolbox、Graphic。

这里的“面积图、堆叠图、分组图、柱线组合图”通常是 Line/Bar 等 series 的配置组合，不必伪造成另一套第三方组件库。

### 3.3 投放 Agent 第一批真正要实现的业务模板

| 模板 | 解决的问题 | 关键限制 |
|---|---|---|
| 单/多指标趋势折线 | 消耗、转化、CPA、CTR、CVR 随时间变化 | 单位不同不得随意共轴；必须显示时区和数据更新时间 |
| 面积趋势 | 强调量级和累计变化 | 不用于容易误导的多系列重叠 |
| 分组/堆叠柱状图 | 账户、计划、产品或渠道对比 | 堆叠只用于可相加的同口径指标 |
| 横向 Top-N | 高消耗/高 Gap/高转化对象排序 | 显示排序口径、单位和被截断范围 |
| 柱线组合 | 消耗与 CPA/转化量的联合观察 | 双轴必须明确单位、颜色和基线，不能制造虚假相关性 |
| 散点/气泡 | 消耗 × CPA、CTR × CVR、异常账户分布 | tooltip 必须能追溯对象；气泡大小口径明确 |
| 转化漏斗 | 展现→点击→转化等阶段损耗 | 只使用同一统计窗口和同一归因口径 |
| 小时 × 日期热力图 | 时段表现、异常密度 | 必须有 visualMap、缺失值说明和时区 |
| 环形占比 | 少量类别的结构占比 | 建议不超过 6 类；类别过多改用排序条形图 |
| Gap/贡献瀑布 | 解释目标差距或增减贡献 | 可用堆叠 Bar/Custom 实现；每段贡献口径可追溯 |

Gauge、地图、桑基、旭日、主题河流、K 线、关系图等先留在官方能力清单，只有 PRD 出现真实问题时再启用。不要为了“图表丰富”而使用。

每个业务图表模板还必须记录：业务问题、输入数据形状、指标单位、最大系列/点数、颜色 token、tooltip、空/错/过期/部分数据、下载、钻取、键盘/ARIA、性能降级和禁止使用场景。

## 4. P0、P1 到底是什么

本项目里出现过三套 P0/P1，必须分开写，不能混用。

### 4.1 产品功能文档里的历史 P0/P1

旧 PRD 中 P0 常表示首批核心功能，P1 表示下一批增强。但项目已经拍板：**不再用 P0/P1/P2 作为开发排期**，而用 S/A/B 价值层级和工程依赖顺序规划完整版。旧标签只能当历史重要性提示，不能据此擅自砍功能或解释上线批次。

### 4.2 业务告警里的 P0/P1

- **P0 业务告警**：可能马上造成严重损失或失控，如快速超消耗、接近关键止损线、异常写操作，需要立即通知、升级和处置。
- **P1 业务告警**：高优先级异常，但不是当前分钟级灾难，需要在正常值守窗口内跟进。

它描述的是投放业务风险，不是代码质量等级。

### 4.3 前端审查里的 P0/P1

- **P0 阻断**：不能合并/上线。包括数据算错、越权看到数据、未经确认写入、密钥进浏览器、不可逆动作无确认、核心页面不可用、敏感数据外泄。
- **P1 高风险**：应在本批次关闭；若不能关闭，必须写明影响和得到明确批准。包括关键流程或移动端坏掉、加载/错误/无权限态缺失、键盘不可操作、图表严重误导、错误完全不可追踪。
- **P2 普通问题**：局部体验、边界态或视觉一致性问题，不代表可以永久不修。

前端交付报告必须写“质量 P0/P1”，不要只写裸的“P0/P1”。

## 5. 前端安全与数据可靠性清单

### 5.1 质量 P0：真实用户或真实数据进入前必须全部通过

- 浏览器 bundle、HTML、localStorage、日志中不得出现平台密钥、长期 token、服务凭证或可绕过权限的 userId。
- 权限与数据范围必须由服务端执行；前端隐藏按钮不等于权限控制。
- 所有媒体写动作遵循“预览 → 用户确认 → 幂等/防重放 → 执行结果 → 审计记录”；诊断默认只读。
- CPA、达成率、Gap、目标状态等业务指标由 domain/API 计算；前端只能格式化和展示，不能各页面自己重算。
- KPI、图表和表格必须显示或可追溯：单位、数据来源、更新时间、时区、筛选上下文、比较基线。
- `0`、`null`、无数据、数据过期、部分成功、无权限必须分开表达；不能把未知渲染成 0。
- 数据过期、部分成功或无权限时，高风险操作要禁用或明确二次确认。
- 用户输入、富文本、Markdown/HTML 和外部链接必须防 XSS；不能直接渲染不可信 HTML。
- 用户必须看得到可理解的错误、重试入口和问题编号；采集日志不得包含真实账户昵称、账户 ID、消耗、考核价、内部人名等敏感原文。
- TypeScript、lint、build 和核心流程测试通过；核心页面不能靠 console error 运行。

### 5.2 质量 P1：首个可用版本与扩大使用前完成

- 接入错误与性能可观测性：可选 Sentry 或内部等价方案，工具未拍板前不要把 Sentry 写成既定技术选型。
- source map 受控上传，错误带 release/version、environment、页面、请求 correlation ID；不公开源码和敏感 payload。
- 收集 Web Vitals 和关键页面性能，表格/图表大数据量有降级、虚拟化或聚合策略。
- Storybook 或等价隔离页覆盖关键组件完整状态矩阵。
- Playwright 覆盖 1440、1366、390 视口、主题、关键交互、console、Tab/Escape/方向键、焦点回收和 reduced motion。
- 增加“数字不对？上报”数据质量入口，携带指标名、时间范围、筛选、数据新鲜度和 correlation ID，不直接上传敏感原始数据。
- ECharts 业务模板通过主题、ARIA、tooltip、数据缩放、导出、空错态和性能验收。
- 与后端建立数据新鲜度、任务延迟、对账差异和异常率监控。

## 6. “错误上报”到底是什么

错误上报不是在浏览器控制台打印一句 `console.error`，也不是把所有原始业务数据发送给第三方。它有三层：

| 层 | 给谁看 | 示例 |
|---|---|---|
| 用户层 | 运营用户 | “数据加载失败，请重试；问题编号 A7F2”，保留当前筛选，不让用户猜发生了什么 |
| 工程层 | 前端/后端排障 | 自动记录 JS 异常、失败接口、页面、版本、环境、浏览器和 correlation ID，去除敏感数据 |
| 数据质量层 | 数据/业务负责人 | “数字不对？上报”：记录指标、时间范围、筛选、更新时间和问题描述，供查口径、延迟或数据源 |

当前仓库未发现 Sentry、Error Boundary、instrumentation 或等价统一链路，因此这项是“规范已定义、工程未落地”。第一版至少要有用户错误态、重试、统一错误编号和服务端 correlation ID；完整可观测平台可按工程依赖随后接入，但真实上线前不能完全没有错误可追踪能力。

## 7. “第一版完成”是什么意思

第一版完成不等于“正常数据下截图很好看”。一个页面要同时满足：

1. PRD、契约字段、权限和动作一致，指标不在前端私算。
2. 正常、加载、空、错误、过期、部分成功、无权限、禁用等实际状态齐全。
3. 单位、来源、更新时间、时区、筛选和比较基线可追溯。
4. 使用的外部组件有官方 URL、许可证、ref/hash、本地路径和修改记录。
5. 桌面/移动、多主题、键盘、焦点、弹层、reduced motion 可用。
6. 图表和表格不制造错误对比或视觉误导；可下钻、导出时权限一致。
7. 有用户可理解的错误、重试和问题编号；异常可追踪且不泄露敏感数据。
8. TypeScript、lint、build、核心交互和视觉回归通过。
9. 已知风险和未完成项写清，不能用静态假数据掩盖真实链路缺口。

Storybook 尚未装好时，可以先用“等价隔离页”完成组件状态验收，但必须避免只在最终业务页面里调样式；基础设施建立后再迁入 Storybook。

## 9. 给前端 Agent 的实际阅读顺序

1. 先读本文件，确认“UI 资产已完成”不等于“页面已实现”。
2. 读 F-004、`apps/web/AGENTS.md` 和当前页面 PRD/契约。
3. 在 `capabilities.json`、catalog、展厅和 guide 中做候选筛选。
4. 多候选按模板同容器对比，老板拍板后才标 `preferred`。
5. 从 `source-cache/manifest.json` 指向的官方 payload/raw source 复制，禁止从预编译预览 bundle 反推源码。
6. 先建组件状态，再接页面/API；图表按本文件的业务模板建设，不照搬官网 demo。
7. 按质量 P0/P1、`frontend-product-standard.md` 和 F-004 验收后交付。
8. 用 `前端视觉与体验审核清单.md` 出正式审核报告；规范参数若导致真实页面不好看，调整语义 token 并提交跨页面/主题/视口对比证据。
