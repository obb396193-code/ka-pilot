## 1. 结论先行

当前代码不是“可以直接接真实媒体写权限上线”的完整后端。

- 代码级质量门禁是绿的：**406 个默认测试通过，1 个真实 SDK 烟测为 opt-in；四个 npm 包依赖审计均为 0 漏洞**。
- 但测试主要证明单模块契约和既定 happy path，并不能证明端到端业务闭环正确。
- 本轮确认了 **14 个上线前阻断项（P0）**、**17 个重要修复项（P1）**。
- 没发现直接拼接用户 SQL、Agent 直接执行媒体写操作、明显依赖漏洞等 Critical 级问题。
- B2-B8 大量能力尚未注册生产 Runtime、没有公开 API/前端或真实 OS 接缝，这是已声明的实施边界，不应伪装成已交付，也不应和代码 bug 混在一起。

从第一性原理看，这套系统上线前必须守住五件事：

1. **数据是真的**：缺数不能显示成 0，归属不能重复，今日暂缺字段不能伪装成精确值。
2. **写操作最多执行一次且可对账**：确认、租约、执行结果、T+1 回收必须形成可恢复闭环。
3. **租户和身份不能靠调用方自觉**：账户、凭证、任务、知识文本都必须在持久化边界重新校验。
4. **消息不能悄悄丢**：先持久化再 ACK，入站和出站都要有可重领、可重试的状态机。
5. **“已实现”和“已接线”必须分开**：领域模块存在不等于可被用户真实调用。

## 2. 审查方法

| 视角 | 核心问题 |
|---|---|
| 第一性原理主审 | 数据真相、写安全、租户边界、失败恢复是否构成闭环 |
| 安全独立审查 | 越权、凭证泄露、确认绕过、注入、资源耗尽、审计完整性 |
| 业务正确性独立审查 | 是否符合优化师真实工作、成本/跑量/任务归属是否会误导决策 |
| 可靠性独立审查 | 并发、租约、幂等、消息交付、状态机、分区和崩溃恢复 |
| 质量门禁复核 | 测试、依赖漏洞、已声明范围和真实运行证据 |

独立审查结论均由主审重新定位源码核对；没有直接采信 Agent 汇报。

## 3. 上线前阻断项（P0）

### P0-01：全量/增量 ETL 只写 raw，不会继续生成 canonical

- 证据：`apps/worker/src/etl/full-handler.ts:27-38,109` 只 append raw 后 finish；Runtime 虽注册 `canonical_merge`，但 full/incr 没有 enqueue。
- 触发：正常跑每日全量或增量任务。
- 后果：raw 有新数据，但经营看板、规则、报告仍读旧 canonical；系统表面“任务成功”，业务数据不刷新。
- 修复：同一业务链上显式编排 `raw -> canonical -> quality`，并以数据日期/账户范围作为幂等键。

### P0-02：账户发现没有同步账户主表

- 证据：全量任务把 `account` 资源写入 raw 并收集 accountId，但没有 upsert `accounts`；后续 canonical 的 settings 查询依赖账户主表。
- 触发：奇航返回一个平台尚未登记的新账户。
- 后果：账户数据已抓到但无法进入有效设置/归属/看板链路，甚至直接失败。
- 修复：建立账户发现同步步骤，校验媒体与 workspace 后 upsert 主表，再进入指标抓取。

### P0-03：回填进度只观察 backfill_day，可能提前宣告完成

- 证据：`apps/worker/src/runtime.ts:93-100` 仅在 `backfill_day` 完成/失败时刷新批次进度；canonical/quality 不在完成判定中。
- 触发：历史日 raw 完成，但 canonical 或质量检查仍排队/失败。
- 后果：用户看到“回填完成”，实际看板仍缺失或质量未通过。
- 修复：批次按完整 DAG 的终态计算，至少覆盖 raw、canonical、quality。

### P0-04：缺失数据被统一 COALESCE 为 0

- 证据：`packages/db/src/semantic-query-metrics.ts:31-43` 对全部指标 `COALESCE(sum(...), 0)`；`report-facts-source.ts:38-66` 再包装成 finite。
- 触发：ETL 未到、权限失败、某字段今日没有来源或范围内无数据。
- 后果：“没有数据”被误读为“真实消耗/转化为 0”，会直接误导停投、加预算、成本判断和管理汇报。
- 修复：引入 `finite/missing/provisional/error` 状态，只有业务语义确认的零才允许显示 0。

### P0-05：一个账户同一天可同时归属多个任务，金额会重复计算

- 证据：任务账户约束只阻止同 task 重叠；任务查询通过 EXISTS 匹配，多个任务都可能获得该账户整笔指标；考核价查询 `LIMIT 1` 可能任取一条。
- 触发：优化师把同一账户在重叠日期维护到两个任务。
- 后果：任务消耗重复、考核价随机、汇总金额大于账户真实金额。
- 修复：产品拍板“一账户日唯一任务”或显式分摊模型；未拍板前写入端应拒绝重叠。

### P0-06：Job Lease 没有 fencing token，过期 Worker 可覆盖新 Worker

- 证据：`packages/db/src/job-repository.ts:152-246` 租约、续租、完成、失败只匹配 job id/status；`apps/worker/src/jobs/consumer.ts:50-75,94-120` 心跳也只传 id。
- 触发：Worker A 租约过期，B 重新领取后，A 从阻塞中恢复。
- 后果：同一任务并行执行；旧 Worker 可以续上新租约并标记完成/失败，媒体写操作可能重复。
- 修复：每次领取生成 lease token/代次，所有状态迁移 CAS token；外部副作用继承同一 fencing/idempotency 标识。

### P0-07：Workflow Run 没有单执行者租约，确认后的写节点可并发执行两次

- 证据：Runner 读取事件后在事务外调用 capability；事件去重只能去重日志，不能锁住真实副作用；同一 run 可被两个推进请求并发处理。
- 触发：同一 runId 被两个 Worker/请求同时 advance，或恢复任务与旧执行重叠。
- 后果：重复改价、重复创建、重复关户等真实操作。
- 修复：Run 级 executor fencing + `runId/nodeId/attempt/phase` 唯一 effect/outbox 记录；补真实并发测试。

### P0-08：确认时间使用字符串比较，且执行前不再次检查 TTL

- 证据：`packages/domain/src/workflow-runtime.ts:381,404` 和 `apps/worker/src/workflows/run-handler.ts:229-231` 直接比较带 offset 的 ISO 字符串；`executeConfirmed:428-457` 未重新校验过期时间。
- 触发：不同 timezone offset 的等价时间，或确认后排队到 TTL 过期才执行。
- 后果：过期确认仍可能执行写操作。
- 修复：统一解析 epoch/UTC；确认和开始媒体执行前都强制重验 TTL。Changeset `beginExecution` 同样重验。

### P0-09：媒体已成功后 T+1 调度失败，会丢失效果回收并破坏状态

- 证据：`changeset-execution-handler.ts:67-90` 把媒体执行、完成落库和后续 finish 放在同一 catch；`:106-124` 在完成事务后单独 schedule T+1。
- 触发：媒体成功且 complete 已提交，但 T+1 enqueue 抛错/进程崩溃。
- 后果：catch 试图二次 complete 已终态变更集并失败；重试又跳过终态，T+1 永久丢失。
- 修复：变更集完成与 T+1 outbox 同事务写入；区分远端不确定、数据库不确定、后续派发失败。

### P0-10：知识业务引用无权时只删引用，仍把引用对应正文送给 Agent

- 证据：`packages/domain/src/knowledge-access.ts:197-222` 对无权 businessRefs 仅 filter，保留 citation.fragmentText。
- 触发：文档本身可读，但片段包含用户无权账户/任务/报告内容。
- 后果：无权业务文本进入模型上下文，违反 B8 “无权文本不得进 Agent”目标。
- 修复：检索 chunk 必须带可裁剪的对象级 provenance；不能证明片段完全授权时丢弃整段，而不是只删 citation ref。

### P0-11：ETL 可把奇航返回的跨 workspace 账户重新标成当前 workspace

- 证据：payload 校验 workspace，但请求 accountIds 未与本地账户归属逐一核对；`rowsToRawRecords` 使用调用方 workspaceId 给所有返回行打标签。
- 触发：同一奇航身份可见多个业务范围，传入/返回了当前 workspace 外账户。
- 后果：跨租户数据污染，后续报表、规则和 Agent 都可能越权看到。
- 修复：请求前校验账户 allowlist；响应再次校验 accountId、media、workspace 映射，异常整批隔离并审计。

### P0-12：钉钉先 ACK 后处理，失败事件无法重新领取

- 证据：`dingtalk-adapter.ts:101-107` 在异步 onMessage 前回 SUCCESS；`message-handler.ts:27-45` claim 后才处理；claim 冲突直接返回，没有 `processed=false` 超时重领。
- 触发：ACK 后、持久化前崩溃；或 claim 后身份查询/业务调用/回复失败。
- 后果：钉钉不再投递，重投也被去重，消息永久丢失。
- 修复：先写 durable inbox 再 ACK；inbox 增加 lease/attempt/error；回复走 outbox 重试。

### P0-13：Changeset Repository 没有形成独立安全边界

- 证据：`packages/db/src/changeset-repository.ts:196-219` 直接信任 initiator、credential owner、work item、target；数据库没有覆盖这些同 workspace/有效状态约束。
- 触发：上层 API/Agent/工作流传入伪造或跨租户 ID。
- 后果：变更集可绑定错误凭证主体或媒体目标，审计链失真。
- 修复：创建和执行前都由仓储/服务端验证 active user、credential owner、work item、账户和目标归属；关键关系加租户外键或约束。

### P0-14：Workflow 输出凭证检测可被普通前缀绕过

- 证据：`apps/worker/src/workflows/run-handler.ts:897-914` 仅对字符串开头匹配 Bearer/sk/ak/api_key。
- 触发：下游返回 `upstream error: Bearer ...`、`token=...` 等嵌入式文本。
- 后果：凭证或密钥可能进入 workflow event/output/审计日志。
- 修复：使用结构化 secret redaction、常见授权头/键值全串检测、敏感字段 denylist；输出在持久化和日志两个边界分别清洗。

| ID | 问题 | 影响/建议 |
|---|---|---|
| P1-01 | 回填用 UTC 日期判断今天 | 亚洲/上海 00:00-08:00 会选错 realtime/offline；注入业务时钟和时区 |

## 5. 已知未接线，不按 bug 统计

以下能力是代码或领域底座已存在、但产品链路尚未完成。对外汇报时只能说“底座完成/待接线”，不能说“用户可用”。

1. 当前生产 Runtime 只注册 ETL、回填、canonical、quality；规则、变更集、T+1、Agent、报表、工作流、知识库尚未统一注册。
2. 钉钉复杂消息会 enqueue `agent_task`，但当前 Runtime 无该 handler。
3. outbound_messages 有存储底座，但没有真实消息发送 consumer。
4. B2-B8 缺统一 Web API、鉴权中间件和前端调用接缝。
5. Workflow 尚未连接真实 B3 Changeset/OS/Multica 能力；知识库尚未建表、迁移、搜索引擎和自动归档。
6. Agent 沙箱目前主要靠工具禁用、路径和网关边界，生产级进程/容器隔离、每 Run 目录权限仍待落地。

## 6. 已验证的正向控制

- SQL 动态部分有白名单，未发现用户输入直接拼接 SQL。

- Gateway 默认 loopback，凭证信封采用 AES-GCM 并绑定 workspace/user/run/provider/model；上游 authorization 不直接沿用调用方 header。
- 媒体写结果不确定时进入 UNKNOWN，不盲目自动重试。

- 钉钉 sessionWebhook 有域名白名单，未发现直接 SSRF。
- `npm audit --omit=dev --audit-level=moderate`：worker、dingtalk-gateway、db、domain 均为 0 vulnerabilities。

## 8. 建议修复顺序

### R0：先让“读链路”说真话

1. 补 raw -> account sync -> canonical -> quality 完整 DAG。
2. 修正回填完成条件、缺失状态、业务时区、今日 provisional。
3. 冻结账户日任务归属/分摊规则。
4. ETL 请求与响应两侧做 workspace/account allowlist。

### R1：再让“写链路”最多执行一次

1. Job lease 和 Workflow Run 全部加入 fencing token。
2. Changeset 创建/执行补同租户、主体、目标和 TTL 强校验。
3. 变更结果、T+1 和通知使用事务 outbox。
4. 确认时间统一 UTC epoch，执行前二次检查。

### R2：补消息和运行时闭环

1. 钉钉 durable inbox -> ACK -> command -> outbox。
2. 注册明确允许的 job handler，并为未支持类型拒绝入队。
3. 增加分区保活、规则扫描系统故障、Qihang 资源预算和吞吐告警。

### R3：收紧 Agent 与知识权限

1. 无法证明对象级授权的知识片段整段丢弃。
2. Agent 调整建议必须有证据、真实 currentValue 和服务端 guard；`insufficient_data` 禁止生成执行建议。
3. session run 绑定/串行化、事件体积上限、凭证清洗和每 Run 隔离。

### R4：契约冻结后接 B2-B8

按 Claude/arch 审定的公开 DTO、权限矩阵、错误码和状态机接 API、前端、OS/Multica，不在自审修复中自行发明公开契约。
