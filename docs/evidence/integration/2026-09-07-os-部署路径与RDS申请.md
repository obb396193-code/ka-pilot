# OS 回收：内网部署路径 / AONE 应用 / RDS 申请 / 发布审批（2026-09-07）+ arch 裁决

> 这批是**日常工作要反复查的平台知识**，不只是一次性问答。证据等级按 OS 标注。

## 一、核心纠正：RDS 申请入口不是 Normandy，是 CloudCenter

| 项 | 内容 | 等级 |
|---|---|---|
| 入口 | CloudCenter 资源中心 `https://cc.alibaba-inc.com/resource` → 创建资源 → RDS PostgreSQL | 平台文档 |
| 文档 | kbase repo 890「开始使用/资源使用/RDS 使用文档」；开放接口 `/apis/core/v1alpha1/namespace/%s/cloud/resource/create` | 平台文档 |
| 必填 | owner（归属 **AONE 应用**）、cloudAccountUid（云账号）、region、规格、存储、引擎版本、网络（VPC/多可用区） | 平台文档 |
| 审批链 | 资源必须归属一个 AONE 应用；操作人须是云账号负责人/管理员/BU 资源管理员或有子账号；审批走应用 Owner/PE + 云账号管理员 | 平台文档 |
| 时长 | **未证**（文档无明确审批时长） | 未证 |
| 硬约束 | 集团容灾治理：CC 建 RDS **仅允许多可用区**，没有单可用区廉价测试档 | 平台文档 |
| 免审批快路 | **没有**。资源认领需先有无主 RDS；无面向业务的共享 PG 池 | 平台文档 / 未证 |

**"工单过不了"的真相**：OS 从未提交过被拒的工单。是 `normandy` CLI 根本没有 RDS create 命令（只有 get/list/login），且 OS 名下无云账号、无 AONE 应用，不满足 CC 创建前提。

**老板要找的三个人**：① BU 云账号负责人/资源管理员（拿 cloudAccountUid + 子账号权限）；② 一个 AONE 应用的 Owner（资源必须归属应用）；③ FaaS 平台 PE（问 FaaS 出口网段/VPC，决定 RDS 网络怎么填）。

## 二、两条 FaaS 部署路（**这条改了我们的部署架构**）

| | 轻量 FaaS（OS 之前用的） | **aone-platform FaaS（正式路）** |
|---|---|---|
| 建应用时 | 不建 AONE 应用，只是 FaaS 壳 | **自动建 AONE 应用 + 代码仓库 + 平台绑定** |
| 应用名 | 自动生成 `a1-client-faas-xxx` | **自己指定**，如 `ka-pilot` |
| 域名 | `a1-client-faas-xxx.fn.taobao.net` | daily `ka-pilot.fn.taobao.net` / 正式 `ka-pilot.fn.alibaba-inc.com` |
| 环境 | 只有 daily | daily / pre / prod |
| 挂 RDS/OSS | ❌ 不行（无 AONE 应用） | ✅ 行 |
| 缺陷 | 无 SLA 可能被回收、域名丑、a1 CLI 有查询 bug | 要建 git 仓库、发布走流水线、纳入集团治理（成本归属/安全扫描） |

**关键**：走 aone-platform **一步拿到 AONE 应用**，不用单独申请应用；这同时解开了「RDS 必须归属 AONE 应用」这个死结。

自定义品牌域名（如 `kapilot.alibaba-inc.com`）走统一接入 `fs.alibaba-inc.com/#/ingressManage`，需域名报备流程，内测用不上。

## 三、发布 SOP 与审批门在哪

| 动作 | 要不要审核 |
|---|---|
| 建 aone-platform 应用 | **不要**外部审批（只有机器预检 + 与 OS 确认 4 项：应用名/仓库组/仓库项目名/模板） |
| 发 **daily** | **基本不要**（构建 + 健康检查即上线） |
| 发 **pre** | 要过门禁：CR 变更单 + 流水线，可能代码评审 |
| 发 **prod** | 门禁最严：CR + 代码评审 + 安全扫描 + 质量卡点 + 可能人工审批 + 发布窗口 |

名词：**CR** = 变更请求单；**流水线** = 发布时自动跑的检查+部署串；**门禁/GATED** = 卡在某道检查等人处理；**daily/pre/prod** = 测试/预发/正式。
**"提交成功" ≠ "发布完成"**：publish 返回成功只表示进了流水线，要等状态变 `success`。

**对我们的影响**：内测全程无外部审批，OS 就能做完；**只有正式化（pre/prod）需要老板提前找一个技术同学/PE 当代码评审与发布审批的对接人**。

## 四、网络：RDS 能不能被 FaaS 连上（仍是命门）

| 网络项 | 该填什么 | 风险 |
|---|---|---|
| VPC | 与 FaaS 同 VPC | ⚠️ FaaS 在哪个 VPC 未查到，需问 FaaS PE |
| 安全组 | 放通 5432 入站，源 = FaaS 出口网段 | ⚠️ FaaS 出口 IP 未测到，是否固定未知 |
| 白名单 | 加 FaaS 出口 IP | ⚠️ **出口 IP 不固定则此方案不成立** |
| 先例 | 无 FaaS→RDS:5432 先例文档 | 未证 |

结论不变：**RDS 到手后由 OS 第一时间实测 FaaS→RDS:5432 + 出口 IP 是否固定**。不通则走 VPC 内网直连或安全组网段放通。

## 六、OS 报的两个执行现实

- **沙箱内无 cron 守护进程**（实测无 crond），也无 CloudCLI cron token → 沙箱里没有轻量定时器。
- **Multica autopilot 的 schedule trigger 触发的是 agent 不是 HTTP**：所谓「cron POST」实际是「定时拉起 agent → agent 执行 curl」，每 10 分钟拉一次 agent 偏重。
- 备份脚本已就绪并跑通（`pg_dump -Fc` → gzip → 保留 14 天，实测产出 dump.gz）；起 PG 脚本就绪。**OSS 上传卡在没有云账号**（bucket + AK 都要云账号）。

## 七、arch 裁决

| # | 事项 | 裁决 | 理由 |
|---|---|---|---|
| 1 | **建 `ka-pilot` aone-platform 应用** | **现在就建**（老板点头即可，无外部审批） | 零成本拿到 AONE 应用 + 带产品名的域名 + 未来挂 RDS/OSS 的前提；不阻塞内测 |
| 2 | 内测数据库 | **不变，方案 A：沙箱 PG** | FaaS 仍连不上 5432；RDS 走完申请链要时间 |
| 3 | worker 形态 | **HTTP 触发口保留（已实现且有单飞锁），沙箱期用部署脚本挂一个 `while true; curl … ; sleep 600` 循环去打它** | 不浪费已交付代码；不依赖 autopilot 拉 agent；正式化切 FaaS 时只换触发源，代码零改动 |
| 4 | 备份调度 | **同上，部署脚本挂后台循环跑 `pg_backup.sh`**，不用 autopilot | 沙箱无 cron，统一风格 |
| 5 | 备份异地 | **内测先只落沙箱本地**，OSS 等云账号到手补 | 沙箱被回收会连本地备份一起丢，风险真实但内测期人产数据少；指标数据可从启航/ka-data 重拉。列为门禁 A12，不装作已解决 |
| 6 | RDS 申请路径 | **走 aone-platform 建应用（拿到 AONE 应用）→ 找 BU 云账号管理员拿 cloudAccountUid → CC 提交** | 比"先找现成团队应用"更干净，且建应用本身零审批 |
| 7 | 正式化对接人 | **老板需提前物色一个技术同学/PE**，负责 pre/prod 的代码评审与发布审批 | 这是唯一必须提前协调的人 |
