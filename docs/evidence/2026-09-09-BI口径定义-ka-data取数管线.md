# BI 口径定义：ka-data 取数管线（老板 2026-09-09 转来，arch 对照系统存档）

> 这份是 ka-data（团队源）自己的取数管线定义，**不是我们系统里的代码**。我们系统两个空间的 BI 数都间接来自它（见 §2）。以后 BI 数对不上，先查这里，再查 ka-data，最后才查我们。

## 1. 原文（逐字，老板转）

媒体数据唯一源：代理后台 queryDataReport（dim=DAY/HOUR），容器直连；只存花费>0；北京时间统一。
落表：agent_daily（账户×天：花费/激励花费/转化/唤醒/转化成本/转化率 + 清洗维度）、agent_hourly（账户×小时）。
后链路 BI：bi_conv_daily（核心三字段：日期 ds / 广告位ID=账户ID / BI数 conv）。四个任务大类 BI 全部接入，各按 bi_defs.json 定义拉取：

- 闪购：surge_dt.ads_ug_jl_wake_attr_deal_sg_stat_1d_all；linktype='ALL' AND g_ab='1'；高客单任务 1051807369 取 sg_newmac_price_getx，其余取 sg_newmac_uv；按账户奇偶双分片防 1 万行截断。
- 促活UV：surge_dt.ads_ug_jl_wake_swdau_stat_afcid_attri_1d_ltv；按 task_name + crowd_name CASE 取字段：促购增量-UV/UV_HS专项→attri_ipvuv@中高购人群_购买目标_IPV策略；促购增量-DAC→attri_swdac@中高购人群_购买目标_总目标人群；其他促活UV任务→attri_ipvuv@实物流量总目标人群_流失非流失AT。
- 闲鱼：fleamarket_data_analysis.ads_idle_3rdgrowth_tb_ad_task_1d；通投/促活任务→fst_callapp_uv（首唤UV），拉新任务→u1_uv；账户列=ad_id（对闲鱼DAU账户即快手account_id）；排除 material_id='ALL' 汇总行。
- CVR：两表——预流失子任务→surge_dt.ads_aac_yls_stat_detail_1d（trade=实物）；其他CVR子任务（CVR有端/CVR排除/CVR无端/DAU-CVR有端IOS）→surge_dt.rpt_surge_acc_index_stat_summary_data_1d（trade=新实物）。BI=SUM(field) WHERE link_type IN ('install','uninstall') AND task_id<>'ALL' AND os_type<>'ALL'；field 按 dim_subtask 选：含「无端」→wd1h（归因卸载，yls_wd_1h_target_attrib_uv / newaac_uv_attrib_wd_1h），其余→attrib（归因安装，yls_target_attrib_uv / newaac_uv_attrib）。定制 _sync_cvr_def：按账户 dim_subtask 选 field、IN 子句只拉工作台 CVR 账户（避开底表海量 ad_id 截断）。RTB 仅拉媒体数据，不接 BI。

防跨任务污染：query_bi_summary 与 build_snapshot 均按 bi_conv.biz = 账户 dim_task 过滤（如闪购 def 给促活账户产生的杂讯 conv 不混入促活口径）。
数据起点 2026-08-31（媒体表有效起点），每日 T-1 自动增量（08:30 媒体、11:10 BI）。

## 2. 我们系统的 BI 数从哪来（对照代码，2026-09-09 核）

| 空间 | 上游 | 我们读的列 | 代码位置 |
|---|---|---|---|
| **团队空间** | ka-data `dwd_account_daily`（按 `media` + `account_id IN(授权户)` + 可选 `task_id` 过滤，`SUM(conv)`） | `conv` → `realConversion` | `apps/worker/src/data/ka-data-client.ts:246-271`、`canonical-query-rows.ts:45,104` |
| **个人空间** | 启航 `account_realtime` / `account_offline` 的「真实转化」列（=FBI BI 数，老板 9-5 已核同源） | `real_conversion` → `realConversion` | `packages/contract/metrics.md:32`、`apps/worker/src/etl/incr-handler.ts:165` |

- ka-data 的 `dwd_account_daily.conv` / `fact_conv_daily.conv` 就是原文里的 `bi_conv_daily.conv`——所以**团队空间的 BI 数 = 上面四张 ODPS 表按 bi_defs 拉出来的数**，我们没有再算一遍，也不该再算。
- 个人空间走启航，启航的「真实转化」与 ka-data 离线口径已对平（OS 9-5：消耗差 0.07%、曝光 0.03%、**点击/转化相等**）。两个空间的 BI 数同源。
- 我们不做 bi_defs 里的字段选择（闪购高客单 / 促活人群 / 闲鱼首唤 vs 拉新 / CVR 无端→wd1h）；那是 ka-data 管线的事。**我们只需保证按 media + 账户 + task_id 过滤**，这与原文「防跨任务污染：按 biz = 账户 dim_task 过滤」是同一条铁律（契约 v1.4.1 §团队 SQL 六铁律第一条）。

## 3. 与旧资料的差异（以本文为准）
- 闲鱼：旧手册（docs/handoff/数据抓取指南 §BI 血缘、ka-src 资料）写「通用 u3_uv」，本文是 **通投/促活 → fst_callapp_uv（首唤UV）、拉新 → u1_uv**。
- 促活UV：本文按 task_name + crowd_name 三分支 CASE，旧资料只写「一般 attri_ipvuv / DAC → attri_swdac」。
- CVR：本文明确 **按 dim_subtask 含「无端」选 wd1h（归因卸载）**，其余 attrib；并且只拉工作台 CVR 账户（IN 子句）防截断。
- 新增：闪购按账户奇偶双分片防 1 万行截断；RTB 不接 BI（只有媒体数）。

## 4. 对我们的两条影响（已进契约/待办）
1. **团队空间数据起点 = 2026-08-31**（媒体表有效起点），更早的日期是 missing 不是 0；日报/趋势往前翻到 8-31 之前显缺数。
2. **T-1 到达时间**：媒体 08:30、BI 11:10。上午 08:30–11:10 之间，昨天的 conv 还没到 → `realConversion` missing、cashCpa/gap undefined（不是 0）；`dataAsOf` 要能区分「媒体已到、BI 未到」。这与 v1.7.7 的 D-3 provisional/updated_at 批次一致，需要团队路径把 `conv` 为 NULL 的行按 missing 处理而不是过滤掉——派 Codex 核一条（F-BI-001）。
