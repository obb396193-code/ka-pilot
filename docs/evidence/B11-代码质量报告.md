## 4. 正确性与可靠性

- 每个小时快照先按稳定输入顺序分片：12 个账户固定生成 5/5/2；广告 ID 按 80/批；账户与广告同时存在时生成确定性交叉批次。
- 默认最多生成 200 批，超过即在访问上游前失败，避免用户范围异常放大请求量。
- 每批分别保存 Raw 和 observation；全部分片成功后才按 `account_id+ad_id+ds` 合并。相同重复去重，冲突重复或缺失身份字段 fail-closed。
- 合并快照保留所有分片中最大的 `last_sync_time`，避免页面把较新的数据错误标成更旧。
- `hh=N` 只作为 0..N 累计快照；独立窗口由 `N-(N-1)` 计算，`hh=0` 使用零基线。
- Qihang 原子 Client 接受实测有效的 0..24；ETL payload、Domain 与小时表继续限定 0..23，`hh=24` 不会成为伪造的第 25 个小时。
- 当前快照缺少上一时点已有广告时不写该行，只生成 aggregate issue；不会产生负消耗假值。
- 回修导致五项累计指标下降时截 0，并记录字段名；bid/budget 取当前快照。
- Qihang 返回错误日期、重复 ad_id、账户漂移、null/字符串/非有限指标均在小时 Upsert 前失败。
- 两份 Raw 均成功后才派生小时指标；小时 Upsert 失败时 ETL Run 失败且不派发 Canonical。重试依靠 Raw append-only + 小时复合键 Upsert 收敛。
- offline 非空只标 `observed_unverified`；没有平台 complete marker 时不产生 complete 状态。
- Worker PG 测试关闭文件级并行，避免两个测试进程同时执行 migration 产生非业务型争锁；生产执行逻辑未因此串行化。

## 5. 安全、租户与性能

- observation 指纹对行/键顺序稳定，只保存 resource/date/hh/rowCount/hash/lastSyncTime/状态；DB 再做字段白名单。
- 派生 issue 只保存计数和固定字段名，不保存 ad/account/user 标识。
- 小时 Upsert 冲突键包含 workspace；同键 account 漂移时 `WHERE` 阻止覆盖并以 rowCount mismatch 失败。
- SQL 使用单个参数化 JSON recordset，无动态标识符或字符串值拼接；0 行不访问 DB。
- 广告查询必须带 accountIds/adIds；默认 5 账户来自第三轮真实分片验证，80 adIds 延续 skill 已有边界；单批恰好命中 2000 即停止，避免用不完整数据做异常归因。
- 分片当前顺序执行，优先保证启航频控与故障定位；尚无真实链路 SLA 数据，不提前引入并发放大。
- 变更生产代码 complexity≤10、单函数≤100 行；未发现 eval、动态 Shell、新凭证或敏感业务样本。

## 6. 自审发现并修复

1. 分片合并最初没有恢复各批次最大 `last_sync_time`，会让产品展示错误的数据新鲜度；已补实现和回归测试。
2. 账户/广告 ID 交叉分片最初没有全局批次数门禁，极端输入可能生成数千次请求；已增加默认 200 批 fail-closed 上限。
3. Worker 两份真实 PG 测试并行执行 migration 时偶发争锁；已在 Worker 测试配置关闭文件并行，并用全量 PG 回归复验。
