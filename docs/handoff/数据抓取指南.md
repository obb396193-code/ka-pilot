# 数据抓取指南

> 来源：KA Pilot（快手渠道投放经营平台）。2026-09-08 出稿。
> 用途：做腾讯渠道的自动化取数和 BI 看板。这份文档把快手渠道已经踩通的数据通路、字段口径、坑和管道设计全部写下来，不用重新调研。
> 配套文档：同目录的 `前端规范与组件复用.md`（前端怎么做成同一水准）。
> **可信度声明**：标「已实证」的部分来自对快手渠道的真实请求。标「待实证」的部分没跑过腾讯，必须先探针确认。别把快手结论当腾讯的既成事实。

---

## 1. 最重要的一件事：数据不在腾讯，在奇航

最初以为要对接快手官方 MAPI，实读代码后发现根本不是。所有连接器指向同一个奇航平台的 HTTP GET 接口：

```
GET https://qh.alibaba-inc.com/qihang/api/rta_auto/tmp/get_data
  ?resource=account|account_offline|account_realtime|ad_realtime
  &userId=<从环境变量读>
  &media=KUAISHOU
  &...
```

关键点：**`media` 是个查询参数**。同一个接口、同一套连接器，把 `media` 换成腾讯对应的值就是腾讯的数据。不需要另找一套接口。

这条请求链里没有 DataWorks、没有 FBI、没有 Multica。就是奇航的一个 GET。

---

## 2. 为什么有的号能拉腾讯、有的拉不到

这是关键，也是能独立开工的原因。

鉴权**没有 token、没有签名、没有 API Key**。代码原文在 `ks_common.py`：

```python
ENV_JULANG_OS_USER_IDENTITY = "JULANG_OS_USER_IDENTITY"
ENV_MOZI_USER_ID = "MOZI_USER_ID"
# 无 API Key / Token / 签名机制，纯粹把身份字符串当 query 参数传给服务端
```

就是把身份字符串当查询参数裸传，服务端**按 userId 校验数据范围**。

所以：
- 快手渠道那边的 userId 授权范围里没有腾讯户，所以拉不到腾讯。
- 有腾讯户授权的 userId 就能拉到。
- 换 userId 就是换可见数据范围。工程上 `resolve_user_identity()` 还支持隐藏命令行参数 `--user-identity` 或 `-u`。

**所以用自己的身份跑同一套 skill 就行**，不需要找别人要凭证，也不需要额外授权。

顺带一条红线：任何 token、密码、身份串**不要通过聊天或中转回传**。这边作废过一枚内部 token 就是因为回传过。在环境变量里设好，回一句「已设置」即可。

## 3. 另一条路：KA Data 里已经有腾讯数据（实证）

上面讲的是奇航。还有**第二个数据源** KA Data，和奇航是两套东西，而且**腾讯数据已经在里面了**。

**实证结论**（内网 OS agent 真实执行，2026-09-05）：一枚 reader token 看到的是全团队账户。

| 渠道 | 账户数 |
|---|---|
| 快手 | 704 |
| 头条 | 4398 |
| **腾讯** | **2670** |
| 百度 | 250 |

旁证：团队空间 SQL 铁律第一条是「转化查询必带 `media=` 过滤，`fact_conv` 存全媒体，不加差 12 倍」。表里本来就装着多渠道数据。

同时 KA Data 与奇航离线口径**对平低于千分之一**（消耗差 0.07%、曝光 0.03%、点击和转化相等），可认为同源一致。

### 三个硬限制，决定它不能当唯一源

**只有离线口径，没有当日实时。**
权威划分是：跨渠道大盘、历史趋势、商品素材 BI 归 KA Data；**当日实时消耗转化、小时 pacing、异常诊断、执行前检查归奇航**。所以盯盘和当日监控**必须走奇航**，KA Data 只能做 T+1 结算和历史分析。

**服务地址是沙箱会话地址，重启就变。**
只能当内测源，正式用需要稳定域名。token 的有效期和审计说明也还没有。KA Pilot 里 `KA_DATA_ENABLED` **默认是 false**，目前没接通。

**没有「个人」这一层，也没有按人拆的维度。**
- KA Pilot 里数据源**由服务端按空间类型固定**：个人空间走奇航（本人授权账户），团队空间走 KA Data（全渠道只读）。浏览器不能选源，个人空间**没有任何通往 KA Data 的路径**。唯一例外是治理后台的对账诊断，要显式开开关加命中白名单，而且不是业务视图。
- 一枚 reader **看的就是全团队**，没有按人的权限粒度。
- 八个分析维度里**没有「负责人」这一维**，枚举是 `task|biz|account|agent_type|resource_position|bid_tool|is_ubp|deduction_range`。人员字段 `operator_name` 只在广告组级的 `dwd_adgroup_daily` 里有，账户级没有。

所以「KA Data 里某个人的腾讯数据」这个切法**现在做不出来**。能拿到的是账户级全量，要按人归属得自己另外维护账户和人的对应关系。

注意最后这条的前半段是 KA Pilot 的设计规则，不是 KA Data 本身的限制。自己做产品可以自己定绑定方式。

### 接入形态和查询陷阱

```
POST <origin>/api/query
Authorization: Bearer <reader token>
body: {backend, sql, limit}
响应: {rowCount, rows, truncated, limit_clamped, note}
```

`backend` 产品路径固定用 `sqlite`，毫秒级、口径已对齐。holo 和 odps 不进产品。

可查表：`dwd_account_daily` 是账户日，`dwd_adgroup_daily` 是广告组日（八维字段在这），`fact_conv_daily` 是转化。

**六条查询铁律，踩了就是错数：**
1. 转化和账户查询**必带 `media=` 过滤**。`fact_conv` 存全媒体，不加差 12 倍。
2. 现金直接 `SUM(cash_yuan)`，**不要再乘除渠道系数**。源已经算好了，再施加就是双算。
3. `cash_yuan` 可能是 null，走三态 missing，**不要 COALESCE 成 0**。
4. `dwd_adgroup_daily` 和 `dwd_account_daily` 与 `fact_conv_daily` 的 `account_id` 是**两套 namespace，禁止 JOIN**。广告组级和账户级分别查。
5. 赔付 JOIN 必带 media。
6. `truncated` 或 `limit_clamped` 为真就按 partial 处理，按日期或账户分批重查。

考核价 `dwd_account_daily.cash_assessment` 已按业务线乘媒体富化，团队口径达标直接用这列，不用自己算。

### 实际建议

两条源**不是二选一，是分工**：
- **历史、结算、跨渠道大盘** 优先看能不能拿 KA Data 的 reader，腾讯数据已经在里面，省掉自建管道。
- **当日实时、盯盘、诊断** 必须走奇航，KA Data 给不了。

想走 KA Data 的话，reader token 由内网服务 owner 签发，命令是 `issue_token.py <名> reader`，有 `--list` 和 `--revoke`。需要通过 KA Pilot 这边或直接找服务 owner 申请。

## 4. 四种取数方式对比

可选的路子有四条，各有各的适用场景。**建议全部试一遍再定，不要一开始就锁死一条。**

| 方式 | 拿什么 | 准不准 | 稳不稳 | 适合 |
|---|---|---|---|---|
| A 浏览器快照（cookie 模拟登录态） | 媒体侧页面能看到的一切 | 和人眼看到的一致，最准 | 差，登录态会过期、页面改版就崩 | 探路、补别的方式拿不到的字段、小站 BI 取表 |
| B 奇航授权拉取（query 技能） | 授权下全部账户的结构化数据 | 账面口径准，**BI 类字段可能有偏差** | 好，接口稳定、已实证 | 主力管道 |
| C KA Data reader | 跨渠道全团队离线数据 | 与奇航对平低于千分之一 | 中，沙箱地址会变 | 历史、结算、跨渠道大盘 |
| D 媒体官方接口 | 账户结构、计划单元创意 | 权威 | 需授权，这边没走通 | 结构类数据、写操作 |

### 方式 A：浏览器快照加 cookie 模拟登录态

思路是给 agent 一个已登录的浏览器上下文，cookie 或者沙箱里的登录态，让它直接读页面。

两个用法：
1. **媒体侧数据**：把登录态给 agent，让它打开媒体后台页面抓数。
2. **小站 BI 数据**：把**每个表的链接**给 agent，并且**明确告诉它每个链接是什么数据**，包括哪个业务、哪个粒度、哪些字段、口径是什么。同样走沙箱登录态。

**这条路的价值**：它是唯一能拿到「人眼在页面上看到的那个数」的方式。当接口口径和页面口径对不上、或者某个字段接口根本不返回时，这是唯一出路。也适合快速探路，先确认某个数据到底存不存在，再决定要不要为它建管道。

**代价必须提前想清楚：**
- 登录态会过期。要设计过期了怎么办：重新注入，还是报警等人处理。**不要静默重试到超时**。
- 页面改版就崩，而且**往往是静默崩**。选择器没匹配到就拿到空值，被当成「这天没数据」。所以抓取结果必须有**合理性校验**：行数突变、关键字段全空、总和为 0，一律标成失败不入库。
- 页面上的数字通常已经被前端格式化过，千分位、万、百分号、保留两位。**解析回数值时容易丢精度或出错**，比如「1.2万」还原成 12000 就丢了精度。要么找页面的导出功能拿原始值，要么明确记录「这个数是从展示值反解的」。
- **不适合当长期主力管道**。定位成探路工具、补字段、小站 BI 取表。主力还是走方式 B。

给 agent 的提示词要点：明确告诉它每个链接对应什么数据，要求它抓完先做合理性校验再落库，解析失败必须显式报错而不是填空值，不要让它自己猜字段含义。

### 方式 B：奇航授权拉取（推荐当主力）

就是第 1 节和第 2 节讲的那条。补充一个**关键好处**：

**一次授权能拿到授权下的全部账户**，不用一个个配。有一条现成的只读发现命令：

```bash
npm run discover:accounts -- --media KUAISHOU
```

它用奇航 userId 调 `resource=account`，把 `{media, account_id, account_name, task_id, biz_name}` 打成 JSON 到标准输出，**不写库、不发任何任务**。实现在主仓 `apps/worker/src/qihang/discover-accounts.ts`，可以直接照抄。里面几个值得学的防御写法：

- 分页每页 50，逐页校验总数前后一致、页号和页大小回显匹配、每页行数等于预期，**任何一项不符直接失败**，不接受「少拉了几页」当成功。
- 遇到 `truncated`、`limit_clamped`、`hasMore` 任何非 false 的分页标记就直接失败。**不把未知的分页标记当完整。**
- 账户 id 去重，重复即失败。
- 出错时不暴露 URL、userId、上游正文，也不返回部分结果。

**一个重要提醒**：走奇航的 **BI 类字段可能不太准**。这边的实证是 `account_real_conversion` 经业务核认与 BI 同源，但源码只能证明字段由奇航返回，**不能证明上游业务血缘**。所以 BI 相关的数进正式结算前，必须逐字段逐日和 BI 后台对平。对不上的字段，考虑用方式 A 从页面取，或用方式 C 从 KA Data 取。

奇航客户端的四种查询形态，见主仓 `apps/worker/src/qihang/client.ts`：

```
resource=account          → pageNum / pageSize / keyword / bizName
resource=account_offline  → beginDate / endDate
resource=account_realtime → ds
resource=ad_realtime      → ds / hh / adIds（必须带 accountIds 或 adIds）
```

## 5. 怎么分类任务、清洗账户

这是做看板最容易被低估的一块。数据拉回来了，但「这个账户属于哪个任务、什么版位、什么出价方式」往往没有现成字段。

### 任务归属：先看有没有现成的 task_id

**奇航拉回的账户可能自带 `task_id` 和 `biz_name`。** 上面那条发现命令返回的就有这两个字段。如果自带且可信，这是最省事的路，直接用，不要自己造映射。

KA Pilot 的落法可以照抄：任务和账户**不是一对一写在账户表上，而是单独一张关系表**，因为账户会换任务。

```sql
task_accounts(workspace_id, task_id, media, account_id, valid_from, valid_to)
```

关键设计：**一个账户同一个业务日只能归属一个任务**，区间重叠直接拒绝写入。用 PostgreSQL 的 `EXCLUDE USING gist` 排他约束在数据库层挡住，冲突返回 409。不做按比例分摊。

这条踩过坑：KA Data 那边每天给的 `task_id` **只代表那一天**，不代表整段生命周期。**中间缺的那几天不能自动补成「持续归属」**，否则归因会错。

### 账户清洗：如果账号命名有规范，让 agent 设计解析规则

这个思路比手工维护映射表省力得多。做法是**把命名规范写清楚告诉 agent，让它设计清洗和映射规则，然后抽样验证**。

比如命名是「渠道-业务线-产品-序号」这种结构，就明确告诉它分隔符是什么、每一段是什么含义、有哪些合法取值、有没有历史遗留的老格式。

**必须让 agent 遵守的几条**，都是踩出来的：
- **解析不出来的必须标成未知，不能猜，也不能归到某个默认值。** 一个归错的账户会污染整个任务的成本口径。
- **保留原始账户名**，别只存解析结果。规则改了要能重跑。
- **给出解析覆盖率**：多少个账户解析成功、多少未知、未知的样本长什么样。覆盖率低于预期就是规则不对，不是数据脏。
- **规则要版本化**。改了规则，历史数据要不要重跑、重跑哪些日期，得说清楚。

KA Pilot 这边**没有现成的账户名解析代码**，因为账户归属靠奇航自带 task_id 加人工确认授权。所以这块是从零做，但也没有历史包袱。

**有一个现成的清洗先例可以参考**：代投还是自投这个维度，是从 KA Data 账户的 `custom_tags["代投/自投"]` 取的，取不到就是 `NULL`，**绝不填默认值**。标签稀疏、很多「无匹配」，就让它是空，不编。

账户元数据落库代码在主仓 `apps/worker/src/etl/account-metadata.ts`，值得学的是它的**严格态度**：字段类型不对直接抛错，同一账户多行元数据冲突直接抛错（不取第一条也不取最后一条），账户 id 逃出可信元组直接抛错。宁可失败也不要脏数据入库。

### 版位和出价方式：这块最容易做错

**版位（资源位）**相对简单，KA Data 的 `dwd_adgroup_daily.resource_position` 直接有，枚举形如 `INVENTORY_UNIVERSAL`、`KUAI_SHOU_YOU_XUAN`、`KUAI_SHOU_LIAN_MENG`、`OPEN_SCREEN`、`ENCOURAGE_VIDEO`。这是快手的取值，腾讯的版位枚举要自己查。

**出价方式是坑。** 主仓为它单独出了一份提案，在 `docs/plans/2026-09-06-R012-快手出价维度映射提案.md`，核心结论通用：

**不要把多个字段压成一套互斥分类。** 快手这边至少有五个字段各管一个轴：

| 字段 | 管什么 | 不能推断什么 |
|---|---|---|
| `bid_type` | 出价类型，CPC 或 OCPM 等 | 不能仅凭数字判断手动还是全自动 |
| `ocpx_action_type` | 优化目标，激活、付费、唤起 | 付费目标**不等于**二阶 |
| `unit_type` | 创意制作方式 | 智能创意**不等于**最大转化 |
| `deep_conversion_type` | 深度转化目标 | 不能等同于当前学习阶段 |
| `campaign.auto_manage` | 智能投放开关 | 和出价、创意是**不同轴** |

采用的方案是：**出价工具这个维度只承载「出价机制族」一个轴**，优化目标和创意制作方式各自保留原字段作为证据。这样分析时不会把「智能创意」和「OCPM」放成互斥的两组。

另外三条硬教训：
- **计划级和广告组级的同名字段字典不一样。** 快手 `campaign.bid_type=1` 是最大转化，但广告组列表里 `bid_type=1` 是 CPM。**不能复用字典。**
- **输入可选值不等于输出全部历史值，也不等于本账户当前可用值。** 创建接口能传的值，查询接口可能不返回。查询接口返回的历史值，创建接口可能已经不支持。映射表要按对象层级和接口版本分别限定，**不要做一张跨版本的全局数字字典**。
- **一个账户里可能同时有多种出价类型，不存在「这个账户唯一的出价方式」。** 要么下到广告组粒度，要么明确标成混合，**不能取第一条或最后一条**。

**扣量**是分桶的：`[0,10)`、`[10,30)`、`[30,+)`，单位是百分比，按 `deduction_rate` 分。

**一个维度已经永久放弃**：UBP 无数据源，那一维永久返回不支持，前端显诚实空态，**不造数**。类似情况会遇到，**没源就大方说没源，别用 0 或空表冒充**。

### 建议的推进方式

对每个分类维度，让 agent 先出**两到三个候选方案**，说明各自依赖哪些字段、覆盖率预估、有什么不能推断的边界。然后选一个，或者让它先跑覆盖率对比再选。

验证标准是**覆盖率加抽样人工核对**，不是「跑通了不报错」。经验是跑通很容易，跑对很难，因为错误往往表现为「某个分组的数偏小」，不是报错。

## 6. 用哪个 skill

取数 skill 有几个变体，别用错：

| Skill | 版本 | 说明 | 用哪个 |
|---|---|---|---|
| `rta-data-queryer` | 1.0.4 | **通用实现**，四类 connector 加 `get_data` | ✅ **用这个** |
| `rta-data-queryer-daemon` | 1.0.4 | 只是守护和安装入口，业务技能是上面那个 | 装它会带上面那个 |
| `ks-data-queryer` | 1.0.2 | **快手定制**，默认 `media=KUAISHOU`，多了 502/503/504 重试和 `insights.py` | ❌ 别用，默认媒体是快手 |
| `qihang-monitor` 下的 `ad-hourly-monitor` | 1.0.2 | 小时监控守护，依赖 `rta-data-queryer`，不是新数据源 | 做盯盘时再看 |

这边实读和真实执行用的是 `ks-data-queryer` 1.0.2。它和通用包**共享同一个 endpoint 和四类 connector**，差异只在默认媒体、重试策略和分析脚本。所以接口协议结论通用，但重试等实现行为要按版本分别确认。

## 7. 四类资源和字段字典

`resource` 四个取值，对应四张数据：

| resource | 口径 | 新鲜度 | 用来干什么 |
|---|---|---|---|
| `account` | 账户列表 | — | 有哪些户 |
| `account_realtime` | 当日实时 | **已实证分钟级**，带 `last_sync_time` | 盯盘、当日消耗、诊断 |
| `account_offline` | 离线结算，T+1 权威 | 批量分区，产出时间会波动 | 结算、财务口径 |
| `ad_realtime` | 广告级小时累计 | 分钟级，带 `hh` 参数 | 小时 pacing、归因下钻 |

字段照抄接口原名，不要自己改名。

**账户实时（`account_realtime`）**

| 字段 | 含义 |
|---|---|
| `account_cost` | 账面消耗，当日实时 |
| `account_exposure` 和 `account_click` | 曝光和点击 |
| `account_conversion` | OCPX 回传转化，账面口径 |
| `account_real_conversion` | **真实转化**，经业务核认与 BI 数同源 |
| `account_cpa` | 真实转化成本，只有有真实转化才返回 |
| `account_budget` 和 `account_budget_usage_rate` | 预算和使用率 |
| `account_deduction_rate` | 扣量比例 |
| `account_main_ad_cost` 和 `_proportion` | 主力广告消耗和占比 |
| `assessment_cost` | 考核价快照 |

**离线结算（`account_offline`）**

| 字段 | 含义 |
|---|---|
| `cost_api` / `cash` / `income` / `rebate` | 结算口径金额 |
| `wake_uv` | 唤端 UV |
| `aac_ptt_uv` | 潜客 UV |
| `newaac_uv_attrib_install` | 归因新装。**只在 `biz_name=CVR` 时含义明确等于转化 UV**，其他业务线语义待定 |

**广告实时（`ad_realtime`）**：`ad_*_h` 系列是小时累计，含 `ad_real_conversion_h` 和 `ad_real_cpa_h`。

**维度边界**：只有账户级和广告级。**没有计划、单元、创意的独立连接器**。账户结构要另外经 agent 同步。

## 8. 已实证的坑（这段最值钱，直接照做）

这些是真实跑出来的，不是推测。管道设计必须先满足这些约束，否则数据会静默错。

**`ad_realtime` 有 2000 行静默截断。**
同一范围不加过滤查询返回 2000 行，按 5 账户分片后去重并集是 2017 行。**页号和页大小参数被服务端忽略。**
所以生产的 `ad_realtime` **必须带 accountIds 或 adIds，默认按 5 账户小批查**。单账户或分片结果恰好等于 2000 行时，必须阻断归因结论，不能当完整数据用。

**离线分区不能硬编码 T-1 或 T-2。**
观测到 `account_offline` 当次 D-1 为空、D-2 命中。但**同一天下午 D-1 又由空转非空**。
说明离线重查必须贯穿日内。一次查空只能记「未观测到」，不能记「无数据」。平台**没有分区完成标记**，所以产品不能显示「奇航已完整产出」，只能展示最后观测时间、行数或指纹变化。要动态向前探测最新已产出分区，并把**实际结算数据日**显示出来。

**`hh` 参数是累计快照。**
`ad_realtime` 的 `hh` 是 0 到 hh 的**累计快照**，不是那一小时的增量。客户端允许查 0 到 24，但小时桶落库仍是 0 到 23。`hh=25` 被服务端静默钳制。较早时点会整行省略。算小时增量要自己做相邻快照差分。

**重试和频控。**
只对 502、503、504 重试 3 次，2 秒起指数退避。**鉴权失败直接抛出不重试**，这是对的，别改成重试。接口**无主动限速**，但自己要控。

**分批上限。** 账户 50 一批，广告 80 一批，可改，自动翻页。

**回溯上限未知。** 代码里没限制，服务端实际上限未知，要实跑试探。历史日期查实时**已实证可以成功返回**，用于诊断回溯，但不能替代离线结算口径。

**素材 URL 每次重新签发。**
要拉素材的话，URL 必须在同一执行链里获取并立即下载，失败就重新获取。**不要把完整 URL 放进持久队列或 checkpoint**，会过期。

## 9. 腾讯渠道特有的、必须先确认的事

这几条**没有实证过**，但资料里有，直接影响看板设计。开工前先验。

**现金折算系数。**
现金消耗要按渠道折算，系数按渠道加生效日期版本化，**绝不硬编码**。

| 渠道 | 运算 | 系数 |
|---|---|---|
| 快手 | 乘 | 0.7812 |
| **腾讯** | **除** | **1.045** |
| 头条 | 除 | 1.09 |
| 百度 | 除 | 1.51 |

注意腾讯是**除**不是乘。运算方向按资料原样存，不要自己存倒数。

**一个大问题：腾讯的赔付约等于消耗。**
资料原话是百度和腾讯的赔付约等于消耗，所以现金贡献接近零。
如果这条对腾讯成立，那么以现金口径做的考核、达标、成本空间在腾讯渠道会全部趋近于零，照搬现金口径可能整版没意义。
**这是开工前第一个要和业务确认的事**，不是技术问题。

**腾讯户能不能从这个 endpoint 出数，没验过。**
契约里一期媒体枚举**只开放了快手**，账户列表接口的 `media` 参数一期仅接受 `KUAISHOU`，其他值会返回 400。数据库层 `media` 是 TEXT 不设限，系数表里也已经有腾讯行，说明设计上留了位。
但「设计留位」不等于「跑得通」。**第一个动作应该是一次最小探针**：用自己的 userId、腾讯的 media 值、`resource=account`，看能不能返回账户列表。返回了再往下做，返回空或报错就先解决这个。
顺带确认腾讯的字段名是否和快手一致。上面那份字段字典是照快手接口抄的，腾讯可能有差异。

**`media` 的确切枚举值。** 契约里写的是 `TENCENT`。奇航接口实际接受什么字符串，探针时确认。

## 10. 建议的管道设计

不要直接从 skill 取数喂给前端。中间必须落库，分三层：

```
奇航 get_data
    │
    ▼
① 原样落库 metrics_raw          ← 接口原始行，一个字都不改
    │   · 按日期分区
    │   · 存 request_params（hh、日期范围等）→ 保证可重放
    │   · resource（account|account_offline|account_realtime|ad_realtime）
    │   · source（realtime|offline）—— 和 resource 正交
    ▼
② 算成 canonical account_metrics_daily   ← 一户一日一行
    │   · cost / exposure / click / conversion / real_conversion
    │   · cash_cost / cash_cpa / cost_space / gap
    │   · field_sources JSONB ← 每个字段是 offline 还是 realtime 还是补的
    │   · data_anomaly 标记
    ▼
③ 每日对平自检 data_quality_checks
        · 存 sample / passed / delta
        · 「数据健康」页读这张表
```

配套两张运维表：
- `etl_runs` 记每次跑的状态、入库行数、失败在哪一步、错误摘要。运行监控页直接列它。
- `backfill_jobs` 是回填任务。状态机是 `running → raw_done → canonical_done → done`，任一阶段失败置 `failed` 并留 `failed_stage`。**`done` 只在三个阶段对全部日期都终态后才置**，别提前置。

**为什么要原样落库**：奇航是唯一数据源且没有完成标记，一旦只存算好的结果，数据对不上时无法复现。存了 `request_params` 就能精确重放当时那次请求。

**`field_sources` 为什么重要**：同一天的同一个户，消耗可能来自实时也可能来自离线，两者口径不同。不记来源，后面就说不清这个数为什么和财务对不上。

## 11. 指标口径

**公式冻结，前端和 agent 永不自算**，一律后端算好返回。

```
ctr        = click / exposure                 分母 0 → null
cvr        = conversion / click
real_cpa   = cost / real_conversion           账面 CPA，只展示，不用于考核
cash_cost  = (账面消耗 − compensation) ⊕ coefficient      ⊕ = 乘或除，按渠道系数表
cash_cpa   = cash_cost / real_conversion
cost_space = assessment_price × real_conversion − cash_cost
gap        = conversion / real_conversion − 1
潜客率      = aac_ptt_uv / wake_uv
BI 转化率   = real_conversion / aac_ptt_uv
消耗速度    = 近 1h 消耗 / 1h
断量倒计时  = balance / 消耗速度      单位小时
```

**考核全部是现金口径。** 考核价、达标、成本空间都用 `cash_cost`，不是账面 `cost`。账面 CPA 只做展示。KA Pilot 的做法是账面消耗和现金消耗两张卡并排放，让优化师看得到差。

**窗口聚合要先聚合再相除**，不是把每日比率求平均。

```
cash_cpa(窗口) = Σ cash_cost / Σ real_conversion
```

达标判定按生效版本逐日取考核价，价格改动期内各日各用各的。

**三态语义必须分开，这是硬门禁不是审美：**
- `0` 等于确认有数据且值为零
- `null` 或 `−` 等于没有有效值或不适用
- 「暂无数据」等于当前筛选没有记录
- 「数据更新中」「部分数据」「已过期」等于值可能变
- 「无权限」不能用空态或 0 伪装

KA Pilot 用 `MetricValue = {value, availability: available|missing|error}` 承载，比率用 `RatioValue = {value, state: finite|infinite|undefined}`。**只有 availability 等于 available 的 0 才是真 0。**

## 12. 接口层怎么设计

**浏览器绝不直连数据源。** KA Pilot 的做法：

```
浏览器 → Next BFF（同源）→ Data API → 奇航
         ↑ 只发 {queryId, params}    ↑ 服务端 token
```

要点：
- 浏览器只发 `{queryId, params}` 两个字段。**禁止提交 SQL、表名、列名、自由表达式、workspaceId、userId**。未知字段直接 400。
- 查询走**白名单 Registry**，每项冻结参数 schema、支持视图、最长日期范围、最大行数、账户范围、模板版本。
- `workspaceId`、`userId`、可见账户**只能从服务端认证上下文注入**，不接受浏览器传。
- 服务端 token 和身份串**不得进入浏览器 bundle、页面日志或响应正文**。
- 每个数据响应必带来源标识：来源、指标版本、数据日期、时区、日切。前端页头常显，让用户一眼看出数字变化是换源不是算错。

如果只有一个人用、内网跑，这套可以简化，但**「浏览器不直连」和「不接受浏览器传身份」这两条别省**。

## 13. 第一周建议这么走

1. **探针**：用自己的 userId 加腾讯 media 加 `resource=account`，确认能返回账户列表。同时核对字段名和上面的字典有没有差异。**这一步不通，后面全白做。**
2. **确认赔付口径**：腾讯赔付是否约等于消耗。这决定看板要不要做现金口径。业务问题，先问人。
3. **落 raw**：先只做第一层，原样落库加存 `request_params`。别急着算指标。
4. **对一天数据**：拿一个成熟日，手工核对 raw 里的数和奇航页面上看到的数。对上了再往下。
5. **算 canonical**：加 `field_sources`，把每个字段来源记清楚。
6. **再做前端**：这时候才动看板，照配套的前端规范文档做。

顺序反了最容易返工的是第 4 步。教训是 **mock 测通不等于真接口通**，放行标准必须是真 payload 打真端点。
