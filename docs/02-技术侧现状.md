# 技术侧现状（v0.2 实证修订）

> 建立 2026-08-13，v0.2 同日修订。
> 来源：老板口述 + **OS 平台上那个 agent（"哈哈哈"）的自述**。它区分了实证（进程表、容器镜像、`~/.claude.json`、环境变量）与推测，本文沿用这个区分：无标记＝实证，`推测` ＝未证实。
> 这份文档定的是我们**造什么、不造什么、能不能不依赖他们**。

## 1. 真实分层（实证）

```
Multica 平台(julang-agent.alibaba-inc.com)   业务/协作层:issue/project/squad/comment/附件
   │   唯一授权通道 = multica CLI(MULTICA_TOKEN 每沙箱注入短期 token)
   ▼
multica daemon(常驻进程, --profile julang-prod)
   │   stream-json 喂输入/收输出
   ▼
claude 子进程 = Claude Agent SDK(Claude Code 内核)  ← 真正的"大脑"
   │   模型请求走本机代理 127.0.0.1 → 企业网关 → Anthropic(不直连)
   ├─ Skill 层:.claude/skills/<name>/SKILL.md + scripts/ + connectors/
   │            项目级(Multica 按 workspace 动态注入) + 用户级(~/.claude/skills)
   ├─ 子 agent(Explore/general-purpose/Plan):进程内分身,生命周期绑定本次 run
   └─ Bash/Read/Edit + MCP(平台塞进来的 stdio Node 服务, 自带 aone-agent token)

宿主层:阿里 ASI(K8s) + OpenSandbox(execd 管进程/网络) + mitmproxy 全量出网审计
本机常驻 aone-cloud-cli(/opt/cloudcli):管 skills/MCP/workflow-gateway/多 agent 引擎
                                        可插拔多引擎(同机还见到 opencode 进程)
```

## 2. 三处纠正（v0.1 我写错了）

| v0.1 我的写法 | 实证纠正 |
|---|---|
| devix = 智能体执行环境，内置阿里版 Claude Code/Qoder | **devix 是沙箱容器的基础镜像代号**（`aone-base-global/devix`），是底座不是大脑 |
| mulica = 后端编排层 | **Multica 是任务/协作平台层**（issue/评论/squad），只负责"给谁一个 run、带什么上下文"，不执行业务逻辑 |
| 启航cli = 账户基建 | **启航cli 管创意、文案、DP 的供给**；**账户基建走 kuaishou-cli** |

老板补充：`ClawOS` 大概率指 cloud-cli + opensandbox 那层宿主体系 `推测`。

## 3. 鉴权分三层——这条改变了全局判断

| 对象 | 谁管鉴权 | 我们的可及性 |
|---|---|---|
| Multica 平台资源（issue/评论） | multica CLI 内部，短期 token 按沙箱注入 | 不可及，**但我们也不需要** |
| **第三方业务系统（快手广告后台）** | **kuaishou-cli 自己管业务鉴权，是完全独立的二进制，与 multica token 无关** | **可能可及 ← 全局关键** |
| 模型/推理 | Multica 分配给 runtime，agent 不可见 | 不需要，我们自己有 Claude |

**推翻 v0.1 的结论**：我原本写"鉴权全在 OS 手里，我们必须先经 OS 调用"。实证表明**不成立**——OS 的鉴权垄断只覆盖它自己的协作平台资源（我们不关心的 issue/评论），而快手媒体侧的鉴权在 kuaishou-cli 这个独立二进制里自管。

所以真正的卡点收窄成一个问题：**kuaishou-cli 的凭证是"沙箱注入"还是"用户自己的账号登录"？**

- 若用户账号登录 → 我们能在自己机器上装、用老板自己的权限跑，**完全不依赖 Multica**，独立产品成立，博弈筹码大得多。
- 若沙箱注入 → CLI 出了沙箱就是废的，得另找路（寄生成 skill / 手工导表 / 直接要 MAPI 权限）。

老板初判"cli 应该能装能跑"，**必须实测确认**，这是开工前第一个必须钉死的事实。

## 4. 五个战略含义

**① 他们的"AI 平台"内核就是 Claude Code。** 这不是比喻，是同一个 Claude Agent SDK。skill 的目录结构、SKILL.md 的 description 匹配机制、子 agent、MCP，全部与老板做 ContentRadar 时天天在用的那套完全一致。**这条把"比技术更懂业务"升级成"业务懂业务、还比他们更会用这套 agent 栈"**——ContentRadar 沉淀的 skill 工程经验在这里是直接可迁移的硬资产，不是软优势。

**② 他们做的是原子执行能力，没有产品面。** kuaishou-cli（媒体读写+基建）、启航cli（创意/文案/DP 供给）、改价等 skill——都是单个动作。OS 前端是**纯对话 agent，没有看板**（老板确认）。

**③ "没看板"是结构性缺口，不是一时没做。** Multica 的形态是任务/协作系统 + agent runtime，天生没有"打开一眼就知道现在怎么样"的常驻界面。而运营、KA 负责人、更高层根本不会用聊天框做日常监控——他们要的是可扫视的结论页。**这就是我们的位置：常驻的、可视的、有判断的那一层。**

**④ 双口径账本的 BI 那半本是真正的难关。** 快手媒体侧数据有 CLI；BI 真实转化"有的 skill 可以查"+ 阿里内部 **FBI 平台**可查，但**存在权限问题待确认**。没有 BI 转化就算不出实际成本和成本空间——那是全部业务价值的地基。**媒体侧权限可能容易，BI 侧才是硬骨头。**

**⑤ 合规必须提前想清楚。** 他们的沙箱有 mitmproxy 全量出网审计 + K8s 隔离，是合规设计。我们的产品跑在沙箱外，就在这套审计之外处理公司投放数据。这不是拦路，但必须：数据落在哪、给谁看、脱敏到什么程度，早定规矩，别等被问。已进 `AGENTS.md` 红线。

## 5. 待验证（可直接发给 OS 上那个 agent 问）

按重要性排。探针提示词见 `docs/plans/OS探针清单.md`。

1. **kuaishou-cli 凭证来源**：沙箱注入还是账号登录？能不能在沙箱外的机器上装并跑通一条只读命令？
2. **BI/FBI 通路**：哪个 skill 能查后台真实转化，走什么接口，鉴权怎么来的，能不能在沙箱外用？
3. **`ks-data-queryer` skill 全文**：它的 `connectors/` 连的是什么数据源，认证链路是什么。
4. **现有广告类 skill 全清单**：哪些是读、哪些是写，各自调哪个 CLI。
5. **kuaishou-cli 只读命令能力边界**：能拿到哪些维度、哪些指标、最细到哪一层、历史多少天。
