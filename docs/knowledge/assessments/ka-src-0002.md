## 1. 原始资料摘要

资料包含四组相互关联的设计：

1. 面向巨量引擎、快手和腾讯广告的 KA 日报 Agent，计划通过统一的 `dailyReportData` MCP 工具取数；
2. `summary/dimension/health/tier/trend` 五类语义查询、30+ 指标、8 个维度和 12 次日报调用序列；

4. 账户/广告组实时盯盘、15 条异常规则、三张数据底表、素材分析 User Story 和非功能验收目标。

它是产品、数据和 Agent 的综合设计稿，不是实际接口文档、运行日志或验收报告。

## 11. 与现有设计冲突的地方

### 11.1 产品边界冲突

- 原文称“全渠道”；冻结 PRD 一期明确只做快手。
- 原文的操作建议可“一键执行”；当前所有写操作必须按风险走变更集、dry-run、确认和审计，自动档也有解锁门槛。
- 原文按负责人展示明细，若演变为个人排名/绩效监控会触碰当前产品红线；只允许作为资源归属与协作维度。

### 11.2 权限与架构冲突

- 原文写“权限统一在 MCP 层完成，Agent/应用无需关心”。当前产品不能把应用安全边界外包给工具：BUC 会话、workspace ACL、resource grant、审计和下游数据裁剪必须共同生效。
- 原文 YAML 示例把用户权限交给 MCP 配置维护；当前应以正式成员/资源授权表和权限系统为事实源，避免静态双写漂移。
- 原文让 MCP 同时做 SQL、权限、指标、环比和分层；当前分层要求领域计算为唯一口径、API 做鉴权、Worker 做 ETL/报告，不应把核心口径藏在不可审计工具内。

### 11.3 数据和合同冲突

- 原文硬编码 `/1.09` 并解释为“去税”；当前已确认这是渠道返点折算系数，必须按渠道和生效日期版本化。
- 原文用 number/`"NEW"`/`null` 混合类型；当前 API 要求比率/CPA 使用 `{value,state}`，需要专门定义 compare 字段，不能直接照搬。
- 原文输入 Schema 把 `channel` 列为必填，但正文又说优化师可省略，内部自相矛盾。
- 原文渠道枚举前面用 `toutiao`，后面用 `oceanengine`；必须归一化并保留 adapter mapping。
- 原文扣量区间一处为 `0-5/5-10/10-20/>20%`，另一处为 `0-20/20-30/30-50/>50%`，不能作为正式枚举。

### 11.4 运行与验收冲突

- 原文实时指标写 5 分钟，User Story/NFR 写 15 分钟；需按数据源时效和业务 SLA 统一。
- 原文 US-001 写日报生成 `<30 秒`，NFR 又写“不要求”；没有稳定验收口径。
- 原文 AD_001 以固定金额判空耗，US-021 又以 `目标成本×2` 判空耗；需按规则版本和业务类型裁决。
- 原文环比颜色既写“正红负绿”，又写“下降红、上升绿”；而成本上升与转化上升语义相反，不应只按数值方向着色。

## 12. 可以直接借鉴的内容

1. `summary/dimension/health/tier/trend` 的查询意图划分和同构行模型。
2. 日报按摘要→大盘→维度→扣量→健康→分层组织，模块失败时显式标注缺失。
3. 指标公式、来源、粒度和环比约定做成可检索字典，而不是散落在 Prompt。
4. 规则用结构化配置表达 metric/operator/threshold/direction/severity/enabled。
5. 账户级和广告组级规则分层；将 15 条作为离线回放候选，不直接启用。
6. 数据表格固定表头、数值格式、可排序和异常证据展示。
7. 素材制作商、AIGC 标识、规格、类型等维度可作为数据源验证清单。
8. 权限错误需要稳定错误码和可审计查询日志，但执行位置按当前架构修正。

## 13. 不建议照搬的内容及原因

1. **不把设计稿当系统现状**：没有工具、表、数据和 UAT 证据。
2. **不硬编码 1.09**：渠道返点政策会变，且原文“去税”解释已被业务纠正。
3. **不把所有权限压到 MCP**：应用层仍必须做身份、租户、资源和动作授权。
4. **不把 12 次独立查询当最终报告实现**：应绑定同一 snapshot/data_as_of，并允许服务端编排、缓存和并发。
5. **不返回无限宽的每行全量字段而不声明适用性**：不同粒度不可计算的指标要有 state/coverage/source。
6. **不使用任意 SQL 作为普通产品路径**：业务用户和工作流走语义层；受控分析环境另行治理。
7. **不直接启用 15 条固定阈值规则**：先离线回放、看误报/漏报，再按业务和生命周期 fork。
8. **不通过 CDN 依赖生成内部正式报告**：应使用受控、固定版本和可审计的本地依赖/渲染服务。
9. **不把建议按钮直接接写接口**：所有写动作复用当前变更集安全闭环。
10. **不使用单一红绿表达涨跌**：按指标“好/坏/中性”语义和无障碍设计展示。

## 15. 对后端架构的影响

不在本批修改 Contract。建议后续审查：

1. 为报告运行增加 `report_run_id/snapshot_id/data_as_of/coverage/source_revisions`，保证 12 模块同一口径；
2. 将查询适配器、领域指标计算、权限、报告编排分层，MCP 只是可选工具接口而非安全与口径的唯一承载者；
3. 建立源字段→canonical 字段→指标的 lineage 和 applicability 矩阵；
4. 统一比率、CPA、compare 和 `NEW/undefined/infinite` 的类型合同；
5. 规则候选先用历史数据回放，记录版本、阈值、样本、precision/recall、批准人；
6. 所有执行建议转为 changeset 草稿，禁止报告 Agent 直接调用写接口；
7. 多渠道只新增 adapter，不复制指标/权限/报告引擎。

## 16. 对前端产品设计的影响

- 报告页可复用“6 核心卡 + 异常摘要 + 12 模块”信息架构，但默认视图应可折叠，避免 34 指标同时压屏。
- 每个模块展示 `data_as_of`、coverage、来源和缺失原因；部分失败不伪装成 0。
- 环比采用数值方向与业务语义分离：箭头表达方向，颜色表达好坏；同时使用文字/图标满足无障碍。
- 宽表使用列组、固定关键列、列配置、虚拟滚动和导出，不将所有指标强塞首屏。
- 异常卡必须显示触发条件、证据窗口、规则版本和“为什么触发/没触发”。
- “执行建议”按钮先进入变更集预览，不直接写媒体。

## 17. 对 Agent、工作流、知识库的影响

- **Agent**：自然语言只负责生成结构化查询/报告配置和解释；指标由领域层计算，权限由应用与数据层共同执行。
- **工作流**：日报运行固定 source snapshot 与报告定义版本；失败模块可重试并保留 run/event 证据。
- **警报**：15 条规则作为 candidate pack，经过回放和批准后才成为默认模板；业务用户可 fork，不覆盖原版。
- **效果回收**：记录告警→建议→人工动作→T+1/T+7 结果，用于阈值评估，不用主观“准确率”宣称。
- **知识库**：本原文在 reviewed/approved 前只供研发参考；批准后可发布“设计参考”，不能标为现状或正式指标口径。正式指标应从 Contract/metric registry 单独发布。
