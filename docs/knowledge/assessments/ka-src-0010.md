## 1. 原始资料摘要

资料描述了一个内部只读查询服务及其数据字典，主要包含：

1. 统一查询入口、reader 级凭证、三类后端、请求/响应、行数和字节上限；
2. 账户日、广告组日、素材日、商品日、BI 转化和维表等本地快照模型；
3. 现金、考核、扣量、五类业务转化、账户 ID namespace 和聚合口径；
4. Hologres/ODPS 源侧查询、常见 SQL、错误码和故障排查；
5. 服务端护栏、运行端口、代码位置与启停说明。

它是一份“内部服务使用指南 + 数据字典 + 口径经验”的混合文档，不是当前 KA 产品 Contract，也不是本项目完成的运行验收报告。

## 2. 已确认事实

### 2.1 关于资料本身

- 用户提供的原文确实定义了一个 `POST` 查询接口，输入包含 backend、单条 SQL、可选 project 和 limit。
- 原文把后端分为 Hologres、ODPS 和本地 SQLite 快照，并描述了账户、广告组、素材、商品、转化和维表的数据粒度。
- 原文列出了 reader/editor/admin 角色、Bearer 鉴权、只读 SQL 护栏、行/字节/超时限制和常见错误处理。
- 原文明确指出两套 `account_id` namespace、部分业务无法直接 JOIN、媒体条件缺失会导致转化放大、赔付 JOIN 需要带 media。
- 原文含内部运行地址、内部工程/表、人员称谓和真实业务示例，因此完整正文只保存在 ignored private 区。
- 原文中的 token 是占位符或环境变量引用；本轮凭证形态扫描结果为 0，没有发现实际 Token、Cookie、AK/SK、PAT、Webhook Token 或数据库密码值。
- 原文未标注正式版本、发布日期、作者/责任人、审批记录、代码 commit、部署环境 SLA、调用日志或逐字段对平附件。

### 2.2 关于当前 KA 产品仓库

- 冻结 PRD 和指标合同仍把奇航 `get_data` 定义为一期数据主链路；`packages/contract/metrics.md` 的基础字段按奇航 resource 定义。
- 当前产品 API 对业务用户提供结构化 `/api/v1/query` 语义层，不是任意 SQL 透传。
- 当前数据库 Contract 使用 PostgreSQL raw/canonical 分层、workspace ACL、字段来源和 ETL run；本地 SQLite 只适合作为来源快照或开发/分析辅助，不是产品生产库。
- 当前商品素材域在后续阶段，素材/商品真实数据源和字段覆盖仍是数据可得性前置。
- 本仓搜索不到资料声称的 ka-data 服务端实现文件，也没有该服务的调用日志、reader token、权限映射或产品 adapter；本轮没有调用内部服务。
- 因此，本项目只确认“资料这样描述”，不能确认服务当前在线、数据范围正确或账户已经授权。

## 3. 合理推断

- 如果资料描述与当前环境一致，ka-data 可能是比“通过 Agent 间接查底表”更直接的只读数据候选通路，尤其可补 BI 转化、素材、商品和跨媒体数据。
- 本地快照层可能适合作为低延迟分析源或 ETL staging，但不应直接充当产品 SSOT；产品仍需把来源数据映射到 workspace 级 canonical 模型。
- 文档中列出的口径陷阱很适合转为数据质量规则和对平用例，因为它们直接说明了 media、namespace、业务类型和日期门槛对结果的影响。
- 资料中的三后端统一 SQL 门面便于研究和排障，但若直接暴露给产品 Agent 或普通用户，会绕开现有语义 Contract、字段级授权和稳定性治理。
- ka-data 与奇航并非必须二选一：可先把它定位为 BI/素材补充源与对平源，奇航继续承担一期已冻结主链路，再根据运行实证决定字段级权威来源。

以上为推断，必须经过 data owner、arch 和 security 审查。

## 4. 宣传性表达

以下原文措辞在缺少实证附件时只能视为来源主张：

- 服务“拥有全部数据”；
- SQLite “毫秒级、最稳、口径已对齐”；
- 某转化表是“权威表”；
- 五类业务转化与某官方表“全等”；
- 某些媒体现金贡献近似为零；
- reader token 足以安全读取全部授权数据；
- 只读关键词护栏能够完整阻止所有写入或越权查询；
- 本地快照日期范围、行数和刷新状态代表当前时刻仍然有效。

这些说法可转为验收假设，不能直接成为产品承诺。

## 6. 对我们产品是否有帮助

**有较高帮助，但价值是“补数据证据与候选通路”，不是直接替换现有架构。**

- 一期直接价值：验证 BI 转化、现金、赔付、扣量和广告组明细是否能补齐现有数据缺口；建立同日同户对平。
- 后续价值：素材/商品池数据、内容标签、跨媒体 adapter、数据血缘和数据质量规则。
- 知识价值：把易错口径沉淀为 Agent 可解释的数据字典与排障知识。
- 风险价值：提前暴露 namespace、media 条件、硬编码系数、临时地址和共享 reader token 等治理问题。

## 9. 部分包含能力

1. **BI 转化**：当前 Contract 把奇航字段标为 BI 同源，但 ka-data 提供更细的五业务来源主张；双方尚未做本轮独立对平。
2. **广告组数据**：当前模型偏广告小时级和媒体结构，资料提供日级配置/表现字段候选，粒度和 ID 映射未统一。
3. **素材与商品**：产品有完整功能方向，真实表、标签覆盖、素材 URL 权限和刷新链路未接入。
4. **多渠道**：资料描述四媒体数据，产品一期仍只快手；adapter 和权限未验证。
5. **数据健康**：产品有 `data_as_of/coverage/sources` 与 ETL 监控，但缺针对 media、namespace、业务日期门槛的具体检查包。
6. **查询工具**：产品有结构化 query，缺面向 data owner 的受控深度排障通道。

## 10. 缺失能力

1. ka-data provider adapter、连接健康探针和稳定环境配置。
2. ka-data reader 身份到 BUC/workspace/resource ACL 的正式映射。
3. 源表字段→canonical 字段→指标的机器可读数据血缘。
4. 奇航、ka-data、MAPI 与业务官方表的逐字段权威级别和冲突处理规则。
5. 两套账户 ID namespace 的映射表、置信度、缺失和版本管理。
6. 本地快照的版本、data_as_of、coverage、生成 run 和失败状态。
7. 现金/考核/扣量公式的版本化导入和业务 owner 审批链。
8. 大结果集的稳定游标/分区导出；文档中的 OFFSET 方案不适合持续变化的大表。
9. 对受控 SQL 的解析器级 allowlist、查询成本限制、行列级裁剪和审计回放。
10. 素材/商品数据的许可、隐私、URL 访问和产品知识库发布边界。

## 11. 与现有设计冲突的地方

### 11.1 数据主链路

- 冻结设计以奇航 `get_data` 为一期主链路；资料可能被误解为“新接口应立即替代奇航”。本轮不作替换，只列为补充/对平 provider 候选。
- 当前 Contract 说真实转化字段来自奇航且与 BI 同源；资料又描述独立 BI 转化表。两份来源不能互相证明，必须做同日同任务/账户对平。

### 11.2 查询与权限

- 资料是任意只读 SQL 透传；产品 API 是结构化语义查询。普通用户和 Agent 若直接拼 SQL，会绕过字段稳定性、成本控制和行列级授权。
- 资料以 reader token 为主要门槛；当前产品要求 BUC、workspace ACL、resource grant、credential owner 和审计共同生效。
- 临时沙箱地址会变化，不能进入产品 Contract、前端配置或知识正文；应由环境级 secret/config reference 管理。

### 11.3 存储与数据模型

- 资料把本地 SQLite 快照描述为主要查询源；冻结生产设计使用 PostgreSQL。SQLite 只能作为上游快照或测试夹具，不能成为多用户生产存储。
- 资料用整数日期、字符串“不限”、多套 ID namespace 和宽表；当前 Contract 使用强类型日期、租户复合键、比率状态和 canonical 表，需要显式 adapter。
- 资料按源表粒度组织；产品按业务对象、workspace 和字段级来源组织，不能把源表直接等同于产品模型。

### 11.4 指标口径

- 资料列出固定媒体系数；当前 Contract 要求渠道系数按生效日期版本化，禁止硬编码。
- 资料的现金公式使用“乘系数”表达，当前 Contract 使用“除以渠道系数”表达。系数定义可能互为倒数或属于不同商务口径，未经业务 owner 对平不能静默统一。
- 资料把部分现金/赔付现象写成结论；产品指标必须保留来源、覆盖、异常和不可计算状态，不能把近似值当零。

## 12. 可以直接借鉴的内容

1. 将每张来源表的粒度、主键、字段和日期范围写成数据源目录。
2. 把 media 条件、namespace、赔付 JOIN、业务 date-gate 等陷阱转成数据质量检查。
3. 对每次查询记录 backend、data_as_of、row count、truncated、limit 和错误分类。
4. 保留三层路径：低延迟快照→源侧回查→canonical 产品查询。
5. 素材、商品和绑定桥的数据模型可作为 P2 数据可得性检查清单。
6. 将“无法列表但可能可查”“超时”“字段不存在”等排障经验沉淀为受权限控制的运维知识。
7. 只读服务应同时有应用层护栏和底层只读身份，而不是只依赖 Prompt 或前端限制。
8. 对高风险口径建立官方样表/业务确认凭证和自动对平任务。

## 13. 不建议照搬的内容及原因

1. **不向普通用户或产品 Agent 开放任意 SQL**：会破坏稳定 Contract、权限和成本治理。
2. **不在产品中保存或展示 reader token**：只能保存 secret reference 和绑定状态。
3. **不依赖临时沙箱 URL**：环境重启即变化，不具备生产稳定性。
4. **不把 SQLite 快照当产品主库**：缺少多租户、并发、审计和正式运维能力。
5. **不硬编码媒体系数和业务日期门槛**：必须版本化并由业务 owner 审批。
6. **不把内部宽表直接暴露给前端**：先映射 canonical schema 和字段权限。
7. **不把“SELECT/WITH + 关键词拦截”等同于完整安全**：需 SQL parser、底层只读角色、allowlisted views、查询成本和审计共同防护。
8. **不把文档样例数据当验收证据**：必须保留原始查询、时间、样本、预期和实际差异。
9. **不因资料覆盖四媒体就扩一期范围**：一期仍只快手。

## 14. 对 PRD 的影响

本批不修改冻结 PRD。建议 arch 将以下内容列为后续候选，而非现在承诺：

- 数据源接入增加 provider registry，区分 qihang、ka-data、MAPI、人工导入及字段级权威来源；
- 数据健康增加 source revision、data_as_of、coverage、namespace mapping 和口径对平结果；
- 商品素材域的数据可得性门中加入 ka-data 素材/商品/绑定桥探针；
- 产品知识库发布经批准的数据字典和易错口径，不发布临时地址、reader token 操作和未经审查的内部表清单；
- 一期主链路是否调整必须另做架构变更与业务验收，不能由本资料自动触发。

## 15. 对后端架构的影响

建议按“受控 adapter”接入，而不是让前端或 Agent直连：

1. `ka_data_adapter` 仅在 Worker/内部数据服务中使用，服务地址和凭证用环境级 secret_ref；
2. adapter 只暴露批准的查询模板/视图，输入是结构化参数，不接收 Agent 生成的原始 SQL；
3. 来源行先进入 `metrics_raw` 或专用 staging，再映射 canonical，保留 source/table/revision/query_run/field_sources；
4. 建立外部 ID namespace registry 与 mapping 表，禁止跨 namespace 猜 JOIN；
5. 每个字段登记 authority、freshness、coverage、fallback 和 conflict 状态；
6. 对现金、转化、赔付和考核建立同日同户/任务自动对平，差异超过阈值进入 data quality work item；
7. 查询层增加 statement parser、allowlisted view、只读 DB role、行列级 ACL、字节/时间/成本限制和审计；
8. 快照读取必须返回 data_as_of、snapshot revision 和生成 run；缺失时 UI/Agent 显示未知，不伪装为实时。

## 16. 对前端产品设计的影响

- 普通业务界面继续使用大盘、透视、总表、账户详情和素材/商品页，不增加 SQL 编辑器。
- 治理后台可增加“数据源状态”：来源、环境、最后成功时间、覆盖日期、行数、对平状态、失败原因。
- 指标/字段详情展示来源血缘、适用粒度、更新时间和已知 namespace 限制。
- 数据被截断、缺权限、超时、来源冲突时显示明确状态，不把空数组或零当真实结果。
- 素材/商品数据在 P2 接入前先做字段覆盖和 URL 权限预览，不能因为表存在就开放页面。
- 若为 data owner 提供深度查询工具，应与业务产品隔离并有模板、审批、查询成本和下载审计。

## 17. 对 Agent、工作流、知识库的影响

- **Agent**：自然语言先编译为 `/api/v1/query` 或批准的工具参数；不得生成任意 SQL、读取 token registry 或回显内部服务地址。
- **工作流**：ETL/对平任务固定 adapter 版本、查询模板、数据日期和 credential owner；重试不换身份。
- **规则**：将 media 缺失、namespace 误 JOIN、日期门槛、截断和快照过期转为数据质量规则，不直接变成投放调控规则。
- **效果回收**：BI 转化若验证可用，可加强 T+1/T+7 回收，但必须记录与奇航/媒体口径的差异。
- **知识库**：审查通过后优先发布“经批准的数据字典、口径与排障摘要”，不发布原始运行地址、内部表全名、人员、真实业务样例或 token 操作步骤。
- **默认可信范围**：在 `approved/published` 前，本资料只供授权研发/审查参考；产品 Agent 不得默认召回。

## 18. 建议动作：融合 / 补证 / 仅参考 / 不采用

总体建议：**补证后选择性融合**。

- 融合候选：数据源目录、粒度字典、namespace 治理、数据质量检查、素材/商品数据可得性清单。
- 先补证：服务连通、reader ACL、底层只读性、快照 freshness、BI/现金/考核对平、ID mapping、数据许可。
- 仅参考：原始 SQL 样例、内部运维命令、当前表规模和日期范围。
- 不采用：普通用户/Agent 任意 SQL、共享 token 台账、临时地址入 Contract、SQLite 作生产主库、硬编码系数、因“全媒体”扩一期。

## 19. 建议优先级

- **P0 安全与事实探针**：由授权 data owner 使用只读测试身份验证 health/query、角色权限、审计和底层只读；不在本项目保存 token。
- **P0 数据对平**：选少量脱敏账户/任务和连续日期，对平奇航、ka-data 与业务确认表的消耗、转化、赔付、现金、考核；记录差异而非只报“相等”。
- **P0 映射**：确认账户/任务/广告组 namespace、media 和业务类型映射，形成可版本化 lineage。
- **P1 adapter 候选**：探针通过后，接入 Worker 作为补充源/对平源，先快手、先只读，不替换主链路。
- **P2 数据扩展**：素材/商品、内容标签和多渠道 adapter，以许可、字段覆盖、ACL 和数据质量为前置。
- **不排期**：面向普通业务用户的任意 SQL 产品化。

## 20. 需要审查 Agent 裁决的问题

1. 谁是 ka-data 的正式 owner，文档版本、服务环境和支持 SLA 是什么？
2. 是否允许把它作为一期奇航的补充/对平源，还是仅作为研究工具？
3. reader token 的数据范围、签发/撤销、审计和 BUC/workspace 映射是否满足项目要求？
4. SQL 护栏和底层只读角色是否经过 security 验证；是否只允许批准视图/模板？
5. BI 转化、现金、赔付、扣量和考核中，哪些来源是字段级 SSOT？冲突由谁裁决？
6. 固定媒体系数与当前版本化 `channel_coefficients` 如何映射；是否互为倒数或口径不同？
7. 两套 `account_id` namespace 是否有正式映射资产；无法映射时产品如何展示 coverage？
8. SQLite 快照的生成链、data_as_of、保留期、失败补偿和 hash/revision 能否提供？
9. 素材/商品/URL/内容标签能否进入本产品，允许哪些角色查看和导出？
10. 是否批准做第一批只读探针和同日同户对平；测试样本由谁提供与验收？
11. 若探针通过，ka-data adapter 进入 P1 还是 P2；是否继续保持一期只快手？
12. 产品知识库可发布哪些派生内容：字段字典、口径、排障摘要、还是只保留受控引用？原文是否继续仅留 private？
