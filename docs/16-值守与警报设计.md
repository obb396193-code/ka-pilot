# 值守与警报体系设计 v1（借鉴 Devix 运维 Agent）

> 建立：2026-08-17　来源：老板提供的阿里内部文章《消费者认知团队 DataWorks 运维 Agent》（Devix 承载，Harness Engineering 理念）+ 八路审查的夜间值守/升级路由结论
> **这篇文章的最大价值：我们独立设计出的两个东西，它在生产环境已经跑通了**——①置信度换自动化程度（=B5 自治度滑块）②手动重跑检测（=我们的带外变更检测）。设计有了内部判例。

## 0. 借鉴总纲：Harness Engineering 三句话（原文，直接采纳）

1. **Agent 负责语义理解与决策推理，脚本负责数据召回与动作执行**——与我们已定铁律（agent 不做确定性计算）完全同构
2. **用置信度换自动化程度**——高置信度全自动、中等人工确认、低置信度升级
3. **让系统从自己的经验中学习**——案例沉淀→反馈决策→规则进化

原文点题句进产品叙事：**"Harness Engineering 的本质，不是让 Agent 更聪明，而是让 Agent 更可控"**、**"系统不是被配置出来的，而是被训练出来的"**。

## 1. 领域映射（运维域 → 投放域）

| 他们（DataWorks 运维） | 我们（快手投放） |
|---|---|
| 实例失败告警 | 账户异常（超成本/断崖/0曝光/断量倒计时/Gap） |
| 重跑 | 调价/压预算/暂停计划 |
| error_pattern 错误模式 | anomaly_pattern 异常模式（规则引擎的规则 ID） |
| 日志层层深入（DataWorks→Logview→ODPS） | 数据层层深入（账户级→广告级→操作史→素材信号） |
| 代码变更检查 | 近期人工操作检查（谁昨天动过这个户） |
| 上游依赖失败 | 上游信号（素材被拒/余额不足/任务口径变更） |
| 重跑成功率 | 建议采纳后 T+1 见效率 |
| 案例库 resolution | 效果回收记录 + 错题本 |
| 手动重跑检测 | **带外变更检测**（后台直接改价被系统感知） |
| 规则自进化三路径 | 我们的规则进化（见 §5） |

## 2. 值守闭环全链路

```
规则引擎扫描（定时+盯盘高频）
  → 发现异常 → 生成告警
  → Agent 智能诊断（多假设检验：素材疲劳？竞价环境？预算撞线？口径变更？数据延迟假象？
                    逐一查证→输出双产物：Markdown 诊断报告给人 + JSON 结论给决策引擎）
  → 分级决策引擎（三级规则匹配 + 案例库查询 + 置信度调整 + 决策树评估）
  → 五种动作之一（见 §3）
  → 钉钉通知（按 §4 分级路由）
  → 结果追踪（T+1 效果回收；处理后再异常则重新触发，闭环）
  → 案例沉淀（含 resolution：怎么解决的/几次/人工还是自动）
  → 规则进化（§5）
```

**诊断 JSON 结构**（照抄其四段式，字段名换投放域）：
- 异常诊断：anomaly_pattern / category / confidence(0-1) / severity / root_cause_summary / evidence[]
- 环境上下文（决策树分支条件）：近期有无人工操作｜上游是否异常（素材拒审/余额/口径变更）｜是否大盘波动期｜是否首次出现｜账户是否冷启动期
- 修复建议：初步方案，最终决策由决策引擎综合历史后给出——**历史经验可覆盖 Agent 初判**（某类异常历史处理失败率高时自动升级人工而非照建议执行）

## 3. 五种决策动作（自动化程度从高到低）

| 动作 | 含义 | 触发门槛 |
|---|---|---|
| **自动处置** auto_act | 白名单防御性动作直接执行（如暂停超成本 200% 的计划），事后钉钉汇报 | 置信度>0.9 + 历史成功率>80% + 无近期人工操作 + 规则标记"安全可自动" + 单日累计影响金额未超上限 + **可一键回滚** |
| **卡片确认** act_with_approval | 钉钉卡片带变更集，点确认才执行 | 首次出现的可恢复异常，或置信度不足 |
| **方案提案** propose_fix | 生成调价/结构调整方案，Web 端确认 | 诊断出结构性问题且有可行方案 |
| **排查建议** investigate | 标注排查方向+证据，不给动作 | 数据异常/上游依赖类需人判断 |
| **升级人工** escalate | 按 §4 路由通知人 | 未知异常/权限类/规则未覆盖 |

**三道防线**（照抄）：①自动处置的复合门槛（上表）②写操作三层校验（诊断层完整提案→决策层命中→执行层人工确认）③**未知异常一律走全局默认规则：升级人工**。

## 4. 警报分级与通知路由（老板点名要的）

| 级别 | 定义（投放域） | 通知行为 |
|---|---|---|
| **P0** | 户在裸奔超成本、断量倒计时<2h、大额异常 | **立即推送+突破静默时段**；30 分钟未确认→自动升级值班/上级（钉钉 DING，必要时电话）；升级前有倒计时，标"处理中"可暂停升级 |
| **P1** | 超成本、消耗断崖、高消耗零转化 | 正常推送；当日未处理→次日催办卡片；48h 未处理→升级运营 |
| **P2** | 衰退预警、机会提示、素材疲劳 | 不实时推，攒到整点/并入早报 |

配套治理（优化师路结论并入）：**同类聚合**（同任务 5 户同种异常合并一条）｜静默时段仅 P1/P2 生效｜户级静音 3 天选项｜规则忽略率>90% 提示调阈值｜冷启动户自动套宽松阈值（生命周期×规则联动）。

**催处理卡片**：待处理工作项超时 → 钉钉催办卡片（带证据快照+一键进 Web）→ 仍超时 → 升级链（优化师→运营→负责人），升级带完整上下文包，不是"他没干活"的告状。

## 5. 规则自进化（三路径，全部"脚本扫描→Agent 分析→人工审核"）

| 路径 | 触发 | 动作 |
|---|---|---|
| A 新规则发现 | 扫描近 30 天 pattern=unknown 的异常 + 被高频忽略的建议，聚类 | Agent 语义分析聚类→设计新规则+决策树草稿→人审后入库 |
| B 规则效果修订 | 某规则建议采纳后见效率 <30% | Agent 分析失败原因→建议调阈值/分支 |
| C 自动化安全审计 | 自动处置类动作实际失败率 >50% | **自动降级该规则的自治档位**——安全最后防线 |

**数据驱动决策树**：新规则的分支不拍脑袋——历史案例里"纯调价恢复占比高"就加自动分支，"要改结构才恢复"就只给提案分支，样本不足就只给升级人工。**这正是 B5 自治度滑块的解锁机制的具体算法。**

## 6. 直接照抄的四个运维工具

| 工具 | 我们的对应 |
|---|---|
| 操作人实名溯源（钉钉 JSAPI 免登识别点按钮的人） | 卡片确认/催办的操作人记录进审计 |
| 故障日报自动生成 | 并入自动日报：当日异常汇总+处理状态+时间线 |
| 诊断报告自动归档 | 诊断报告存知识库（复刻 CR 那套），自动成为案例文档 |
| **手动重跑检测** | **带外变更检测的内部先例**：绕过按钮在后台手动操作，系统同样感知并通知——证明该模式在阿里内部已是生产实践 |

## 7. 架构参考价值 + Devix 可用性（2026-08-17 老板确认）

- **★老板确认：我们有 Devix 权限**——Devix 就是 OS/Multica 平台底下的运行时（02 文档实证过：devix 是沙箱基础镜像，宿主层=cloud-cli+opensandbox）。**可以设计链接 Devix**。
- 这改变值守子系统的托管选项：文章证明 Devix Sandbox 能跑 **7x24 常驻 Python Flask + 公网中转 + 钉钉回调**。我们的值守组件（监控轮询/诊断触发/催办升级）可以选择跑在 Devix 沙箱里——**好处：与 agent 取数/执行天然同环境（不用跨环境调 skill）、有内部判例背书；代价：多一个部署面**。
- 架构选项待定（不阻塞设计）：A 值守全在 FaaS（node-cron 轮询+webhook 触发 agent）｜B 值守常驻 Devix（照抄文章三组件模式）｜C 混合（FaaS 管产品与数据，Devix 管值守与执行中转）。**倾向 C**：各取已验证的强项，等写链路实证结果后定。
- 他们的"监控脚本/中转服务/诊断 Skill"三组件分离 + 钉钉群做人机协同界面——与我们"ETL/规则引擎/钉钉中心"分层同构。
- **政治价值**：这是阿里内部垂直业务团队（非平台技术部门）自建 Agent 运维系统的公开先例，与我们"业务侧自建投放工作台"叙事同型——可引用为判例。
