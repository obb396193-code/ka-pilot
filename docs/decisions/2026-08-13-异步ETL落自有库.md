# 决策：取数走异步 ETL 落自有库，产品只查自己的库

> 日期：2026-08-13　状态：**已定（架构主干）**　依据：`docs/07-已有网关资产.md`、`docs/08-平台能力实证.md`

## 背景

取数只有一条已验证通路：建 Multica issue → @agent → agent 调 skill → 轮询评论拿结果（自建钉钉网关实证，8 秒轮询、一问一答、几十秒到几分钟）。

我一度判定"这撑不住产品级批量，必须绕开 agent 直连底层"。**这个判断混淆了交互式查询和批量取数两件事。**

## 决策

```
定时（夜里/每小时）：我方服务 → 建 issue @agent → agent 用自己的合法凭证调 skill 取【原始数据】
                  → 回写评论 → 我方服务读取 → 落进我们自己的库
用户使用（白天）：  前端 → 我方 API → 查我们自己的库（毫秒级）
```

## 理由

1. **产品要的实时性是"快速看到已存下的数据"，不是"实时穿透查媒体"。** 用户等待发生在白天查库，取数发生在夜里没人等 —— 轮询慢完全无所谓。
2. **口径计算留在我方**（台账 #37 铁律）：只要原始数据，指标/成本空间/Gap 在我们服务里算一遍。这是四角色数字同源的唯一保证，也是避免重踩网关 10.15（真实/回传 CPA 算成同值）的唯一办法。
3. **凭证边界干净**：我方不持有任何人的个人 token。agent 在沙箱里用它自己的合法凭证取数，我们只接收数据。
4. **零新增权限即可起步**：不必等 MAPI 应用身份、不必等 FBI 开放接口（两者均未证实存在）。
5. **有历史快照**：落库天然积累时间序列，才可能做效果回收（T+1 验证建议是否生效）——这是 agent 与脚本的分水岭（03 文档）。

## 代价与边界

| 代价 | 说明 |
|---|---|
| 数据新鲜度 = 上次 ETL 时间 | 前端必须显式标注"数据截至 HH:MM"，不许假装实时 |
| 依赖 agent 可用性 | ETL 失败要有重试 + 告警，且前端要能显示"今日数据未更新"而不是展示旧数当新数 |
| 一期合法性挂在个人权限上 | 见 08 文档 §5 分期模型；二期部门级推广必须换应用身份，硬门槛 |

## 被否的替代方案

- **直连底层服务**：`ks-data-queryer` 底层是什么尚未查明；FBI/DataWorks 现有路径全是个人 token 或浏览器自动化，直连等于把个人凭证搬进产品，与 05 文档原则冲突。**未证实的通路不能作为架构前提**（OS 原话，采纳进红线）。
- **借用 agent 的 token**：已在 05 文档否决。
- **纯人工导表**：留作 BI 侧兜底，不作主干。

## 立即可做

1. 起骨架用 `Next.js BUC 中后台模板`(scaffold-id 10)：前端 + BUC 登录一次解决。
2. 定时不走 ScheduerX（Java 脚手架）——常驻容器内用 `node-cron` 即可；**须先实测 daily 环境会不会回收/休眠**，方法是挂 5 分钟心跳任务跑满一天，翻 `a1 faas logs` 看断点。
3. 库先申请 RDS/Tair（Normandy IaC）；未批下来前用最小可行存储跑通闭环。
