# 决策：OS 基建对话采用平台托管，提示词生成作为兜底

> 日期：2026-08-17
> 状态：已确认
> 范围：账户基建、Multica/OS 对话和结构化指令接入方式

## 决策背景

当前一个账户通常对应一段 OS 基建对话，用户通过 Skill 完成日常广告组基建和定时任务配置。现有操作依赖聊天框，账户、对话、基建配置、定时任务和运行结果之间缺少可视化关系。

现有产品设计已经包含账户池、基建工作流、Multica 执行、运行对账和原始日志，但尚未把“账户—OS 对话—结构化指令—基建运行”作为一组可管理对象。

## 已选方案

采用 **B 为主、A 兜底**：

### B：平台托管 Multica 对话（主方案）

- 新发生的基建任务优先从 KA 平台发起；
- 平台创建或管理自己拥有的 Multica issue/对话；
- 平台保存账户、任务、对话、Skill、基建配置和运行实例的关联关系；
- 用户通过表单选择参数，系统生成结构化指令并发送至 Multica；
- 平台轮询或接收执行结果，解析后形成基建台账、运行状态和审计记录；
- Multica/OS 继续作为受保护媒体能力的执行层，平台作为管理和调度层。

### A：结构化提示词生成（兜底方案）

当以下情况出现时，平台只生成可复制的结构化提示词：

- Multica 创建或续接失败；
- 指定 Skill 暂时不能通过平台调用；
- 需要在历史 OS 对话中继续，但该对话没有可用接入接口；
- Multica 服务不可用，但用户仍需人工处理。

兜底模式必须明确显示“尚未由平台发送”，不能把生成提示词当作已经执行。

## 未选方案

### 仅做提示词生成器

不采用为主方案。它只能减少手写提示词，无法建立账户、定时任务、运行结果和效果回收的闭环。

### 完整同步新 OS 的全部历史对话

暂不采用。当前没有实证确认以下接口存在：

- 用户对话列表；
- 指定对话消息读取；
- 向指定已有对话发送消息；
- OS 定时任务查询、修改和取消。

后续拿到正式接口后，通过连接器扩展，不改变本次产品对象模型。

## 产品边界

- 平台管理的是账户与 OS 执行资源的绑定关系，不保存或展示用户 Token；
- “一个账户一个对话”作为一期迁移习惯，不写成永久数据约束；
- 一个账户可保留多段历史对话，但同一时间只设置一个主要基建对话；
- 平台只能完整管理自己发起并获得结果的请求；历史 OS 对话同步能力以接口实证为准；
- 写操作仍遵守预览、确认、幂等、冲突锁、执行后回查和审计要求；
- 发送成功不等于执行成功，Multica 返回未知状态时先对账，禁止盲目重发。

## 产品入口

- 不做一级导航；
- 在“账户资源”内部增加独立的“基建管理”Tab，与账户池并列；
- 不使用“OS 对话管理”作为 Tab 名称，OS 对话作为基建管理中的执行资源；
- 账户池、任务详情 SOP、我的工作、自动化运行记录和钉钉卡片提供上下文快捷入口；
- 所有入口进入同一基建管理 Tab，并携带账户、任务或运行筛选，避免形成多套状态。

## 后续待设计

- OS 执行空间和对话绑定的数据模型；
- 账户基建控制台的页面和入口；
- 结构化指令模板及参数 Schema；
- 定时基建任务由平台调度还是由 OS 代理调度；
- 历史对话的人工绑定、导入和只读展示方式；
- Multica 创建、发送、轮询、取消和续接能力的接口实证。
