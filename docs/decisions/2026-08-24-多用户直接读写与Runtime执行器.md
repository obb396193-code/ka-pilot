# 决策：多用户直接读写与 Runtime 执行器

> 日期：2026-08-24  
> 状态：老板已确认方向；源码与真实 Runtime 能力仍须逐项验真。

## 已选方案

KA 平台采用“产品控制面 + 可插拔执行器”。用户登录后绑定或授权自己的渠道身份与凭证；平台统一负责账户范围、变更集、确认、幂等、审计和效果回收。

执行后端保留三类：产品正式直连、常驻于 Multica/OS Runtime 的直接 CLI/MITM 执行、Multica Run 兜底。Multica 是可替换 Provider，不是产品永久唯一权限入口。

## 渠道边界

- 钉钉 Stream、身份映射、常驻运行时、结构化指令、确认和审计属于公共能力。
- 外部 SOP 的 `tt.sh` 明确按字节/巨量渠道处理，不视为全渠道通用。
- `tools.py`、`deduct.py` 和 MITM 身份头对快手/腾讯/百度的适用性，在取得源码并真实验证前统一标“未验证”。
- 每个媒体实现独立 Adapter，并在 Capability Registry 中声明支持范围和证据等级。

## 未选方案

- 不把一个人的全套凭证做成全群共享机器人。
- 不让群消息直接修改生产系统提示词或官方知识。
- 不绕过变更集和确认门自动执行媒体写操作。
- 不把“在 Multica 沙箱里直接写”表述成“产品已取得完全独立的服务权限”。

## 影响

- 新增独立 Runtime Executor 部署单元；DingTalk Gateway 继续保持低权限。
- 接入管理从固定“三凭证”扩展为按用户、渠道、执行后端管理授权档案。
- 操作工具箱、工作流、钉钉卡片和 Agent 使用同一 Capability Registry，不感知底层执行通路。
- 后续取得 `dingtalk-bot-migrate.tar.gz` 后必须先做源码审计，再决定复用、改造或拒绝。
