# 已有网关资产（钉钉 ↔ OS 网关）

> 建立：2026-08-13，来源：老板提供的自建项目架构文档 + 运营先例补充说明
> **定位：这不是听说的先例，是我们自己已经跑通并部署过的系统。管道已经通了。**

## 1. 一句话

我们已经有一个部署在 `a1 faas` 上的 Node/Koa 常驻服务，它用 Multica CLI 建 issue + @agent、轮询评论拿结果，再用无头 Chromium 把 HTML 模板渲染成 PNG 发到钉钉群。**全链路实测跑通过，含踩坑记录 18 条。**

运营那边说的"建了个服务能直接把请求发给 OS、OS 对话不感知 token"——就是同一个模式。

## 2. 它一次性回答了探针 B 的关键问题

| 探针 B 问题 | 答案（已实证） |
|---|---|
| 2. FaaS 能跑常驻服务吗 | **能。** `custom.debian10` 自定义运行时，`bootstrap` 里 `exec node server.js`，Koa 监听 PORT 9000。不是只能写函数 |
| 4. 能多路由吗 | 能，就是个完整 Node 服务 |
| 7. 凭证怎么配 | `a1 faas config vars set` 配环境变量；绝不写进代码/仓库 |
| 10. 前端能不能托管 | **不止能托管——能跑 Chromium 做服务端渲染。** 实测单次渲染内存峰值 540MB，实例限额 3GB，部署包 243MB |
| 13/14. 多用户鉴权 | 这套走的是**钉钉企业内部应用**（ClientID/Secret + Stream 模式），不是 SSO。是另一条可行路 |
| 21. 外部服务能不能操作 Multica issue | **能。** 用 `mcn_` 令牌 + CLI 建 issue、读评论 |
| 25. 部署 | `a1 faas deploy .` 发 daily；`a1 faas logs --function-name index` 看日志；owner 权限由 `appops/owner` 组控制（403 就是 empId 不在里面） |

## 3. 三个最重要的发现

### 3.1 `mcn_` 令牌就是"外部服务合法调 OS"的官方答案

文档写得很明确，三种令牌前缀：

| 前缀 | 绑定对象 | 用途 |
|---|---|---|
| `mul_` | 某个人的账号 | Personal Access Token |
| **`mcn_`** | **外部服务／节点** | **Cloud Node 令牌，本场景就该用这个** |
| `mat_` | 单次 agent 任务 | 临时令牌，`multica login --token` 直接拒绝，任务结束即失效 |

**这解开了 06 文档 §3 的谜题**：运营的"有权限但不是拿到 token"，实质是他的服务持有一个**为外部服务专门签发的 `mcn_` 令牌**——不是借用某个人或某次任务的凭证。所以 05 文档定的原则（不借个人 token）和这条路完全兼容：**这是官方为外部服务留的正门。**

### 3.2 双口径转化字段本来就存在

踩坑 10.15 写得很清楚：数据源里 `conv_real`（真实转化，入库／打款等严格口径）和 `conv_report`（回传转化，媒体账面）**是两个独立字段**，`ks-data-queryer` 查询直接返回。

**这是本项目最大的好消息。** 之前我把"BI 真实转化拿不到"列为最大未知、业务价值地基悬空。现在证明：**真实转化通过 skill 已经能拿到**。双口径账本（账面 vs 真实、真实 CPA vs 回传 CPA vs 考核 CPA）的数据基础是现成的。

仍需确认：口径细节、延迟、可回溯天数、能否按小时／计划级拆分。

### 3.3 钉钉 Stream 模式＝零部署摩擦的触达通道

反向长连接，服务主动连出去，**不需要公网 IP、域名、证书、白名单**。这对推广是硬优势：用户不用装任何东西、不用记网址，在他们本来就待着的群里就能收到。

## 4. 战略含义：缺的不是管道，是产品

管道已通，所以真正的空白很清楚——**现在这套是「问答机器人」**：

| 现状 | 产品需要 |
|---|---|
| 你问它才答（pull） | 主动发现问题推给你（push） |
| 一次一答，无状态 | 有状态：处理过／忽略过／待观察 |
| 无持久化 | 存工作项、历史快照、效果回收 |
| 单人对话 | 多用户、可见范围、任务分发 |
| 图片＝终点 | 图片是入口，点进去能干活 |

**所以我们不是从零开始，是在已通的管道上加「判断 + 状态 + 协作」三层。** 这把工期认知整体前移了一大步。

## 5. 一个必须改的架构决定：agent 不能当计算层

现有网关把「查数据 + 字段映射 + 算指标 + 选模板 + 算图表坐标」全交给 Multica Agent 做，网关只做变量替换和截图。**这个分工对问答机器人合适，对产品不合适。**

两条踩坑记录就是证据：

- **10.15 真实 CPA 和回传 CPA 算出同一个值**——因为 agent 把同一个转化数往两个公式里各算了一遍。
- **10.16 超过 3 个账户数据静默消失**——因为 agent 按过时文档往不存在的占位符塞数据。

这两个都不是偶然 bug，是**把确定性计算交给概率模型的必然结果**。放在群里答错一次没人追究；放进产品里，就是 03 文档 §3 说的那件致命事——**负责人看到的成本和优化师看到的不一样，一次失信再也拉不回来。**

**架构原则（定为铁律）**：

| 层 | 谁做 | 理由 |
|---|---|---|
| 取数 | agent／skill／CLI | 它有权限，这是它的价值 |
| **口径计算、指标派生、聚合** | **我们自己的服务** | 必须确定性、可测试、可复现、四角色同源 |
| 判断与建议 | LLM（可控 prompt + 规则兜底） | 这才是模型该干的 |
| 渲染呈现 | 我们自己的服务 | 已有现成能力 |

**向 agent 要原始数据，不要它加工过的结论。** 加工在我们这边做一遍，四个角色的数字才可能一致。

## 7. 通道分工：钉钉做触达，Web 做工作台

不是二选一，各有不可替代之处：

| 通道 | 干什么 | 为什么 |
|---|---|---|
| **钉钉** | 每日早报、异常预警、派活通知、一句话结论 + 跳转 | 零安装、在人本来就在的地方、推得动 |
| **Web（FaaS 托管）** | 工作台、待处理队列、任务分发、下钻、历史复盘、四角色视图 | 有状态、可交互、能承载"干活"，也是视觉差异化的战场 |

现有网关的图片渲染能力正好是钉钉侧的现成弹药；ActionCard 的按钮跳转就是从钉钉进 Web 工作台的桥。

## 8. 仍然未知（进探针 C）

1. `mcn_` 令牌怎么申请、有效期、权限范围、能不能续期。
2. `ks-data-queryer` 底层调什么服务——**能不能让我们的服务直连**，绕开 issue 轮询（轮询有 8 秒周期 + 一问一答的架构限制，撑不住产品级批量）。
3. 数据库：有没有可申请的 RDS／Tair，还是只能先用轻量存储。
4. 快手数据的账户可见范围由什么决定——我们的服务能查到哪些户。
5. 生产环境发布路径（daily 之外）。
6. 组织架构／上下级关系接口（任务分发要用）。

## 9. 两条方法论（值得刻在墙上）

- **"逻辑看起来对"不等于"实际生效"**（10.14 会话续接命中率 1/几十）：光看代码发现不了，必须翻真实运行日志统计命中率。
- **部署成功不等于服务起来了**（10.18）：`a1 faas deploy` 报 `healthStatus=SUCCESS`，进程却在 require 阶段就语法错误退出。必须去 `a1 faas logs` 确认看到干净的启动序列。

这两条和全局工作纪律里的"记忆和文档是快照不是现状，报状态前对 live 实测核实"完全一致，已进 AGENTS.md。
