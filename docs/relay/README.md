# 信箱规则（多 Agent 协作）

> 现在是单会话（老板 + 我），本机制**先立不用**。加角色时按这里执行，不临时发明。

## 为什么要信箱

多个 CLI/agent 并行时，口头转达会丢、会串。派活写进对方信箱文件，谁在处理、处理到哪一步都留痕，也不需要老板当人肉传话筒。

**铁律：不生成"发给 XX 的话术"让老板复制粘贴，直接写进对方 inbox。**

## 文件约定

- 每个角色一个信箱：`inbox-<角色>.md`（例：`inbox-impl.md`、`inbox-review.md`）。
- 只有信箱**所有者**可以改自己信箱的状态列；派活方只往里追加条目。
- 条目编号连续不复用，格式见下。

## 条目格式

```markdown
### R-001 <一句话说清要干什么>

- 派活方：<角色>
- 日期：2026-08-13
- 背景：为什么要做（一两句，附相关文档路径）
- 要求：具体做什么，验收判据是什么
- 边界：不许动哪些文件/哪些范围
- 状态：待处理 | 进行中 | 已完成(SHA/产出路径) | 有疑问(写清疑问)
```

## 处理规则

1. 自己的信箱有「待处理」条目，按编号顺序处理，**每条处理完立刻更新状态列**再做下一条。
2. 有疑问不猜：状态改「有疑问」并写清问题，回抛给派活方。
3. 完成后写明产出路径或 commit SHA，方便审计。
4. 派活方收到完成回执后**逐条审计**，✅/❌ 列清，不默认相信汇报。

## 角色边界

| 角色 | 可做 | 禁止 |
|---|---|---|
| root Codex | 计划、台账、集成、逐项审计和 Claude 交接 | 默认相信其他 Agent 汇报；覆盖他人脏工作树 |
| review-codex | 只读审查并回传文本 | 改共享文件、提交代码、冒充 Claude/arch 终审 |
| fe-codex | 只在独立 `codex/fe-vertical-slice` worktree 修改前端候选 | 触碰当前 `fe/f001`；改后端 Contract；宣称完整前端 |
| Claude/arch | 最终契约和架构复审 | 未实读文件即沿用临时 Agent 结论 |
| Claude/fe | 最终前端复审、保留/修改/重做 | 把临时 Codex 视觉当成已拍板正式皮肤 |
