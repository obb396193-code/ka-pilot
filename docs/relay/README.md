# 信箱规则（多 Agent 协作）

> 现在是单会话（老板 + 我），本机制**先立不用**。加角色时按这里执行，不临时发明。

## 为什么要信箱

多个 CLI/agent 并行时，口头转达会丢、会串。派活写进对方信箱文件，谁在处理、处理到哪一步都留痕，也不需要老板当人肉传话筒。

**铁律：不生成"发给 XX 的话术"让老板复制粘贴，直接写进对方 inbox。**

## 文件约定

- 每个角色一个信箱：`inbox-<角色>.md`（例：`inbox-impl.md`、`inbox-review.md`）。
- 只有信箱**所有者**可以改自己信箱的状态列；派活方只往里追加条目。
- 条目编号连续不复用，格式见下。

## 条目格式

```markdown
### R-001 <一句话说清要干什么>

- 派活方：<角色>
- 日期：2026-08-13
- 背景：为什么要做（一两句，附相关文档路径）
- 要求：具体做什么，验收判据是什么
- 边界：不许动哪些文件/哪些范围
- 状态：待处理 | 进行中 | 已完成(SHA/产出路径) | 有疑问(写清疑问)
```

## 处理规则

1. 自己的信箱有「待处理」条目，按编号顺序处理，**每条处理完立刻更新状态列**再做下一条。
2. 有疑问不猜：状态改「有疑问」并写清问题，回抛给派活方。
3. 完成后写明产出路径或 commit SHA，方便审计。
4. 派活方收到完成回执后**逐条审计**，✅/❌ 列清，不默认相信汇报。

## 角色边界

【等真的加角色时再定义】定义时必须写清：这个角色能改哪些目录、不能碰哪些目录。

## research/knowledge 角色注册提议（待 arch 审查，尚未生效）

> 提议日期：2026-08-20
> 提议方：KA 投放经营平台“资料研究与知识资产 Agent”

### 职责

- 接收内部、官方、竞品、开源和调研资料；
- 保存内部原文到 Git 私有区，登记机器索引；
- 区分来源事实、合理推断、宣传表达和未证实项；
- 评估对 PRD、架构、前端、Agent、工作流和知识库的影响；
- 提交 arch 审查，获批后进入产品知识库发布队列。

### 可修改范围

- `private/knowledge-sources/`（Git 永不跟踪）；
- `docs/knowledge/`；
- `scripts/validate-knowledge-catalog*`；
- 自己的 `docs/plans/*research-kb*`、相关设计/实施计划；
- 只追加工作台账和目标审查信箱条目。

### 禁止范围

- 不直接修改冻结 PRD、Contract；
- 不修改前端、后端生产代码；
- 不替 arch 把评估结论融合为正式产品口径；
- 不修改其他角色的职责和目录边界；
- 不存 Token、Cookie、AK/SK、PAT、Webhook Token、数据库密码等凭证值。

### 审查门

本角色可以把资料推进到 `review_pending`；只有 arch/指定审查 Agent 可以裁决 `reviewed/approved`。审查通过前，本节只是角色注册提议，不改变既有协作边界。
