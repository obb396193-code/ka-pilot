## 4. 两个技术解法（都不需要新权限）

### 4.1 定时任务：不用 ScheduerX，用进程内调度

OS 说定时能力走 `ScheduerX定时任务` 脚手架，但那是 `ginkgo-java8`（Java），而我们要 Node。

**不用绕这个弯**：我们的服务是**常驻容器**，不是冷启动函数——自建钉钉网关那条钉钉 Stream 长连接就是活证据（长连接要求进程一直在）。常驻进程里直接用 `node-cron`／`setInterval` 排定时任务即可，零额外申请。

**待实测的风险**：daily 环境会不会自动回收或休眠。若会，进程内定时会漏跑。验证方式——挂一个每 5 分钟写日志的任务跑一整天，翻 `a1 faas logs` 看有没有断点。（这正是网关踩坑 10.14 那条方法论：逻辑看起来对 ≠ 实际生效，必须翻真实日志。）

### 4.2 取数：异步 ETL 落自有库，产品只查自己的库

OS 确认 Multica issue 是"一问一答 + 轮询"，我原本判定这撑不住产品级批量。**但这个判断混淆了两件事：**

| | 交互式查询 | 批量 ETL |
|---|---|---|
| 用户在等 | 是，几十秒不可接受 | 否，夜里跑，几分钟无所谓 |
| 走 issue 轮询 | 不行 | **完全可以** |

**产品的实时性需求其实是"快速看到已经存下来的数据"，不是"实时穿透查媒体"。** 所以：

```
夜里/每小时：我方服务 → 建 issue @agent → agent 用它自己的合法权限调 skill 取原始数据
           → 回写评论 → 我方服务读取 → 落进我们自己的库
白天用户用： 前端 → 我方 API → 查我们自己的库（毫秒级）
```

三个好处：
1. **绕开延迟问题**：轮询慢无所谓，因为没人在等。
2. **口径计算在我方**（台账 #37 铁律）：只向 agent 要原始数据，指标、成本空间、Gap 全在我们的服务里算一遍，四角色同源。
3. **凭证边界干净**：我们不持有任何人的个人 token；agent 在沙箱里用它自己的合法凭证取数，我们只接收数据。

## 5. 合法性的分期模型（必须承认的边界）

第 3 节那个风险不能靠技术绕过去，只能分期承认：

| 阶段 | 用户范围 | 数据获取方式 | 合法性论证 |
|---|---|---|---|
| **一期** | 老板本人 + 身边少数同事 | 经 agent 取数，底层可能落在个人权限上 | **等于把本来就手工在做的取数自动化**——优化师本来每天就在导表看数，工具只是替他跑。个人权限用于个人工作范围，站得住 |
| **二期** | 部门级推广 | **必须换成应用身份的正规通路** | 一旦多人使用，"用某个人的权限给全部门取数"就不成立了。这是硬门槛，不是可选项 |

**这条要写进产品路线图，不能装看不见。** 一期做出实效正是为了拿去申请二期的正规权限——这也回到 01 文档的次序：先有东西，再谈权限。
