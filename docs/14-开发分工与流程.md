# 开发分工与流程 v1

> 建立：2026-08-17　状态：待老板拍板（后端归属 Codex/Claude 二选一）
> 蓝本：ContentRadar 四方协作模式（约 30 个会话验证过的打法），按本项目特点裁剪。

## 1. 角色分工

| 角色 | 谁 | 职责 | 文件边界 |
|---|---|---|---|
| **产品负责人** | 老板 | 拍板、业务口径、真实数据验证、**内网消息中转**（探针/部署包/回执） | 全部 |
| **arch 总架构+审查**（本会话） | Claude | 与老板对话定设计 → 出契约（DB schema/API 合同/类型）→ 派活写信箱 → 收 SHA 逐条验收审计 → 整合 main | `packages/contract/`、`docs/`；不写业务代码 |
| **后端** | **Codex（推荐，待拍板）** | ETL（get_data 拉数落库）、API、规则引擎、钉钉网关内置、Multica 托管对话 | `apps/api/`；按契约实现，不发明字段，不动前端 |
| **前端** | Claude 新开 CLI（cli-front） | 页面、图表、交互、视觉 | `apps/web/`；按契约 + mock 开发，视觉小样拍板后才 commit |
| **内网执行** | OS/Multica agent | a1 faas 部署 daily、内网实测、运维日志 | 不进仓库；经老板转发沟通 |

## 2. 后端归属：Codex vs Claude 对比（老板拍板）

| 维度 | Codex | Claude（新开 cli-b） |
|---|---|---|
| ContentRadar 先例 | 后端主力，磨合成熟 | cli-b 也做过后端，同样成熟 |
| 本项目上下文 | **已有**（写了 v0.4 讨论版+原型图） | 需从 arch 会话转移（成本低，文档全） |
| 口径/踩坑敏感度 | 需契约写死+验收把关 | 对 18 条踩坑和口径文档更熟 |
| 老板操作成本 | 现成工作流 | 要多开一个 Claude 会话 |

**arch 推荐：Codex 做后端。** 理由：①ContentRadar 验证过；②已有本项目上下文；③**Claude 名额留给前端**——前端是本产品核心差异化（数据报告+图表美观），Claude + taste 技能栈是我们最强的牌，好钢用在刀刃上；④口径重灾区（双口径/补洞/幂等）由 arch 写成契约级伪代码+测试用例交给 Codex，验收逐条审计兜底。

## 3. 前端从 ContentRadar 借鉴什么

**风格换掉，织法保留**：

| 层 | 借鉴内容 | 说明 |
|---|---|---|
| 工程模式 | Next.js + Tailwind + **mock 层先行**（`lib/api/mock.ts` 模式） | 前端不等后端，按契约 mock 开发；**整合放行前必用真 payload 打真端点 E2E**（Mock≠真API 教训） |
| UI 铁律 | ①子功能做页面顶部收敛 tab 不进侧栏 ②空态标「示例」角标+降饱和+写解锁条件 ③黑话→人话（界面不出现"接口/字段/契约"）④响应式只加不改 | ContentRadar 拍板级规则直接继承 |
| 组件织法 | 数据表格（筛选/排序/分页/状态 chip）、KPI 卡、详情抽屉、批量操作栏、确认弹层 | 模式复用，样式重写 |
| 拍板流程 | **视觉改动先出截图小样 → 老板批 → 才 commit；被否整颗回退不辩护** | 原样继承 |
| 视觉风格 | **不用 ContentRadar 风格，用 D-CON**（钉钉网关已验证的 Apple 风格：#ff6a2c 主色、四级灰阶、tabular-nums 数字右对齐、状态 chip、数值格式化规则、红负绿正） | 数据密集场景已验证好看，且和钉钉推送图视觉统一 |
| 图表 | **重点投入**：ECharts + dataviz 方法论（色板/形式启发/暗亮主题一致） | 图表是"数据报告要好看"的主战场，规格由 arch 出图表规范契约 |

## 4. 开发流程（契约先行，并行开发）

```
阶段0（当前）：八路审查回收 → 功能定稿 → 信息架构/页面清单 → D-CON 视觉小样拍板
阶段1：arch 出契约包 = DB schema + API 合同 + TS 类型 + 脱敏 mock 数据集 → 老板批
阶段2：并行开发
   Codex：ETL → 库表 → API → 规则引擎（按契约）
   cli-front：页面+图表（按契约用 mock）
   arch：批次验收（SHA 逐条 ✅/❌）+ 契约变更唯一出口
阶段3：联调 = mock 切真 API + E2E（真 payload 打真端点才放行）
阶段4：打包 → 老板转内网 agent → a1 faas deploy daily → 老板真实数据验收
循环：小步迭代，每个里程碑真部署验一次，不攒大批
```

## 5. 工程纪律（沿用 ContentRadar 铁律 + 本项目差异）

- **仓库**：GitHub 私有仓（外网协作中枢），monorepo：`apps/web` + `apps/api` + `packages/contract` + `docs`。
- **提交**：commit 前缀 `[fe|be|arch]`；各角色只动自己目录；**main 由 arch 整合**，fe/be 走分支。与 ContentRadar 不同点：本仓可以 push（GitHub 就是协作中枢），但 main 保护。
- **契约**：字段/端点谁都不发明，改契约走 arch；`packages/contract` 是唯一事实源。
- **信箱启用**：`docs/relay/inbox-be.md`、`inbox-fe.md`、`inbox-arch.md`（规则已在 README，现在生效）。派活直接写信箱，不生成话术让老板搬运。
- **验收**：交付方给 SHA，arch 逐条审计 ✅/❌ 列清；子 agent 只返回文本不动共享文件。
- **台账**：`docs/plans/工作台账.md` 继续唯一事实源。
- **内网交付**：阶段性 zip（或同步阿里 Code 仓）→ 内网 agent 部署；部署后必看 `a1 faas logs` 确认干净启动序列（deploy 成功≠服务起来）。
