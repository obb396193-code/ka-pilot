# KA Pilot 部署提示词（发给你的内网 OS / devix 类 agent，配合仓库地址一起发）

> 用法：把下面「提示词正文」整段复制给你的内网 agent，再把三样私密输入**私下**给它（不要贴进聊天记录）。
> 仓库：https://github.com/obb396193-code/ka-pilot （取 origin/main 最新）

---

## 提示词正文

你是内网部署 agent。目标：把仓库 https://github.com/obb396193-code/ka-pilot 部署成可用产品，让我登录后在「数据分析」页看到**本人**（个人空间 = 启航取数）和**团队**（团队空间 = ka-data）的真实数据。**数据分析页不允许出现任何合成/示例数据**；工作流、知识库等演示模块保留示例无所谓。仓库里 `scripts/seed-demo-data.py` 是本地假数据脚本，**禁止在这套部署上运行**。

### 输入
1. **我的启航 userId**：**先自己取**——内网 agent 的环境变量 `JULANG_OS_USER_IDENTITY`（OS 沙箱实证它与启航 userId 一致，`Cf` 开头 31 字符，正则 `^[A-Za-z0-9_:-]+$`）；没有这个变量就看 `~/.ka_secrets/qihang_userid` 或启航页面个人信息；都拿不到再问我。拿到后只落文件，聊天里只回「已取到，31 字符」。
2. **ka-data（团队数据源）地址与 reader token**：随本提示词一起发给你（见文末「ka-data 接入信息」，分发者填写）。用法：`KA_DATA_BASE_URL` 是 ka-data 的根地址（owner 沙箱会话地址，**重启会变**，变了就改 env 重启 data-api），`KA_DATA_READER_TOKEN` 是只读 token，一枚可见全团队账户。自检：`curl --cacert $NODE_EXTRA_CA_CERTS -H "Authorization: Bearer $KA_DATA_READER_TOKEN" -H 'Content-Type: application/json' -X POST "$KA_DATA_BASE_URL/api/query" -d '{"sql":"select count(*) from dwd_account_daily","backend":"sqlite"}'` 返回 200 且有 `rowCount` 即通。没拿到就先只做个人空间，团队页显「团队源未配置」。
3. **登录用户名（只能 ASCII）和密码（≥12 位）**：我私下给你；只落 Secret，聊天里只回「已设置」。

### 环境要求
- Node 20+（运行）；PostgreSQL 16（要 `pgcrypto`、`btree_gist`；`pg_trgm` 可选，缺了迁移自动降级）。
- 出网能到启航 `get_data` 与 ka-data；沙箱若有 mitm CA，把它和系统 CA 合并成一个 bundle：`cat /opt/mitm-ca/ca.crt /etc/ssl/certs/ca-certificates.crt > ~/.ka_secrets/combined-ca.crt`，三个 node 进程都带 `NODE_EXTRA_CA_CERTS=` 它。
- 内存 ≥1G 即可（web 用预编译产物，常驻约 150MB）。**不要用 `next dev`**。

### 步骤（照顺序做，每步回我一行 ✅/❌ + 证据）
0. **代码**：clone 到 origin/main 最新，记下 `git rev-parse --short HEAD`。仓库根 `npm install`（允许 postinstall）；自检 `ls apps/web/app/fonts/misans/misans.css` 存在。
1. **数据库**：建库 `ka_pilot`；`cd packages/db && DATABASE_URL=<dsn> npm run migrate`；自检 `select count(*) from pgmigrations` 必须等于 `ls packages/db/migrations/*.cjs | wc -l`（当前 20），不等就停下来报我。
2. **身份与空间**（`cd packages/db && npm run --silent seed:bootstrap -- '<JSON>'`，形状见 `docs/evidence/proposals/seed/bootstrap.example.json`）：1 个 identity（display_name 写我真名）、2 个 workspace（`personal` 与 `team`，名字写真名/团队名，**不要写「示例」「假数据」**）、2 条 membership（`role:"admin"`，`user_id` 自己生成 UUID 并**显式写进去**）。记下：personal workspace id、personal 的 user_id、team workspace id。
3. **绑定我的启航身份**：`npm run seed:qihang-identity -- '{"workspace_id":"<personal ws>","user_id":"<personal user_id>","qihang_user_id":"<我的启航 userId>"}'`（JSON 从文件读，不进 shell 历史）。返回 `status:"bound"` 或 `"unchanged"` 都算成功。
4. **登录凭证**：用 `docs/runbooks/2026-09-04-DataAPI内网部署与环境变量.md` 里「生成 scrypt 材料」那条 node 命令生成 `passwordSalt/passwordScrypt`，组成 `INTERNAL_TEST_AUTH_CREDENTIALS_JSON=[{"username","passwordSalt","passwordScrypt","identityId":<第 2 步 identity id>}]`，并设 `INTERNAL_TEST_AUTH_ENABLED=true`。
5. **账户发现与授权**：`cd apps/worker && QIHANG_BASE_URL=https://qh.alibaba-inc.com/qihang/api/rta_auto/tmp/get_data WORKER_SERVICE_QIHANG_USER_ID=<我的启航 userId> npm run --silent discover:accounts -- --media KUAISHOU` 得到账户清单（JSON）；把每个账户变成一条 grant `{"workspace_id":"<personal ws>","media":"KUAISHOU","account_id":"<account_id>","user_id":"<personal user_id>"}`，再跑一次 `seed:bootstrap`（幂等，只追加 grants）。我还有别的媒体（TENCENT 等）就各跑一次。回我账户数。
5b. **账户昵称清洗规则**（数据分析按优化师/资源位/目标/承接等昵称字段分组全靠它）：登录后用管理员会话把仓库里的规则装进去——`PUT /api/internal/admin/naming-rules?media=KUAISHOU`，请求体就是 `scripts/seed-naming-rule-kuaishou-v1.json` 的内容（腾讯用 `seed-naming-rule-tencent-v1.json`，`media=TENCENT`）；响应 `meta.dryRun.hitRate` 是命中率。装完等第 9 步抓数结束后 `POST /api/internal/admin/account-names/reparse {"media":"KUAISHOU"}`，再 `GET /api/internal/admin/account-names?media=KUAISHOU` 看 `parsed / failed` 数量，回我。命中率低说明这家团队的命名规范和默认规则不一样，我会在治理后台「归属清洗」页改规则。
6. **系数**：`npm run seed:coefficients`（需要我给的渠道系数与生效日；我没给就跳过，只影响现金成本换算，页面会显「缺系数」）。
7. **环境变量**（写进受控 env 文件，`chmod 600`）：
   - data-api / worker：`DATABASE_URL`、`QIHANG_BASE_URL`、`WORKER_SERVICE_QIHANG_USER_ID`、`DATA_API_HOST=127.0.0.1`、`DATA_API_PORT=3101`、`DATA_API_INTERNAL_TOKEN=<≥32 位随机>`、`INTERNAL_TEST_AUTH_ENABLED=true`、`INTERNAL_TEST_AUTH_CREDENTIALS_JSON`、`AUTH_SESSION_TTL_SECONDS=28800`、`WORKER_TRIGGER_TOKEN=<随机>`、`WORKER_HTTP_HOST=127.0.0.1`、`WORKER_HTTP_PORT=3102`、`NODE_EXTRA_CA_CERTS`。
   - 团队空间（拿到 ka-data 后再加）：`KA_DATA_ENABLED=true`、`KA_DATA_BASE_URL`、`KA_DATA_READER_TOKEN`、`KA_DATA_TEAM_WORKSPACE_ID=<team ws>`、`KA_DATA_ACCESS_MODE=internal_trial_shared_reader`。
   - web：`KA_DATA_BACKEND_ORIGIN=http://127.0.0.1:3101`、`KA_DATA_SERVICE_TOKEN=<与 DATA_API_INTERNAL_TOKEN 完全一致>`、`KA_READ_MODEL_DETAILS_ENABLED=true`、`NODE_EXTRA_CA_CERTS`。入口若是 http（非 https）则 web 与 data-api **两侧**都加 `AUTH_COOKIE_INSECURE=1`；https 不设。
8. **起后端**：`cd apps/worker && npm run start:data-api`（`curl 127.0.0.1:3101/healthz` → `{"ok":true}`）；`npm run start:worker-http`。
9. **首次抓数**：`WORKER_ONCE_WORKSPACE_ID=<personal ws> WORKER_ONCE_MEDIA=KUAISHOU npm run --silent worker:once`。回我 `etl_runs` 最新一行的 `status / rows_ingested / step_failed` 和 `select count(*), count(distinct account_id) from account_metrics_daily`。成功后挂 10 分钟循环：`curl -X POST -H "X-Worker-Trigger-Token: $TOK" http://127.0.0.1:3102/internal/worker/once`。失败就把 `error_summary` 原样贴我，**不要删 jobs 表里的任务**。
10. **起 web（预编译产物）**：`git fetch origin deploy/web-standalone && git worktree add ../ka-web-standalone origin/deploy/web-standalone`，`cat ../ka-web-standalone/SOURCE_SHA` 应等于第 0 步的 SHA（CI 在 main 变动后约 15 分钟更新；不等就等它或自己 `cd apps/web && npm run build`，需 ≥4G 内存）。启动：`cd ../ka-web-standalone && HOSTNAME=0.0.0.0 PORT=3000 node apps/web/server.js`（带 web env）。
11. **验收（必须真浏览器，Chrome/Edge ≥119 或夸克；不要 QQ 浏览器）**：登录 → 工作台「三步开工」里「绑定启航凭证」显已完成 → 进「数据分析」：大盘的消耗/转化/现金 CPA 是数字不是「−」；换窗口数字变；按优化师 / 资源位 / 业务维度能出分组（这两个维度来自昵称解析，5b 没做会全是「未归属」）；「维度透视」选账户 × 任务能出表；页脚「数据截至」是今天或昨天。右上角切到团队空间再看一遍（没配 ka-data 会显「团队源未配置」，这是预期）。接口抽查：`POST /api/internal/data-query {"queryId":"account.summary","params":{"dateFrom":"<T-7>","dateTo":"<T-1>"}}` 个人与团队各一次，`ok:true` 且 `rows[0].metrics.cost.value` 非 null。截两张图（个人/团队大盘）给我。

### 已知坑（不要重新踩，代码都已修，别手工改回去）
- 启航 `resource=account` **不传** accountIds（上游忽略该参数；766 个 id 会把 URL 撑过网关 8192 字节，回 HTML 拦截页）。
- ka-data 的 SQL 护栏拒绝 `replace()`，代码已改 `strftime`；`dwd_account_daily.ds` 是 TEXT。
- `KA_DATA_SERVICE_TOKEN` 漏配 → 登录 503；ENV 只在启动时读，改完必须重启。
- 迁移 022 缺 `pg_trgm` 时自动降级；精简版 PG 想装扩展要按 PG 源码版本编 contrib/pg_trgm。
- 页面上任何写着「示例」「假数据」的名字都来自 seed-demo-data.py，这套部署不该出现。

### 回执格式
每步一行 ✅/❌ + 证据；最后汇总：代码 SHA、`pgmigrations` 数、`etl_runs` 三列、`account_metrics_daily` 行数与账户数、`SOURCE_SHA`、两张截图。凭证与 token 一律不回传。

## 给分发者的说明（不用发给 agent）
- 这份提示词对应仓库 main ≥ `a2013be8`（2026-09-11，内网四个取数根因已修）。
- 绑定启航身份目前走第 3 步的命令；产品内自助绑定（设置页「凭证」）在后续版本开放，届时第 3 步改成登录后自己填。
- ka-data 地址与 reader token **不写进仓库**，发提示词时把文末「ka-data 接入信息」填上再发（或单独私发）；没有就只有个人空间有数。
- 多人共用一套部署：每加一个人重复第 2–5 步（identity + personal workspace + 启航绑定 + 授权），团队 workspace 共用。

## ka-data 接入信息（分发者发送前填写；不要提交进仓库）
```
KA_DATA_BASE_URL=<ka-data 根地址，形如 https://xxxx-sandbox-sessionxxxx-3000.agent.alibaba-inc.com>
KA_DATA_READER_TOKEN=<只读 token>
KA_DATA_ACCESS_MODE=internal_trial_shared_reader
说明：地址是 owner 沙箱会话地址，重启会变；token 一枚可见全团队账户，只读。
```
