## 2. 已证实的主链问题（先处理这些）

### A1 / P0：大盘、总表、透视、盯盘仍未真正消费业务查询

证据：`apps/web/components/business/data/tabs/overview-tab.tsx:30` 直接读 fixture；`table-tab.tsx:58`、`pivot-tab.tsx:35`、`hourly-tab.tsx:32` 同样直接读 fixture。`apps/web/lib/data/use-data-query.ts:13` 是全仓唯一 `useDataQuery(` 出现处，没有页面调用者。

影响：登录身份/空间可以切换，但页面数字仍不能证明来自那个人、那个空间、那个日期。后端有 API 与页面有数字，是两种不同证据。

验收：真实模式禁止回落 fixture；登录后实际请求、响应、图表、明细与同范围基准数能对应。缺数/断源应显缺数，不用示例填。

### A2 / P0：清洗页面存在“成功提示但没有持久化”的断路

证据：`apps/web/components/business/admin/naming-tab.tsx:52` 规则/账户来自 fixture；重解析、存规则、单条保存、批量确认、冲突选择多处仅 toast 或 setState。切 TENCENT 不会加载对应真实规则。

干跑也未闭环：该页 `:76` 把 media 放 URL，body 仅 sampleNames/separators；`apps/web/lib/data/r014/forwarder.ts:93` 与 `:107` 原样转 query/body；后端 `apps/worker/src/r014/naming-routes.ts:86` 却从 **body.media** 取媒体，缺失会 400。后端 draft 只传 separators 也不会替代完整规则。返回 hitRate 是 RatioValue，但前端 `lib/fixtures/naming.ts` 当 number、直接乘100。这里是静态逐跳证实，不冒称本轮已发真实认证 POST。

验收：选渠道→加载规则/本范围账户→改段/别名→干跑→保存→重解析→刷新再读到变化→分析页相同分类变化，全链同一规则版本。

### A3 / P0：部分指标标签、值和分析含义不相符

证据：`dashboard/kpi-rows.tsx:61` 将 costSpace 显为“激励花费”；这是成本空间，不是激励支出。`:62` 转化卡显示 conversion，`:63` CPA 分母为 realConversion，用户无法拿两卡直接复算。

建议：明确“回传转化 / 考核或真实转化 / 各自 CPA”；激励无源就 unsupported，不用成本空间代替。现金支出采用已验证的渠道折算规则，不用一个未经确认的“账面减激励”文案解释所有渠道。

### A4 / P0：窗口交互不能只让一部分数字动

main：`data-page.tsx:40,63` preset 未传入 OverviewTab。前端候选 a23f3b4f 已接窗口，但仍用 fixture 的日行重算部分 KPI：`overview-tab.tsx:45,63`；`kpi-rows.tsx:78–96` 部分现金/花费随窗口变化，BI/达标/部分环比仍取旧 summary；维度与钻取仍旧范围。windowed=null 时又回旧 summary（`:61,78`），与候选注释“区间没有数据则不顶旧值”冲突。

验收：日期/渠道/优化师/任务一变，KPI、图、维度、下钻、导出同范围；无数据的区间不能显示旧窗口整盘数。保留旧数据加载时必须标“正在更新/上次结果”，不能换新日期标题却挂旧值。

### A5 / P1：图表能切类型，不等于数据更新会重画

## 3. 清洗器是否适合真实运营脏数据

已有可复用基础：workspace+media 规则版本、enum/regex/free、分隔符、锚点、一个多值吸收段、未知段隔离、人工覆盖、原文和规则版本留存。方向对，**不是把所有渠道写成快手固定段位**。

但“认出字符串”与“得到可靠分析维度”还不是一回事。

### B1 / P1：空段后移，可错人却显示成功（实际执行）

合成规则：运营方(enum 自投，anchor) / 优化师(free) / 业务(free)。

| 输入 | 当前结果 | 应验收行为 |
|---|---|---|
| 自投-甲-任务A | parsed，甲/任务A | 正常 |
| 自投--任务A-备注 | **parsed，优化师=任务A，业务=备注** | 空优化师不得用下段顶替；待确认或字段缺失 |
| 自投-甲-任务A-多余片段 | parsed，同时 leftover 非空 | 非预期尾段显式提示；不得让 parsed 被理解为完全符合规范 |

根因：`packages/domain/src/r014/account-name-parse-contract.ts:165–167` 删除空 token；`:239` 仍按位置分段；free 可接受错误领域的任意字符串。锚点只能对齐锚点附近，不能修复锚点后任意漏段。

### B2 / P1：枚举允许多种写法，不等于归一为一个值（实际执行）

enum values=[IOS,iOS]，matchLongest=true：两条均匹配，但输出仍分别 IOS、iOS。`:173` 仅排序，`:185` 精确比较，`:208` 保留输入 bare 字符串。

建议：明确 `原值→标准值/标准ID`。同一人昵称/工号、同一任务缩写、同一设备大小写需要可维护的别名映射；并非所有看起来像的词都应合并。不要把用户 `owner`、账户名中的 optimizer、代理商当同一身份字段。

### B3 / P1：规则容错过宽可能覆盖字段（实际执行）

规则允许两个不同 order 的段使用相同 key=optimizer；`namingRuleSchema.safeParse` 返回成功；输入“甲-乙”最后只有 optimizer=乙，仍 parsed。规则发布至少应拒绝重复 key、冲突映射/锚点歧义；不可静默后者覆盖前者。

### B4 / P1：版本、生效日与历史归属没有统一闭环

`account-name-parse-repository.ts:172–179` 取最大 version，不按 effective_from 选；`:535–550` 账户列表维度拿当前规则解释旧解析/override。交互数据 evidence 则保留 rule_version/nameMatches。两条读路径不能只因都叫“昵称来源”就认为一致。

业务问题：账户上周归甲、本周交乙；改规则/改名后，看上周应按“当时归属”还是“当前负责人的账户回看”？需要显式口径；历史解析结果只有一份当前行不足以自动证明完整归属历史。改明日生效的规则也不应悄悄影响今天。

### B5 / P1：冲突机制已有，但重解析没有接实际对照事实

`apps/worker/src/r014/naming-routes.ts:192` 调 computeConflicts 时传 platform:{}、qihangTaskIds:[]。所以不能把“无 conflict”当“已经核对启航任务无冲突”。实际 task 查询使用有有效期的 task_accounts，而昵称括号 ID 只作校验；必须解释二者不同，不把解析 taskIds 自动当投放事实。

### B6：不要把不同渠道同名字段强行合并

快手“优选/联盟”等是账户业务标签；腾讯“联盟/朋友圈”和“自动/手动”是两个独立概念。最新腾讯候选已用 resource_position→placement、ad_slot 独立 analyzable，这个方向可保留。

应在字段字典展示：原段名、渠道含义、标准维度、来源、规则版本、是否可分析。昵称版位只是业务分类，**不能凭它声称查到了平台真实广告版位拆账**；真实版位分布必须有对应广告组/广告数据与映射证据。

### B7：命中率不等于准确率

main 既有34条测试通过不覆盖 B1–B3。main 可选段缺省仍计 partial 的问题已在 be2 候选修复，不能重复报“无人做”。仍需人工标注集测每字段准确率/误判率；尤其统计未归属账户数及其消耗占比，不能只算完整昵称百分比。

`dryRunAll :623` LIMIT5000，无 total/截断状态，超过阈值时不得宣称“全空间命中率”。需明确样本范围和完整性。无昵称账户也要单列，而不是从业务质量分母消失。

## 4. 从“展示维度”到“能作优化判断”还差什么

### C1 / 产品口径高风险：BI 按消耗分摊不能用于判断子级效率

假设两账户花费100/300，总BI40，按占比分为10/30，则两户的分摊 CPA 都是10。若现金折算比例相同，分摊现金CPA也必然相同；差异被算法抹平，不是实际效果相同。

arch v1.9.27 已要求分摊标记、完整子集、父BI缺失不分摊，这些是必要防护，但**仍不能消除上述分析限制**。建议分摊仅作估算归属/管理展示，与实测列分开；不得用于账户/版位效果排名、自动加减量、成本告警。没有该粒度的真实BI，就保留该粒度未知，或展示已有媒体转化及其明确口径。

### C2：分版位不能只有消耗占比

`dashboard/dimension-chart.tsx:24` 只使用 cost 画分布。它回答“钱花在哪里”，不回答“哪里跑得好”。默认配可排序表：量、真实/回传转化、现金CPA、考核达标、超成本、预算进度、样本量/完整性；可切“任务×版位”“优化师×任务”。不同任务考核价不同，不能用绝对CPA给优化师排好坏。

### C3：分任务必须保留任务身份与归属边界

主后台有任务有效期、同账户同日多任务歧义拒绝，属正确防重复计数机制（`semantic-query-dimension.ts:64`）。但界面需要给可处理原因，不是泛化“查数失败”。总表 `table-tab.tsx:28` 只显 tasks[0]，隐藏其它关系；任务名不能代替任务ID；同名任务、任务改名、账户转任务需测试。

### C4：优化师需要双向路径，不只固定树

默认“我的任务→账户”与团队“优化师→任务→账户”合理，还要能从异常版位反查受影响任务/人，以及从账户回到保留原筛选的汇总。主仓 `drilldown.tsx:42` 仅 depth=3 给账户链接，biz树账户在depth2无法点；`:46` 展开只绑行click，没有键盘按钮。至少按对象类型导航，非按树深度猜对象。

### C5：使用效率缺口，不宜被新增大模块掩盖

- 同一套筛选状态贯穿所有Tab、下钻、导出和AI上下文；URL可复现，返回保留。
- 清洗入口应能从“未归属”行/维度直达具体样例，而非强迫先去治理后台找账户。
- 透视 `pivot-tab.tsx:38,57` 设置pageSize50却隐藏分页；DataGrid启用分页模型。超过50组时存在后页不可达风险，需大列表真实渲染反例；不是当前几个fixture行能证明通过。
- 总表账户选择键 `accountId` 没带media，媒体选项固定快手；多渠道同号可能混淆（后端三键隔离不等于前端选项正确）。
- 保存视图现在只在内存，导出只toast（`table-tab.tsx:91–92`）；刷新/重进/导出文件都要验。
- 资源位分布将缺失值当0再丢弃（`:25`），需要缺失组/未归属提示，避免占比看似100%就被理解为数据齐全。
- “分析所选”只传条数不够，应带结构化对象集合、窗口、媒体、数据口径与requestId，不能让Agent重新猜范围。

## 5. 建议字段体系（待业务确认，不代替冻结Contract）

| 层 | 核心字段 | 用法/边界 |
|---|---|---|
| 身份与归属 | 媒体、账户ID/原名、任务ID/名、业务大类、优化师标准身份、代理/自投 | 跨渠道统一身份；原文保留；历史有效期明确 |
| 渠道特征 | 业务资源位、自动/手动投放、出价模式、设备、转化目标、RTA、扣量标记、承接、专项/实验标签 | 按渠道字典展示；有源才开放；未知段先待确认 |
| 量 | 账面/现金花费、预算与消耗进度、曝光/点击、回传转化、真实BI | 区分累计/小时增量，说明截至时间 |
| 效率 | 两套CPA、CTR/CVR、回传Gap、超成本/成本空间、分日生效考核价 | 比率先求和再相除；混合目标/考核价不盲目排名 |
| 可信度 | 来源、数据截至、缺失/待到/截断、规则版本、人工/昵称/平台标记、未归属消耗占比、实测或分摊 | 必须和指标一起可见，不能藏在开发日志 |

先为版位/优化师/任务各做默认视图，再开放自定义字段；不要让优化师第一次使用先学建BI报表。公共模板和个人保存视图都保留，不能以模板替代用户自定义。

## 6. 建议按八个真实业务场景验收

1. 昨日所有本人任务：同范围合计与原始源核对，明确实时/离线；缺一账户不能显示全量完整。
2. 某任务近7日按业务版位：行总和+未归属=总计；加优化师筛选后所有组件同步；下钻可复算。
3. 同名任务/同号跨媒体：绝不合成一个对象；空授权不回全盘。
4. 快手、腾讯各取人工标注样本：规范/旧命名/缺段/空段/别名/带括号/多任务/未知段/改名/人工覆盖分别验证；不直接暴露真实样本到仓库。
5. 改错归属：从分析未归属行进入清洗，预览影响账户数和消耗，保存刷新后生效，既有人工结论和历史口径可解释。
6. 今日15点对昨日同截止时点：实际同步覆盖一致；不能拿今日半日比昨日全天当跑量暴跌；最小转化样本门槛明确。
7. BI迟到、部分账户失败、只有账面数：不补0、不假分摊、不判达标；恢复后数据及警告正确更新。
8. 保存/导出/返回/AI：窗口、渠道、筛选、排序、列、数据版本一致；导出真文件；展开错误/超50组/键盘操作都可用。

**业务接受门**：不仅test绿，还需有“原始源→规范化字段→聚合→HTTP响应→实际页面→导出”的同范围证据；每个层级可回答“为何这一行被算进来”。在此之前，不把图表精美或fixture数字自洽当作业务完成。
