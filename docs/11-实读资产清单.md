## 1. 三条 API 通道（从文件原文确认）

| 通道 | 域名 | 鉴权方式 | 谁在用 | 我们能不能直接调 |
|---|---|---|---|---|
| **启航 get_data** | `qh.alibaba-inc.com/qihang/api/rta_auto/tmp/get_data` | userId query 参数（裸，无 token） | ks-data-queryer / rta-data-queryer | **能**，只要出网 + userId（沙箱外无出网实测过） |
| **私有数仓（DataWorks）** | `private-dataservice-api.dw.alibaba-inc.com` | appCode（`E1A16AACB57E4B07BD3532FC1CAA7330`） | qihang-cli `account list-by-user` | **★能**（appCode 是硬编码公开值，不绑定个人身份，09 报告标"查不到"的那条在这里有答案） |
| **快手 MAPI** | `open.kuaishou-adt.com`（BASE_URL） | Access-Token（由 MITM 代理注入，CLI 里写的是 `<token>` 占位符） | kuaishou-cli | **不能**——占位符，真实 token 在沙箱 MITM 里，出不来 |

## 2. ★关键发现：qihang-cli `account list-by-user` 是无 token 的账户归属直连

`account.py` 源码确认：
- 请求 `GET https://private-dataservice-api.dw.alibaba-inc.com/ds-tb-erfangyinliu/project/23017/account`
- 鉴权参数：`appCode=E1A16AACB57E4B07BD3532FC1CAA7330`（硬编码）+ `userId` + `media=KUAISHOU`
- 返回：指定 userId 在指定媒体下有权限的 `accountId / adSpace` 列表
- **不绑定个人身份**——appCode 是服务级凭证，不是个人 token

**这意味着"谁管哪些账户"（数据可见范围）的查法，存在一条不依赖任何个人 token 的路径。** 这是本次实读最重要的发现之一。

## 3. ★kuaishou-cli 确认：出不来的不只是 token

`client.py` 源码确认：

```python
TOKEN_PLACEHOLDER = "<token>"  # config.py

# client.py headers()
token = self.config.access_token or TOKEN_PLACEHOLDER
return {
    "Access-Token": token,      # 写入固定占位符
    "Authorization": token,     # 同一个占位符
    ...
}
```

代码原文写得明白：**CLI 不获取 token、不落地 token、token 是占位符**，真实 token 由沙箱内 MITM 代理在 HTTP 发送前替换。`BASE_URL = "https://open.kuaishou-adt.com"`，是公网快手开放平台，但没有真实 token 就是废的。**02 文档"kuaishou-cli 能不能拷出沙箱用"的答案是：代码能拷，token 拷不出来。**

## 5. 两份 analyze（insights.py）里的指标口径（代码确认）

| 派生指标 | 公式 | 用的字段 |
|---|---|---|
| ctr | 点击/曝光 | `account_click/account_exposure` 或 `ad_click_h/ad_exposure_h` |
| cvr | 转化/点击 | `account_conversion/account_click` 或 `ad_conversion_h/ad_click_h` |
| **cpa（真实成本）** | **消耗/真实转化** | `account_cost/account_real_conversion` |
| account-trend | 按日汇总+环比 | `_dod = pct_change()`，字段含消耗/曝光/点击/转化/ctr/cvr/cpa |
| ad-anomaly | 异常筛查 | 规则1：真实转化=0 且消耗≥min_cost；规则2：real_cpa > target_cpa |
| top-ads | Top N | 按任意列排序取前 N |

## 6. 两个必须知道的工程细节

**① `load_account_data.py` 的补洞逻辑**：历史日优先走离线口径，**当日走实时口径**；如果某日离线无行，自动用实时补（`_gap_filled_by_realtime`）。这个设计直接决定了我们的 ETL 必须保留 `_data_source` 字段来标记数据来源，否则同一个指标会出现两个口径而不自知。

**② 离线口径的转化字段缺失**：insights.py 原文写得很清楚："纯离线账户数据无转化字段，故 cvr/cpa 不可用"。需要转化/真实成本趋势必须用实时口径。**这决定了 ETL 不能只跑离线，必须同时拉实时口径的账户数据，两份拼起来才能完整。**

## 7. 对之前架构的直接修正

| 旧认知 | 修正 |
|---|---|
| "账户归属只能人工维护映射表" | **qihang-cli 有现成 API 可查**（private-dataservice，appCode 硬编码，无个人 token） |
| "FBI/DataWorks 无应用身份通路" | **DataWorks 私有数仓这条路存在且有 appCode**（但只是账户归属，不是 BI 转化数据，BI 仍无着落） |
| "启航接口是唯一数据源" | 有两套：启航 get_data（消耗/转化/成本）+ private-dataservice（账户归属） |
| "os 报告说 mcn_ PAT 是长期凭证" | **代码里看不到任何 mcn_ 相关内容**——不依赖它，当前两条直连通道（get_data + private-dataservice）都不需要它 |

## 8. 架构含义

```
【我们的 FaaS 服务】
  │
  ├─ get_data（qh.alibaba-inc.com）
  │   消耗/转化/成本/预算/考核价 → 落自有库
  │   鉴权：userId 参数（需实测：FaaS 能不能访问此域名）
  │
  ├─ private-dataservice-api（账户归属）
  │   "userId + media → 该用户有权看哪些账户" → 用于数据可见范围
  │   鉴权：appCode 硬编码（无需个人 token）
  │   需实测：同样要能访问 dw.alibaba-inc.com 域名
  │
  └─ 指标计算、诊断规则、工作项管理、四角色视图
      全在我们自己的 Node 服务里
      （insights.py 的分析逻辑可直接移植，不依赖任何外部服务）
```

**结论：两块最硬的骨头（账户归属 + 数据可见范围）有现成 API，且都不需要个人 token。** 唯一要验证的是技术层：FaaS 能不能出网到这两个域名。一旦通了，产品就独立了——不依赖 agent 取数。
