## 一、SIT标准流程简介

SIT是系统集成测试（System Integrate Test）的简称，即当一个大项目在所有业务侧内部测试通过之后，拉通上下游进行全链路测试。与标准的业务测试不同，SIT更多关注业务全链路每个节点的重要细节，比如入口的透出、标记展示、Icon、入口文案等，以及上下游之间的调度和跳转关系，比如从上游入口进入落地页再到下单流程的一步步跳转以及参数传递是否正确。简单来讲，SIT更贴近用户使用流程，与用户体验和探索性测试有所类似，但技术关注上会更细一些。

SIT主要可以分为三大部分，准入前的测试准备，预发测试验证，线上验证及巡检：

![](https://intranetproxy.alipay.com/skylark/lark/0/2023/png/159530/1686037673272-a972fd9b-423d-49a6-b5d8-618c8ab16ce2.png "")

SIT要求对应的测试负责人需要有强大的学习能力去熟悉掌握全链路所有业务域的改动点，能了解每个业务的方案、数据、页面改动和上下游的调用关系。同时还需要足够的耐心和沟通推动能力，在整个测试过程中会非常频繁得需要跟各业务域的技术、产品负责人打交道，推送问题解决。

## 二、项目SIT前期准备

在SIT开始之前，有很多事情是要先准备好，才能保障SIT开始后能稳定有序的向前推进，包括SIT测试时需要的数据，SIT的项目排期，SIT链路的上下游交互方案和各业务域的产品文档/UED文档等。

### 1、测试数据和测试环境

测试数据，面向项目所有需要上线的国家，需准备数据如下：
- 买家测试账号，包括各个国家可支付下单的带资金账号；
- 测试商品，需覆盖所有需要测试的商品类型，如Choice和Global hit商品，bundle商品等。如涉及履约，还需要配置可履约的测试商品；
- 可供测试商品报名的活动；
- 可供查询商品和活动详细内容的FBI报表

对测试环境来说，需要的是各业务在约定时间内使预发同一套环境达到相对稳定状态，如果多个业务部署在不同的环境分支上，将无法达到SIT的效果。尽量避免过多的调试和部署造成的测试阻塞，包括前端的页面功能稳定及服务端的服务稳定，根据业务测试链路，通常包括：
- 首页、ELP、搜索、订单详情等入口业务的环境
- TPP、Summary等推荐算法环境
- Landing page、频道、交易、PDP等主要业务

### 2、项目排期

| 分类 | 需确定的内容 | 备注 |
|------|------------------|------|
| 待SIT项目的整体排期 | <ul><li>SIT的测试周期有多少天，根据项目的大小和涉及的国家，通常需要3-7天；</li><br><li>项目的交付deadline，以及项目下一步交付Action开始的具体时间，避免在SIT过程产生阻塞问题时，无法评估整体项目的delay风险；</li></ul> |  |
| 业务域的交付排期 | <ul><li>SIT涉及的全链路上的业务域，什么时间可以完成域内的业务case的测试；</li><br><li>业务域内测试完成时，是否有包含了单层上下游调用的测试，是否通过；</li></ul> |  |
| 多语言翻译 | <ul><li>多语言翻译的产品/运营接口人；</li><br><li>业务域提供美杜莎Key的时间</li><br><li>国家完成所有多语言翻译的时间</li></ul> | 多语言的翻译完成时间，通常对业务域来说，是需要在适配测试前提供（如果需要适配）。<br>对SIT来说，至少需要在SIT结束时间提前2天，给SIT留足做最后检查补齐的时间。 |

### 3、各业务产研测责任人

由于SIT是一个贯穿全链路的测试，涉及的业务过多，需要提前跟所有业务确认好各业务的产品、前后端研发、UED、测试负责人，避免在SIT过程中发现问题无法及时推动解决，造成阻塞。对SIT的执行者来说，SIT不是一个单纯的测试，需要非常多的沟通推动能力贯穿整个测试过程。

### 4、SIT调用链路的上下游产品/交互方案

对SIT的执行者来说，这是整个过程中比较有挑战性的点之一。SIT需要能至少了解整个项目从顶层入口到下游下单整个链路是如何运作的，包括中间涉及到的每个业务的改动点、需关注的业务重点，以及业务间的交互等等。

| 方案 | 关注内容 | 举个🌰栗子 |
|------|------------|----------------|
| 各业务域的产品改动方案 | <ul><li>需关注每个业务内改动的重点</li><br><li>需关注每个业务内所关注的重点功能、模块，知晓他们是如何运作的以及业务的预期结果</li></ul> | 如：购物车是否区分主购与mini cart，两者计数是否相通；<br>又如：业务预期进入从不同的入口进入Landing page展示的模块和商品是什么样子的。 |
| 复杂业务内的上下游技术方案 | <ul><li>商品数据的来源</li><br><li>活动数据的来源</li><br><li>推荐商品的逻辑</li><br><li>上游入口进入下游页面需要带什么参数，参数来源是上游拼接还是从哪个下游获取</li><br><li>当某个页面模块报错时，需要找的对应业务是当前业务域还是哪个下游的业务。</li></ul> | 如：NNLP的活动排期数据来源与PDP页面的活动数据来源就不一样，这些不同页面的数据可能来源于不同的数据表；<br>如：首页的choice模块，more链接是首页配置的，商品数据却来源于TPP。<br>如：从首页、搜索入口等进入NNLP，需要带的promotionId、configId、itemsId等参数的名称和内容。 |

## 三、预发环境SIT准入条件

| 准入项 | 优先级 | 准入标准 |
|---------|---------|------------|
| 预发环境所有上游入口 | 高 | <ul><li>入口已配置透出</li><br><li>入口配置的链接、参数符合下游页面要求</li></ul> |
| 预发环境业务域内测试 | 高 | <ul><li>业务域内已完成测试，无阻塞性问题待解决</li><br><li>业务上下游交互方案已达成一致，无方案Gap</li></ul> |
| 预发环境活动排期 | 高 | <ul><li>预发环境所有待验证活动类型均有活动透出</li></ul> |
| 预发环境商品 | 高 | <ul><li>预发环境待验证商品类型均有测试商品可用</li><br><li>如涉及履约，有可履约的测试商品</li></ul> |
| 预发环境上下游数据 | 高 | <ul><li>推荐商品有可推送到上游业务的商品数据</li><br><li>营销活动排期可推送到上游各业务</li></ul> |
| 所有涉及国家的环境部署 | 中 | <ul><li>至少有一个国家所有业务环境已部署，可测试</li><br><li>其他国家环境如涉及Summary，需在SIT开始前确认预发部署排期。</li></ul> |
| 多语言翻译 | 中 | <ul><li>需要在SIT开始前确认所有多语言翻译完成时间</li></ul> |

## 五、业务响应标准

| 问题分类 | 响应人 | 响应标准 |
|------------|---------|------------|
| 阻塞性环境问题 | 业务QA | 5min 内业务QA响应；<br>30min内推动业务开发恢复环境； |
| 主流程阻塞性代码问题 | 业务QA | 5min 内业务QA响应；<br>30min内推动开发给出风险评估，修复时间，作为最高优先级问题跟进；<br>1 hour内解决问题发布预发； |
| 非主流程阻塞性问题 | 业务QA | 5min 内业务QA响应；<br>30min内推动开发给出风险评估，修复时间，作为最高优先级问题跟进；<br>0.5D 内修复问题； |
| 非阻塞性代码问题 | 业务QA | 业务QA名下bug日清，将bug转给对应的开发或将非问题关闭，将修复了的问题回归关闭； |
| 业务实现与产品描述不一致问题 | 业务QA/开发/产品 | 业务QA/开发/产品 30min内响应拉通会议，10min内对齐理解Gap、评估修复时间（如需修复）。 |
| 文案翻译问题 | 产品/运营接口人 | 翻译问题日清，或给出具体的修复时间 |

## 九、用户Feedback监控

线上发布之后，需要配置对应的Feedback规则和接收feedback通知的群机器人，用于接收线上的用户反馈。

对于反馈内容，需要每天清理所有未处理的用户反馈，将有效反馈转为Aone ticket，提给对应的QA/研发/产品负责人跟进解决。
