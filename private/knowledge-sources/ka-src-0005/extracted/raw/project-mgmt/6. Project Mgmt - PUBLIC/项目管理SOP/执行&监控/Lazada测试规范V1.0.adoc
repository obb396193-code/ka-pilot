### 1，Lazada需求生命周期介绍

#### 1.1 通用需求生命周期介绍

Lazada的需求可能会涉及到业务、产品、研发和测试，在不同的需求阶段，每个角色有明确的分工，下面对各个关键节点加以解释。

![](https://intranetproxy.alipay.com/skylark/lark/0/2022/png/21256432/1657007441617-ac519c18-bb20-4a99-9a09-17042f3362b4.png "")
- **需求提出**

  事实上，需求提出可能是业务，也有可能是产品或者研发。但是一些较大的业务项目往往由业务提出，比如Arise项目等。PD可以从产品设计或者用户体验出发，提出需求，而研发也可以提出一些技术改造的需求。
- **BRD Sign Off**

如果需求是业务提出，则需要业务输出BRD，BRD会系统的论证需求的业务背景、业务价值以及当前的机会点等，经过多轮的Review之后，确定最终的BRD。
- **PRD Sign Off**

在BRD Sign Off之后，紧接着PD就需要把BRD的业务计划拆分成具体的产品方案，这个阶段需要多轮的PRD Review。Review的过程中，研发和测试必须参加，以保证产品方案在技术上是可行的，需求能够顺利交付。
- **研发提测**

在PRD Sign Off之后，研发就需要设计技术方案，然后是编码的工作，其中技术方案也需要进行Review，以尽可能早的暴露风险。

测试在这个阶段可以根据PRD设计测试策略和测试用例。同时需要参与到技术方案评审中，从可测性、资损等角度评估技术方案的风险。
- **SIT**

SIT阶段主要是测试同学的时间，用来执行功能测试，接口测试，E2E测试等，在这个阶段尽可能通过全面完善的测试发现产品的缺陷，同时我们也需要通过技术手段，提升测试的效率，以减少测试的独占时间。
- **UAT**

UAT主要是业务来验收交付的需求是否符合预期，这个阶段可能需要测试或者其它角色帮助业务创建UAT的基础数据，比如账号，商品等，如果需求是技改需求，可能没有UAT阶段。
- **灰度验证**

所有上线的需求一定要经过灰度验证，需要研发在技术方案设计阶段设计并实现较为完善的灰度方案，遵循灰度的一些基本规范。研发在该阶段还要做好发布规范和线上监控完善，QA在该阶段需要进行发布后的测试验证，以保证发布上线的功能是符合预期的。
- **全量上线**

如果是业务需求，在灰度之后，业务或者PD可能会收集线上的运行数据，以分析是否要继续全量发布。如果是技改需求，灰度阶段没问题，就可以全量发布了。

#### 1.2 Lazada App版本发布流程介绍

APP的需求和发布流程有一些特殊的点，因为APP不像后台系统可以快速的发布或者回滚，在测试通过之后，最终还需要提交应用商店审核，下图介绍一下APP的发版的流程。

![](https://intranetproxy.alipay.com/skylark/lark/0/2022/png/159530/1657792906040-95de2653-e196-487c-ac0f-214a8ef356b5.png "")

其中客户端测试流程主要分为三大部分：业务模块测试、集成单测试、发布单测试：

**业务模块测试：**主要进行新需求的功能测试、兼容性适配测试，根据业务需要选择是否进行性能测试、稳定性Monkey测试。

**集成单测试：**集成单测试主要对增量功能进行回归，以及涉及到的旧流程回归和周边业务回归。

**发布单测试**：发布单测试区分灰度版本和正式版本。灰度版本只对改动了的业务做P0 case回归。正式版本针对所有业务做P0/P1 case回归，同时所有增量的业务功能都需要做回归。

### 2，需求评审【需求评审checklist】

本文主要是面向测试同学，所以直接从测试参与的第一个阶段-需求评审开始。在需求评审阶段，需要达成4个目的。
- 搞清楚需求的背景和逻辑，对需求的业务逻辑、各种异常情况等提出建议
- 审核PRD是否规范，约定好的内容是否有遗漏，比如结算业务如果需要PD在PRD中明确标注需求的资损风险，如果PRD没有标注，则可以要求PD补充
- 根据需求的复杂度，评估测试时间
- 需求拆分是否合理，根据敏捷迭代的原则，每个需求拆分需要合理以便能快速交付。Lazada建议需求的交付时间不超过18天，需求的研发时常控制在11天。

![](https://intranetproxy.alipay.com/skylark/lark/0/2022/png/21256432/1657783447179-846fde77-7170-413b-9530-d2187becb0fe.png "")

| <span style="background-color: #ADC6FF;">​</span> | <span style="background-color: #ADC6FF;">通用检查项</span> |
|---------------------------------------------------|---------------------------------------------------------------|
| 1 | 需求逻辑设计是否合理<br><ul><li>上下游一致性</li><br><li>异常情况处理</li><br><li>UED是否规范</li></ul> |
| 2 | PRD是否规范 |
| 3 | 需求拆分是否符合敏捷原则 |
| 4 | 评估测试时间是否有风险 |
| <span style="background-color: #ADC6FF;">​</span> | <span style="background-color: #ADC6FF;">客户端检查项</span> |
| 1 | 当前架构能力是否支持需求逻辑 |

| 4 | 需求是否涉及服务端的交互 |

在需求评审结束之后，测试同学可以继续提前做一些事情：
- 测试分析：<span style="color: rgba(25, 26, 31, 0.9);">从资源、业务要求角度设计测试完成所需计划。明确测试范围，测试目标，测试重点和难点，测试深度和广度，如何安排测试工作节奏，测试如何分层等</span>
- <span style="color: rgba(25, 26, 31, 0.9);">监控梳理：从业务需求梳理业务监控点和风险点</span>

关于测试排期，我们建议：**每个需求或者每个版本，测试独占时间不超过开发独占时间的50%**，更多排期指导参考[敏捷研发中的测试排期](https://yuque.antfin-inc.com/lazadaqa/wugtyd/qrkpct)

#### 4.3 测试用例设计

**4.3.1 测试用例评审 【要求】**

测试用例评审主讲人是测试同学，参与人员包括产品、设计师、前后端开发，有需要的话还可以包含关联方的开发与测试同学。

测试用例评审是对齐需求理解的必要步骤，也可以根据相关同学的反馈，进一步完善测试用例，保障测试用例更充分。做好测试用例评审，可以参考以下注意事项：
- 根据文档（包括PRD、UED、前后端技术方案），输出对应的用例场景，
- 对测试用例的优先级进行区分
- 明确冒烟测试用例，要求研发必须通过冒烟才能提测
- 根据测试用例评审的反馈，继续完善测试用例

从分层测试的角度看，微服务的测试可以分为单元测试、接口测试、链路测试、E2E测试，测试时间是依次增加，测试成本也是依次增加，测试范围由小到大。

其中单元测试更多需要开发在写代码时写对应的单测用例，测试同学在提测时要求开发的单元测试覆盖率等。接口测试是对单应用进行接口测试，是服务端常用的测试手段，有比较高的ROI，推荐大家多使用接口测试。链路是针对几个应用进行测试，比如结算链路，可以覆盖从收单、拆单、结算这个流程。从而保证本业务域的逻辑正确。E2E测试是站在用户的视角进行测试验收，更接近用户真实的用户体验，但是自动化难度较大，测试成本较高。

#### 6.5 Aone和缺陷管理流程  <span style="color: #1E90FF;">@骞轩</span>

[Aone](https://aone.alibaba-inc.com/)是Alibaba的一站式研发平台，用来管理需求，应用的CI/CD以及缺陷的管理。关于Aone的的介绍可以参考Aone的[帮助文档](https://yuque.antfin-inc.com/aone/platform)，下面重点介绍一下缺陷状态管理的一些规范。缺陷的状态精简一下分为三类：待处理、已处理、已关闭。为了细化区分这三大类，人为地增加了状态。状态其实应该是这样的一个级联分类：

待处理：New、Open、Reopen已处理：Fixed，Wont'fix，Later，Worksforme，Duplicate，Invalid，External，ByDesign已关闭：Closed已处理中的8个状态都可以视为问题处理人对此问题的处理意见。我们暂且叫它为：解决方案。

​

**bug各种状态定义**

| <span style="background-color: #81BBF8;">分类</span> | <span style="background-color: #81BBF8;">bug状态</span> | <span style="background-color: #81BBF8;">说明</span> |
|------------------------------------------------------|---------------------------------------------------------|------------------------------------------------------|
| 待解决 | New | 新创建的bug |
|  | Reopen | 已解决的问题未能通过验证或解决方案不合理。<br>如：fixed的bug验证发现依然存在。Bydesign bug的处理不合理 |
|  | Open | N/A，这个状态较为少用，一般使用reopen来代替 |
| 已解决 | Fixed | bug已修复 |
|  | Won'tfix | 有些情况一些特殊的bug影响很小，经过评审，可以不需要修复 |
|  | Later | 该bug在本开发阶段中不会被解决，经过评审，可后续后续修复 |
|  | Worksforme | 偶现问题无法复现 |
|  | Duplicate | 重复bug |
|  | Invalid | 该bug是一个无效的bug |
|  | External | 问题依赖于外部条件，如：android个别适配手机问题，其他二方库的问题等 |
|  | ByDesign | 产品功能设计如此 |
| 关闭 | Close | bug关闭 |



**有效BUG的定义**
- 解决方案为 Duplicate、Invalid、ByDesign的BUG是无效BUG，其余情况均为有效BUG（New、Open、Reopen、Fixed、Wont'fix、Later，Worksforme、External）
- 如果一个BUG被Reopen多次，则以最后一次的解决方案来判断是否是有效bug



**缺陷管理规范**
- 所有缺陷最终都应该由缺陷验证者或者与之平级权限的人变更到Closed状态。非Closed状态的都被认为是活动的缺陷。
- 解决者可以将“待处理”状态的缺陷置为任意“已处理”状态。



状态流转图如下图：![](https://intranetproxy.alipay.com/skylark/lark/0/2022/png/10852/1657176171047-63246ea3-1cbe-45b1-aa0f-c05b8ebc7f7a.png "")

Later、won't fix、by design这三个状态的切换，从产品功能及设计完整性层面考虑，仅允许PD/UED进行切换，其他角色无该权限操作

### 7，发布&变更     <span style="color: #1E90FF;">@骞轩</span>

发布变更遵守[集团通用变更红线](https://tr.alibaba-inc.com/portal/article/lzozlw/fzg6dy/do9umw),在此基础上根据各个业务需要可以灵活增加。核心的内容如下：

#### 7.1 变更红线&注意事项 【checklist】 
- <span style="color: #262626;">禁止一切未通过变更管理平台申请或报备的变更操作，紧急故障处理，可事后补填申请</span>
- <span style="color: #262626;">禁止封网期、非变更窗口期进行除紧急变更外的变更</span>
- <span style="color: #262626;">禁止未经测试验证、未经预发、未经灰度的线上变更</span>
- <span style="color: #262626;">禁止无影响面说明、操作步骤、验证方案、应急预案的变更。应急预案（如回滚方案）必须具备可操作性。</span>
- <span style="color: #262626;">禁止一切与变更方案计划内容、线上问题排查无关的生产环境变更操作</span>
- <span style="color: #262626;">禁止对数据弄虚作假，不允许非正常业务流程的修改，所有的业务数据都必须真实、一致，对数据的不真实性0容忍</span>

<span style="color: #262626;">​</span>

<span style="color: #262626;">其中灰度执行要求（紧急变更除外）如下：</span>

<span style="color: #262626;">a，分批次要求</span><span style="color: #262626;">\- 安全生产</span>环境（SPE）已覆盖所在BU和系统，则必须先在SPE内进行发布，此环境针对发布批次无要求；只有在SPE验证无问题后，才能在线上生产环境进行灰度发布。 \- 生产环境发布批次至少分2批，如有生产环境一批次发布（特殊报备除外），变更执行人和变更系统工具同时触发变更红线，承担同等责任

b，时间间隔要求

一般变更：SPE环境及前2个线上生产环境批次，每个批次变更后观察时间应大于5分钟。

重大变更：SPE环境及前2个线上生产环境批次，每个批次变更后观察时间应大于20分钟，观察指标必须包括1个关键业务指标（推荐的关键业务指标：含可用率定义的业务、接入GOC P1P2故障等级定义的业务监控等）。

高危变更：第1批(若有SPE环境的，SPE环境发布即为第<span style="color: #262626;">1批，若无SPE环境的，即指生产环境第1批)发布完后至少观测60分钟；第1批发布后的前2个线上生产环境批次，每个批次至少观察20分钟。观察指标要求和重大变更相同。</span>

### 8，线上运营质量

线上运营质量是测试“右移”的重要体现，运营质量一般体现在以下几方面：
- 线上系统监控大盘，比如机器水位监控，业务成功率监控
- 用户的反馈
- 工单

#### 8.1 线上系统监控

绝大多数的线上系统监控使用[sunfire监控](https://x.alibaba-inc.com/home/)，可以找对应的负责人要到系统监控的地址，关注线上监控。

也有些业务监控使用的[鹰眼](https://eagleeye-console.alibaba-inc.com/)，相关平台的介绍可以参考平台的说明文档。

#### 8.2 用户反馈

Lazada的用户有多种渠道反馈遇到问题，比如App Store或者通过Lazada App的feedback功能，Lazada QA部门的[UXQA](https://lzdmobile.alibaba-inc.com/#/feedback/list)平台管理了不同渠道的用户反馈，可以对用户的反馈打标，跟进处理等一系列功能。

平台参考文档：

[UXQA平台介绍](https://yuque.antfin.com/lazadaqa/lwc2ab/retauz)

[Lazada App智能舆情平台——Feedback](https://ata.alibaba-inc.com/articles/203338?spm=ata.23639746.0.0.766b3744ow7Wac)

feedback是QA同学了解用户使用习惯的重要渠道，**只有真正的了解用户使用习惯，才能站在用户的视角来保障系统的质量**，因此QA有责任了解并跟进处理相关的feedback，我们给处理feedback的参考建议。

（1）客服处理第一轮，确认feedback是疑似软件缺陷，是吐槽，是产品新需求，是答疑，还是运营问题？

（2）开发和测试（有一个代表即可）针对疑似缺陷快速处理第二轮，判断是否有效缺陷

（3）如果是有效缺陷，开发给出解决计划，测试验证以及给出漏测改进措施

![](https://intranetproxy.alipay.com/skylark/lark/0/2022/png/21256432/1657871863773-a00075ef-7447-4115-8a8c-9e268e4a61b0.png "")

#### 8.3 工单

工单一般是由运营等其他公司同事提的ticket，一般是线上的紧急问题或者用户无法解决的问题，工单的时效性更强，需要在一定时间内及时处理。

工单首先会由911团队来接手，如果无法处理需要研发协助，则会转给技术同学，研发或者QA同学都可以直接处理工单，比如广告团队，就优先由QA团队接手并处理，如下图所示。
