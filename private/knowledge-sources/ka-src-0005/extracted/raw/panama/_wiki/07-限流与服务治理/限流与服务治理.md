# 限流与服务治理

## 概述

本页汇总巴拿马跨境分销（淘系海外 OVS 供给侧）在**服务治理与稳定性工程**上的核心建设，围绕四条主线：

1. **多维度限流**：以 `ovs-pnm-security-sdk` 为载体，低侵入注解 + 小二控制台 + Diamond 动态配置，对开放平台 HSF 接口按分销商多维度限流；
2. **分层分权管控（Matrix）**：将限流/字段屏蔽能力抽象为"主能力 + 子能力 + 约束"模型，通过 `ovs-pnm-matrix` 应用统一收敛商品池、渠道价、WF、购物车等业务白名单管控；
3. **基础治理**：统一/动态线程池规范、服务与接口迁移、灯塔 JAVA 工程治理、JDK 版本升级；
4. **容量与压测**：核心接口压测摸底容量，据此配置 Sentinel 单机/集群限流阈值；以及域名整理。

其中限流 SDK 与 Matrix 是同一体系的两代形态：**多维度限流 SDK 是底座（HSF 接口 AOP + 方法限流 + 字段屏蔽），Matrix 在其上增加了主能力/子能力模型，实现分层分级管控**（参见 `awq2td34ozgc8wv8`）。

> 关联页面：账号/开放平台侧的接口治理见 [[账号体系与开放平台.md]]；整体研发规范见 [[技术架构与研发规范.md]]；稳定性预案见 [[安全生产与稳定性保障.md]]。

## 多维度限流架构

### 核心概念与策略模型

多维度限流面向"国内商品卖给国外分销商"的开放平台场景，因分销商规模/用量差异大而设计。核心维度与策略：

- **限流维度**：
  - 分销商级别：`default` / `normal` / `vip`
  - 分销商个体：分销商 ID（专属配置）
  - 时间维度：秒 `second` / 分钟 `minute` / 小时 `hour` / 天 `day`
  - 限流次数：时间窗口内的点击（调用）次数
- **限流策略（拒绝策略）**：`reject`（拒绝服务，抛异常）/ `warn`（警告）/ `continue`（继续服务）
- **策略表达式格式**：`{维度}-{时间单位}-{次数}-{策略}`
  - 方法级示例：`vip-minute-30-reject`（vip 级分销商一分钟超 30 次即拒绝；无级别默认走 `default`）
  - 用户级示例：`2100000927014-hour-3000-reject`（指定分销商一小时上限 3000 次）

### 方法级与用户级优先级

- 生效顺序：**用户配置 > 方法配置**，二者取**并集**，并集内以用户配置优先。
- 用户级配置只对指定分销商生效，不影响其他用户请求。

### 限流器实现（限流算法）

限流器接口层次（模版模式）：

- `TimeWindowLimiter`：限流器接口，唯一方法入参为当前时间戳；
- `AbstractTimeWindowLimiter`：抽象类，实现共有算法（如按时间间隔取 key）；
- `FixedTimeWindowLimiter`：**固定窗口限流器**（已实现），按自然时间间隔计数（如整点小时 8:00–9:00 为一个窗口）；
- `SlippingTimeWindowLimiter`：滑动窗口限流器（**当时未完成**，计算最近一个时间单位内的调用量）。

**计数算法**：使用 `TreeMap` 作为计数存储体，key = 处理后的时间戳，value = 该窗口点击次数；判断触发时先计算当前请求数，与配置阈值比较，返回"是否限流 + 当前窗口总请求次数"。计数实现为"取数 → +1 → 存数"。

### 设计模式与运行原理

采用的设计模式：**代理模式**（Cglib，且用 Spring 自带的 Cglib 以减少 jar 引入、避免类冲突）、**模版模式**（限流器抽象类）、**工厂模式**（简单工厂按参数创建不同限流器）、**单例模式**（限流器缓存复用）、**责任链模式**（一次请求可命中多条策略，如小时 + 天）。

启动/运行链路：

1. Spring Boot 自动配置扫描 `spring.factories`，注册 `PnmSecurityAutoConfigure`；
2. 注入 `PnmSecurityBeanPostProcessor` 后置处理器；
3. 后置处理器增强带 `@HSFProvider`、`@HSFMethodSecurity` 注解的 bean，按注解配置生成 Cglib 代理；
4. 调用时经 `PnmSecurityMethodInterceptor` 方法拦截器横切 → 自动 Sentinel 埋点 → 取分销商级别限流 key → 合并方法级 + 用户级策略 → 获取限流器 handler 执行 → 命中 `reject` 抛异常返回限流错误码。

低侵入特征：仅需一个注解；小二控制台 + Diamond 配置联动 SDK，**动态更新限流策略无需重启应用**。

## 安全限流接入与 XFLUSH 报警

### 接入步骤（`ovs-pnm-security-sdk`）

1. **父 pom.xml** 引入 BOM（`type=pom, scope=import`）：

```xml
<dependency>
    <groupId>com.alibaba.ovs.panama</groupId>
    <artifactId>ovs-pnm-security-sdk</artifactId>
    <version>1.0.0-SNAPSHOT</version>
    <type>pom</type>
    <scope>import</scope>
</dependency>
```

2. **应用模块**引入 starter：`ovs-pnm-security-starter`；
3. 在接口/方法上写注解（`@HSFProvider` / `@HSFMethodSecurity`）；
4. **启动应用**：方法被自动推送到 Diamond 配置，剩下只需在小二控制台配置策略；
5. 小二控制台配置地址（HK 站点示例）：
   - 预发：`https://pre-tmallworld.alibaba-inc.com/supply/visual/security/center/app/config?siteId=HK`
   - 生产：`https://tmallworld.alibaba-inc.com/supply/visual/security/center/app/config?siteId=HK`
6. **用户自定义回调**：实现指定接口并声明为 Spring component bean，即可获取被限流的详细回调信息。

## Matrix SDK 与分层分权（Iceluna）

> 说明：本主题的可用源文档均以 **Matrix 分层分权系统 + `ovs-pnm-security-sdk`** 描述；命名"Iceluna"未在这批源文档中出现，此处以 Matrix 体系为准。

### 体系定位（横向工具领域）

| 应用/二方包 | 职责 | 前台/数据 |
| --- | --- | --- |
| `ovs-pnm-matrix` | 分层分权管控 | 前台 `.../supply/visual/matrix/solution/config`；数据库 `tmw_panama`（TDDL APP `TMW_PANAMA_APP`） |
| `ovs-pnm-security-sdk` | Matrix 对应 SDK，应用引入后做限流 + 透出字段屏蔽 | 前台 `.../supply/visual/security/center/app/config` |
| `ovs-pnm-common` | 巴拿马公共基础包 | 常用工具/对象缩写输出等 |
| `ovs-pnm-dependencies` | 公共依赖（日志等） | — |

限流 SDK 模块划分：`autoconfigure`（bean 后置处理器、注解扫描）/ `common`（公共工具）/ `core`（模型工具）/ `diamond`（与 Diamond 动态配置交互）/ `limiter`（限流器 + 字段屏蔽器）/ `starter`（外部引入坐标）。当前主要配置应用为 `ovs-pnm-open`。

### 能力命名规则

- **主能力**：`M_{类别}_{业务}`，类别取 `SELF`（业务能力）/ `PLATFORM`（平台/Portal 能力）/ `API`（接口调用），其他默认 `SELF`。
- **子能力**：`S_{子业务}`。
- 示例（商品池管控）：主能力 `M_SELF_ITEM_POOL_2C`；子能力 `S_OVS_ITEM_POOL_FOR_ALL` / `_FOR_SIGN` / `_FOR_SIGN_FILTER_BLACK_WORDS` / `_FOR_SIGN_MULTI_LANGUAGE`（另有 `_FOR_PANDABUY`、`_FOR_DSERS` 等示例）。

### 接入与校验接口

- 校验接口：`com.alibaba.ovs.panama.facade.MatrixCheckerFacade#check`，入参 `MatrixCheckerRequest`。
- 请求结构：`abilityCode`（主能力）、`userId`（主账号 ID）、`subAbilityValueMap`（map，key = 子能力，value 固定 `ON`）。
- 响应结构：`checkResult`（各子能力 true/false）、`hintRoles`（未命中白名单的提示文案）。
- 接入需先在 AONE 定义业务场景（主能力 + 子能力），再联调。

### 分层分级数据模型（服务化技术方案）

Matrix 将"单个功能白名单控制"视为一个主能力（WF、购物车、商品池、渠道价各为一个主能力），核心表：

- **能力项表** `hierarchy_ability_tb`：`ability_code`、`ability_name`、`ability_api_path`、`ability_clazz_path`（如 `...TestHsfSecurityServiceImpl#testmethod1`）、`ability_type`（`main_ability`/`sub_ability`）、`enable_fast_fail`、`fail_duration`、`wait_duration`、`ability_target`（api/自定义）、`app_name`、`main_ability_id`。
- **约束模版模型**：`hierarchy_code`（`default`/`normal`/`ska`）、`time_unit`、`type`（`<=`/`<`/`>=`/`>` 等）、`constraint`、`limited_type`（`reject`/`continue`/`warn`）、`hint_message`、`ability_id`。
- **权益模板表** `hierarchy_rule_template_tb` 存主能力 code；**权益子规则表** `hierarchy_rule_tb` 存 `sub_rule_code`；**规则约束表** `hierarchy_rule_constraint_tb` 存约束。
- Diamond 配置 `temp.matrix.config.diamond`（group `ovs-pnm-matrix`）承载主能力/子能力/约束初始化。

主能力 code 对照：`M_SELF_ITEM_POOL_2C`（商品池）、`M_PLATFORM_WF`（WF）、`M_PLATFORM_CART`（购物车）、`M_SELF_CHANNEL_PRICE`（渠道价）。

权益/能力接口：`MatrixSolutionFacade#insertSolution`（权益新增）、`MatrixSolutionFacade#addAbility2Solution`（能力项新增）。相关应用分支涉及 `ovs-pnm-account`、`ovs-pnm-matrix`、`ovs-pnm-distributor`。

- **新链路**：分层分级小二配置 → Matrix 应用更新本地数据库 → 推送多维度限流配置到 Diamond → Diamond 推送到应用。

## 统一线程池 / 动态线程池规范

### 统一线程池接入

引入依赖：`ovs-pnm-dependencies-bom` + `ovs-pnm-thread-starter`。提供三种获取方式：

1. **注解 `@PnmThreadPool`**（**不建议使用**）：字段级注解，配 `executorName`/`corePoolSize`/`maximumPoolSize`/`queueClazz`/`rejectHandlerClazz`。
2. **枚举**：实现 `TpSupplier extends Supplier<ThreadPoolExecutor>`，通过 `PnmThreadPoolExecutorManager.getThreadPoolExecutor(...)` 获取（示例枚举 `CommonTp`）。
3. **配置文件 + 注入（推荐）**：`application.properties` 配置后用 `@Resource(name="...")` 注入：

```properties
panama.thread.pool[0].executorName=test-properties
panama.thread.pool[0].corePoolSize=100
panama.thread.pool[0].maximumPoolSize=200
panama.thread.pool[1].executorName=test-00001
panama.thread.pool[1].keepAliveTime=500
panama.thread.pool[1].queueSize=500
panama.thread.pool[1].queueClazzName=java.util.concurrent.ArrayBlockingQueue
panama.thread.pool[1].rejectHandlerClazzName=java.util.concurrent.ThreadPoolExecutor$AbortPolicy
```

线程池参数默认值：`keepAliveTime=200L`、`queueSize=50`、队列默认 `LinkedBlockingQueue`、拒绝策略默认 `PnmCallerRunsPolicy`；`corePoolSize`/`maximumPoolSize` 默认取 `Runtime.getRuntime().availableProcessors()`。

> ⚠️ **注意**：配置阻塞队列/拒绝策略若为**内部类**，需用 `$` 分隔（如 `ThreadPoolExecutor$AbortPolicy`）。

### 动态线程池（V1.0）

解决两个痛点：线程池**无监控**、操作**无法透传上下文 traceId**。核心能力：动态配置、动态监控、鹰眼 TraceID 透传。

- 配置：Diamond（示例 `dataId=distributor_executor_id`，`group=distributor_executor_group`，`namespaceId=ovs-pnm-distributor`），修改参数后线程池动态更新。
- 监控日志格式（配专属日志文件 + XFLUSH 采集）：

```
traceId|traceId|应用领域|业务领域|线程名字|线程池名字|dataId|groupId|线程核心数|最大核心数|当前任务数|近似执行中线程数|未执行任务数|剩余队列大小
```

海外供给团队按业务域推进 JDK8 → JDK11 → JDK17。海外分销域约 12 个应用，多数已升级到 JDK11，部分已到 JDK17：

- **已到 JDK17**：`ovs-pnm-purchase`、`ovs-pnm-gateway`、`ovs-pnm-incentive`、`ovs-supply-job`；
- **JDK11**（已完成/灰度中）：`ovs-pnm-matrix`、`ovs-pnm-xt`、`ovs-pnm-item`、`ovs-pnm-account`、`ovs-pnm-open`、`ovs-pnm-im`、`ovs-pnm-distributor`、`ovs-pnm-data`、`ovs-ai-lab` 等；
- 难点应用（需工程改造，短期难升）：`ocg`（2016 老 war 包 + JSP）、`sword`、`ovs-base`（部分 JDK 基类被删）、`ovs-item-service`（Dockerfile 脚本失败）等。

### JDK17 排坑

**编译报错** `module jdk.compiler does not "opens com.sun.tools.javac.processing" to unnamed module`：

- **原因**：JDK17 module 化后部分 package 不对业务 module 开放，Lombok 注解处理依赖了未开放的 jdk 包。
- **方案一（推荐）**：升级 Lombok 到 `1.18.26`；
- **方案二**：为 `maven-compiler-plugin`（3.11.0）配置 `annotationProcessorPaths`，显式声明 `mapstruct-processor`、`lombok`，并加 `lombok-mapstruct-binding:0.1.0`（Lombok 1.18.16+ 需要）。

### jdk11 stream 的 count() 潜在问题

AONE 自动化升级流程会把 `stream().count()` 改写为 `stream().mapToLong(e -> 1L).sum()`，原因：

- JDK11 中 `count()` 做了性能优化——当**流的元素数量可从源直接得到**（如 `List` + 无改变数量的中间操作 `peek`）时，**可能跳过管道执行**，导致有副作用的中间操作（如 `peek`/日志）失效。
- 当中间操作会改变数量（如 `filter`）时，`count()` 等价于 `mapToLong(e -> 1L).sum()`。
- **结论**：纯计数用 `count()` 性能更优；若 stream 中间操作含业务逻辑/副作用，应改用 `mapToLong(e -> 1L).sum()` 以保证管道执行（这也是自动改写"看似多余"但稳妥的原因）。

## 核心接口压测

压测用于摸底单机容量，作为 Sentinel 限流阈值依据。统一压测平台 `pas-server`，机器 4c8g，4 台施压机。

### 撞库接口压测（`ovs-pnm-item` `ItemApi#queryItem`）

- 数据：单 sku 商品（713961697936）与 8 个 sku 商品（703264908962）；因货通限制不能重复铺货，仅压不重铺场景。
- 结论：**不触发重新铺货逻辑时，单机（4c8g）最大 ~65 qps，平均 RT ~560 ms**（含铺货调用可能升至 ~800 ms，较线上 1.8s 下降约 50%）。qps 达 72/80 时错误率升到 8.5%/17%。

### 账号接口压测（`ovs-pnm-account`）

- 接口配比 `getAccount : hasFuncPermission : getPageResource = 50 : 10 : 1`，压测前关闭缓存。
- 结论：不存在性能问题，服务端平均 RT ~2 ms，继续加压主要因线程切换导致 CPU 升高；作为非高流量业务，**建议单机限流**：`getAccount=200`、`hasFuncPermission=40`（80 足够）、`getPageResource=10`（50 足够）——与上文 Sentinel 配置一致。
