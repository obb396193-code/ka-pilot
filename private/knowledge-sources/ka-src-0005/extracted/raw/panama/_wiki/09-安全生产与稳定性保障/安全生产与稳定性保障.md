# 安全生产与稳定性保障

## 概述

本页汇总巴拿马跨境分销域（淘系海外 OVS 供给侧）的安全生产与稳定性保障机制，覆盖**安全生产技术场景梳理、故障等级定义、预案与降级、大促保障机制、压测与容量流量模型、监控与报警治理、问题排查 SOP、性能治理案例**八大主题，聚焦可复用的机制、规范与操作方法，跳过一次性值班/告警流水记录。

核心自建应用（贯穿全文）：`ovs-pnm-open`（开放平台网关/核心）、`ovs-pnm-account`（账号）、`ovs-pnm-item`（商品）、`ovs-pnm-xt`（搜索）、`ovs-pnm-distributor`（分销工作台）、`ovs-pnm-matrix`（权限/leads）、`ovs-pnm-purchase`（购物车）、`ovs-pnm-pressure`（压测施压机）。核心链路强依赖**货通平台（gsp-order/gsp-assortment）、集团交易（Buy2）、国际开放平台、国际会员平台**，稳定性保障需与这些团队协同。相关业务与链路参见 [[巴拿马跨境分销业务与产品总览.md]]、[[采购交易与履约链路.md]]、[[账号体系与开放平台.md]]。

**核心业务目标（FY26）**：下单成功率保持 99.5% 以上；无 P3 及以上故障；无资损相关故障。大促技术目标：无 P2 及以上故障、0 资损；压测目标：关键链路/核心接口成功率 3 个 9（99.9%）。

## 一、安全生产技术场景梳理（FY26）

按「域 × 模块」梳理每个场景的高可用/稳定性/资损三维要求，并落实到监控与对账保障措施。这是安全生产的顶层地图，用于确定保障投入优先级。

| 域 | 模块 | 高可用 | 稳定性压力 | 资损 | 保障要点 |
| --- | --- | --- | --- | --- | --- |
| 用户 | 登录 | 高 | 低 | 低 | 登录监控 ForGOC，依赖国际会员平台 |
| 用户 | 用户基础服务 | 高 | 高 | 否 | QPS 高、渗透多场景，稳定性直接影响多业务；账号接口性能指标 |
| 商品 | 撞库寻源 | 高 | 中 | 否 | 与货通商品协同保障，货通底层有难度 |
| 商品 | 商品查询 | 高 | 中 | 否 | 与货通商品协同，受外部影响大 |
| 交易 | 下单 | 高 | 低 | 否 | 与货通交易、淘天交易共同保障 |
| 交易 | 订单查询/支付 | 高 | 低 | 否 | 与货通交易、淘天交易、支付渠道共同保障 |
| 结算 | 定向行业佣金结算 | 低 | 低 | **是** | 架构天然有重试机制，重点是对账（MAC 对账） |
| 激励 | 佣金预估 | 高 | 中 | 否 | 涉及用户体验、不涉及实际资金 |
| 激励 | 返佣结算打款 | 中 | 中 | **是** | M+1 结算模式，重点是资损防控（保障待建） |

**关键洞察**：
- **稳定性压力最高点是「用户基础服务」**（账号），因为 QPS 最高且渗透所有场景——这也是压测/限流的重点对象。
- **资损场景集中在结算/激励域**（定向佣金结算、返佣打款），保障手段以对账为主而非高可用，详见 [[佣金结算与资损防控.md]]。
- 商品撞库/查询强依赖货通，高可用保障需靠「协同 + 监控 + 限流降级」而非单方面扩容。

## 二、故障等级定义

### 2.1 设计准则（FY24）

- 对齐[集团故障等级标准](https://ata.alibaba-inc.com/)，提升研发人员与外部协同团队的安全生产意识。
- 业务快速发展阶段需平衡：只对**核心业务场景**（撞库、商品查询、订单创建、订单支付）定义故障等级，其他功能点走日常处理流程 + 客诉兜底。
- **时效设计**：采购集中在每天 08:00–18:00（10 小时）；按日均成交 7w 件、GMV 250w、件单价 35 元测算，创单成功率跌到 90% 持续 1 小时约影响 700 单、24500 元 GMV。参考海外既有定义并兼顾业务发展，**故障判定时效以 1 小时起**。

### 2.2 FY24 故障判定标准

**故障有效时间段：08:00 ~ 18:00；成功率口径：分钟级成功率，分钟内无流量时成功率=100%。**

设计阶段（最高等级评估，涉及外部团队）：

| 功能点 | 涉及外部团队 | 影响 | 最高等级 |
| --- | --- | --- | --- |
| 开放平台 API 可用性 | 国际开放平台 | 分销商无法经营 | P3 |
| 分销工作台注册登录 | 国际会员平台 | 分销商无法经营 | P3 |
| 商品撞库（API） | AE 货通平台 | 无法下单 | P3 |
| 商品查询（API） | AE 货通平台 | 无法获取准确商品信息 | P3 |
| 创单（API） | AE 货通平台 | 无法下单 | P3 |
| 订单查询（API+工作台） | AE 货通平台 | 无法支付（影响面可控） | P4 |
| 支付（API+工作台） | AE 货通平台 | 无法支付（影响面可控） | P4 |

初版落地判定阈值（P4 触发线，含关联接口依赖）：

| 功能点 | P4 判定阈值 | 关键接口依赖 |
| --- | --- | --- |
| 开放平台 API 调用 | 持续 2h 成功率 <80% 且 ≥50%；或持续 1h 成功率 <50% | 需与开放平台对齐监控项 |
| 分销工作台登录 | 持续 2h 成功率 <80%；或持续 1h 成功量为 0 且近 1h 总量 >10 | 需与会员平台对齐监控项 |
| 商品撞库 `/product/get` | 持续 2h 成功率 <90% 且 ≥50%（每分钟总量>100）；或持续 1h <50% | `SupplyItemService.queryItem`、`GspAssortmentOpenApi.queryDistributionGspProduct`、`GspProductService.joinProductPool` 等（强依赖货通） |
| 商品查询 `/product/details/query` | 持续 2h 成功率 <90% 且 ≥50%（每分钟>100）；或持续 1h <50% | `GspAssortmentOpenApi.queryGspProductByIds`、`SupplyItemService.queryItem` |
| 订单创建 | 持续 2h 成功率 <90% 且 ≥50%（每分钟>10）；或持续 1h <50% | `GspOrderSolution.collectOrder` |
| 订单查询 | 持续 2h 成功率 <90%（每分钟>10）；最高到 P4，不再升级 | `PurchaseOrderQueryFacade.queryPurchaseOrder` |
| 订单支付 | 持续 2h 成功率 <90%（每分钟>10）；最高到 P4，不再升级 | `GspOrderSolution.payPurchaseOrder` |

> ⚠️ **内容分歧**：设计文档将撞库/查询/创单最高定为 **P3**，而落地初版判定表中所有功能点的实际配置阈值最高标注为 **P4**（订单查询/支付明确"最高到 P4，不再升级"）。落地时以更保守的 P4 阈值执行，实际升级判断需结合影响面。

### 2.3 FY26 故障等级定义

> ⚠️ **内容缺口**：源文档《FY26 天猫淘宝海外故障等级定义》(pageId `nY1wAJvcXpGItA9n`) 两次读取均为空，无法同步 FY26 最新阈值。当前 FY26 目标口径以《安全生产技术场景梳理》为准：**无 P3 及以上故障、无资损故障、下单成功率 ≥99.5%**；大促口径为无 P2 及以上故障、0 资损。需补充读取该页。

## 三、预案与降级

### 3.1 预案体系与平台

- **预案平台**：`preplan2.alibaba-inc.com`（线上）、`pre-preplan.alibaba-inc.com`（预发）。巴拿马运行在**国际化新加坡单元**（`rg-sg` / `envGroup=rgOnlineGroup`）。
- **预案分类**：提前预案（大促前定时执行）与应急/紧急预案（触发条件满足时执行）。
- **预案要素规范**（来自淘海外履约侧 SOP 模板，可复用）：每条预案应明确 **【执行时机】【执行动作】【执行影响】【恢复时机】【客服口径】【相关方（业务/产品/技术/测试）】**。
- 预案需标注：应用、类型、等级、是否压测、开发/测试/录入/验证责任人、预案项（switch/diamond/sentinel 配置 key）。

### 3.2 巴拿马核心预案项

| 预案 | 类型 | 应用 | 配置项 / 说明 |
| --- | --- | --- | --- |
| 巴拿马商品更新消息限速 | 紧急 | ovs-pnm-open | 开关 `MQ_MESSAGE_CONSUME_DELAY_LIMIT_OPEN`——防止用户接收过大消息体量 |
| 商品详情 KC 商品直铺降级 | 应急 | — | 执行后不再触发直降逻辑 |
| 订单数量统计降级 | 应急 | ovs-pnm-distributor | 降级工作台订单列表统计值（历史，已划线） |
| 导购搜索底池开关 | 应急 | — | 关闭走旧搜索底池（历史，已划线） |
| 购物车大促优惠查询降级 | 应急 | ovs-pnm-purchase | 开关 `CART_ITEM_PROMOTION_QUERY` |
| 订单导出降级 | 提前 | ovs-pnm-distributor | 开关 `ORDER_EXPORT_FUNCTIONAL_SWITCH` + 导出条数白名单 `ORDER_EXPORT_FUNCTIONAL_WHITELIST` |

FY26 双11 大促巴拿马纳入集团预案汇总，共 **2 条预案**（存量 2、下线 3），责任人凝惜，线上/预发均已验证。

### 3.3 日常预案维护规范

- 提倡**「大促预案与日常预案各留一个」**：许多降级项（如我淘各组件、营销金豆/支付满减降级）在日常态也保留一份应急预案，避免大促临时新建。
- 预案统一录入预案平台并在预发验证；文本类预案（无法在平台验证的，如 TPP 平台自动降级、diamond 文本配置）单独标注「不在预案平台验证」。
- 每次大促做预案盘点：统计存量/新增/下线数量，标注是否压测、录入人、测试人、线上确认人。

### 3.4 大促提前预案时间窗（2024 双11 示例，体现节奏规范）

分**两波**执行（第一波约 10-21～10-25 预热，第二波约 10-31～11-12 正式）：
- **前置工作**：`ovs-pnm-open`、`ovs-pnm-distributor` 等应用在 10-21、10-31 清理日志并重启。
- **搜索/详情/购物车筛选项透出**：通过 `ovs-pnm-open` 搜索配置 + `ovs-pnm-item` diamond `item.promotion.config` 配置大促活动 tag（如天猫 `3432514`/`3432578`、淘宝 `3433666`/`3433730`），配合活动生效/失效时间。
- **限量保护**：大促期间限制淘宝主订单数量 10000（16:00–次日 10:00 窗口）。
- **渠道价黑名单**：向 `ovs-pnm-matrix` 写入 `DATASET_CHANNEL_PRICE_BLACK_LIST` 数据集（约 773 个 leads），手动控制生效窗口。
- **跟价任务暂停 / 页面禁止编辑**：大促开卖前后手动控制（如 17:55–20:30）。

## 四、大促保障机制

### 4.1 整体保障流程（历年 618/双11 通用节奏）

1. **QPS 预估**：基于[巴拿马监控大盘](https://x.alibaba-inc.com/custom/19)读取日常 QPS，按流量模型放大（见第五节）。
2. **接口评估**：逐接口判定「是否需要压测」——只压核心高流量接口，低流量接口参考往年经验免压。
3. **扩容安排**：按需扩容核心应用（近年多为「参照往年，无需扩容」）。
4. **压测**：申请施压机 → 部署 → 峰值压测 + 系统摸高。
5. **预案盘点与录入**：新增/复用/下线预案，预发验证。
6. **限流配置**：按压测结论配置单机/集群限流值。
7. **大促值守 + 复盘**。

### 4.2 接口依赖与协同接口人（流量预估阶段对齐）

| 依赖模块 | 接口人 | 模块 | 接口人 |
| --- | --- | --- | --- |
| 货通 | 应军 / 陈磊 | 账户、matrix | 冈刀 |
| 开放平台 | 笛福 | 商品 | 览青 |
| 交易 | 俊龙 | 优惠价格 | 雪薇 |
| 国际会员 | 肖张 / 方辰 | 履约 | 起元 |

其余多为淘系接口，日常容量即可支撑。压测负责人：缀明。

### 4.3 上下游依赖与保障群

- **监控/报表口径**：见第六节监控汇总。
- **保障沟通群**：FBI 开放能力上下游沟通&保障群、红包收账异常问题查询群（钉钉群，用于跨团队快速拉起排障）。
- 交易链路上下游：巴拿马（ovs-pnm-open）→ 货通（gsp-order）→ 集团交易（Buy2）→ 千帆（国际段接单），详见 [[采购交易与履约链路.md]]。

### 4.4 618 复盘要点（FY24，方法论沉淀）

- **技术目标 review**：撞库成功率 98%、创单 99.9%、支付 99.5%——实际 OpenAPI 撞库 99.69%、支付 99.86%，整体 0 故障。
- **复盘结构**：业务表现（成交趋势/峰值）→ 技术目标达成 → 各域系统水位（QPS/RT/成功率/CPU）→ 工单分析 → 问题汇总 → 后续 action。
- **暴露问题**：创单服务成功率统计未排除业务异常（库存不足、限购），造成成功率误解——需在监控口径中剔除业务异常。峰值时 `ovs-pnm-open` CPU 仅约 7.5%，容量充裕。

## 五、压测与容量/流量模型

### 5.1 流量预估模型（多版本演进）

| 版本 | 预估公式 | 系统摸高 |
| --- | --- | --- |
| FY24 双11（容量预估） | 预估 QPS = (双11目标 GMV / 日常 GMV) × 日常 QPS × 系数(1.3)，约日常 1.8~2.07 倍 | — |
| 通用流量模型 | 大促 QPS = 日常峰值 QPS × max(2, 大促 GMV/日常 GMV) | — |
| FY24 618 | 日常峰值 × 2 | 日常峰值 × 3 |
| FY26 双11 | 爆发系数 = 去年双11峰值/去年日常峰值；压测目标 = 爆发系数 × 当前日常峰值 | 预估峰值 × 1.5（历史大促经验值） |

### 5.2 核心压测接口与目标 QPS（FY26 双11，单位 QPS）

| 接口 | 应用 | 爆发系数 | 日常峰值 | 预估峰值 | 摸高 |
| --- | --- | --- | --- | --- | --- |
| 撞库 `/product/get` | ovs-pnm-open | 4 (65/16) | 53 | 212 | 318 |
| 商品详情 `/product/details/query` | ovs-pnm-open | 2.4 (116/49) | 113 | 271 | 407 |
| 订单列表 `/purchase/orders/query` | ovs-pnm-open | 1.6 (26/16) | 22 | 35 | 52 |
| 账号查询 `getAccount` | ovs-pnm-account | 1.1 (344/227) | 836 | 920 | 1380 |

**FY26 压测结果：全部通过**——4 个接口峰值+摸高成功率均 100%，RT 符合预期；open CPU 稳定 <20%、account CPU <20%，**无需扩容**。

### 5.3 历史压测结论（FY24 618）

- 日常峰值 ×2、×3 压测：撞库/商品详情/订单列表/供应链报价/账号查询成功率均 100%。
- **铺货接口是唯一瓶颈**：读写并行下，铺货 QPS ×3（约 7qps）系统摸高失败，成功率 99.54% <99.9%；降到 ×2.4（约 6qps）摸高成功，99.94%。RT 高达 7-9s，为链路薄弱点。
- **账号限流调优**：账号系统触发限流后，将单机限流从 `200×5` 提到 `400×5`，摸高 1200 QPS 未触发，大促维持 `单机 400×5`。
- open CPU 稳定 <15%，无需扩容。

### 5.4 容量预估细节（FY24 首次全量压测）

- **压测三步计划**：① open 应用压测得上下游容量 → ② 货通铺货链路压测 → ③ open 铺货详情/搜索接口压测。
- **货通依赖接口压测结论**（预估 vs 实测）：`queryDistributionGspProduct` 预估 48 / 实测 188；`queryGspProductByIds` 单商品 400、巴拿马混合压支持 329；`joinProductPool` 第二次压测 62（平均 RT 1.5s）。
- **`queryGspProductByIds` 性能隐患**：内部单商品单线程串行查询，日常 QPS 25、平均 RT 813ms，双11 后需优化。
- **消息体量预估**：`gsp_channel_product_update` 消费 QPS 约 250（峰值 289），`PANAMA_ITEM_UPDATE` 约 250（峰值 281），open 消息出口需加降级&限速能力。

### 5.5 压测环境准备 SOP（可复用）

1. 新建/复用压测应用 `ovs-pnm-pressure`（PAS 平台不再提供施压机）。
2. 诺曼底平台 `n.alibaba-inc.com` 申请压测机器权限与额度，划入 ovs-pnm-pressure。
3. 在容量平台 `pas-server.alibaba-inc.com` 通过 IP 部署施压机（一个场景一台机器）。
4. **实操经验**：先将 ovs-pnm-pressure 机器全部下线再扩容；新机器通过 IP 添加后部署。

### 5.6 核心接口容量与限流基线

FY26 压测得出的单机限流值（部分，QPS）：撞库 20、货源详情 20、商品详情 20、订单列表 20、IM 未读 50、账号查询 200、鉴权 30、matrix 权限校验 200、商品搜索 3。集群限流（FY24 结论）：撞库集群 500+、商品详情 300、货源详情 108、货源物流费 90、订单列表 180、图搜 40。详见 [[限流与服务治理.md]]。

## 七、问题排查 SOP

### 7.1 单机报错 SOP

1. **定位机器 IP**：根据预警信息获取报错机器 IP。
2. **判断客户影响**：影响客户体验→考虑单机降级；不影响→做代码分析、优化逻辑。
3. **降级 IP 所在服务**：通过 HSF QOS 平台按 IP 摘除服务（预发 `envType=pre`，生产 `envType=online`）。
4. **单机服务下线（而非直接置换）**，原因：① 保留问题现场便于后续排查；② 置换审批耗时，先下线可缩短处理时间。
5. **扩容或置换**：通过 iOne（`ione.alibaba-inc.com`）扩容，或诺曼底（`n.alibaba-inc.com`）置换机器。

### 7.2 淘系订单常见问题排查

- **排查工具**：tpConsole（订单数据查看）、bsp 工具平台/星环运维（下单链路排查）、AEDT 全景数据信息（订单数据变更过程排查）。
- **改地址排查**：通过订单标确认。卖家改地址 `lm=1`；买家改地址 `modifyAddress=1`（付款前）/ `=2`（付款后），来源系统看 `tiModifyAddressSource`。

### 7.3 上下游保障群

排障时通过保障群（FBI 开放能力上下游群、红包收账异常群）快速联动货通、开放平台、会员等外部团队。

## 八、性能治理案例

### 8.1 API 高峰流量 & GC 抖动（ovs-pnm-open）

**现象**：客户反馈交易/商品接口报错 "RPC 超时"，RT 达 15s。

**排查路径**：鹰眼 trace 全链路分析 → 下游 account 查询耗时正常，瓶颈在 open 网关机器 → 系统水位分析发现该时刻 QPS 出现平均 **3 倍**高峰 → CPU 打满源于**堆内存频繁 CMS 回收 + 频繁 GC 的线程切换**；JVM 老年代 GC 频繁、堆内存不足（老年代已用 1.65G / max 2G，仅剩 358M）。

**根因（大对象）**：Dump 堆（`jmap -dump` → zprofiler 分析）发现 250 个 `GspProductDTO` 实例占堆 12.22%。两处场景：
- **铺货列表查询接口**（`SellerProductService#convertProductSpuResponse`）：对外未限制分页大小，用户每次查 500 条，为补类目数据批量查 GP。
- **采购创单接口**（`PurchaseOrderAssist#getUnBuildRelationList`）：读取 GP 素材信息 + 货源商品 ID 反查断供校验。

**优化方案与效果**：① 强制分页大小（500→100→逐步切 20），通知客户整改；② 类目信息查询替换（调研从 IC 类目获取，避免从 GP 拉取）。**去掉 500 分页后 GC 显著下降**。

**JVM 基线**（ovs-pnm-open 启动参数）：`-Xms4g -Xmx4g -Xmn2g`（new:old=1:1，各 2G），CMS GC，`CMSInitiatingOccupancyFraction=80`，MetaspaceSize 256m。

### 8.2 ThreadLocal 缓存清理导致 FullGC（gsp-order）

**背景**：多线程环境下，子线程的 ThreadLocal 缓存未清理导致 FullGC 频繁报警。

**排查方法**：还原「多线程 + 并行流 + `@CacheThreadInvokeResult` ThreadLocal 缓存」业务处理，加 JVM 参数（`-XX:+PrintGCDetails -Xloggc`）本地生成 GC 日志对比三种条件：

| 测试条件 | 5 分钟 FullGC 次数 | 内存表现 |
| --- | --- | --- |
| 不开启缓存 | 52 次（以 MinorGC 为主） | 稳定 ~5G |
| 开启缓存 + **未清理** | **接近 700 次** | 快速增长，1 分钟内到 8.57G **OOM** |
| 开启缓存 + 开启清理 | 41 次 | 稳定 ~5G |

**结论**：并行流中每个子线程使用 ThreadLocal 缓存后必须显式 `clear()`；否则线程池复用线程使缓存对象无法回收，大对象堆积触发 FullGC 直至 OOM。开启清理后指标与不开缓存相当。

**通用治理经验**：巴拿马域两起 GC 事故均由**大对象/未释放对象堆积**引起——治理手段是「限制批量入口规模 + 及时释放线程内缓存 + 堆 Dump 定位大对象」。
