# 日本站与自营独立站

## 概述

本页汇总淘宝天猫海外（AIDC）面向**日本独立站**的供给侧建设方案。日本站是一个**面向日本市场的独立站（淘外站点）**，供给侧的核心目标是把淘宝/天猫的商品作为货源，通过铺货、定价、采购与履约的完整链路，在日本站以**自营店（自营模式）**的形态对外销售。

整体存在两条并行的供给形态：

- **自营模式**：日本站作为「二方分销商」入驻巴拿马跨境供货平台，把淘宝商品上翻（铺货）到日本站 IC（商品中心），由平台统一定价、统一采购履约，交易履约在日本站体系内闭环。这是本期（530/630/730 版本）落地的主线。
- **全托管模式（草稿）**：让淘系/独立站商家以托管形式供货，平台代运营销售。存在多种链路方案（复用淘内供应链平台、TBC 影子店铺、独立站站内闭环等），本期为方案设计阶段。

关键系统/应用：

| 应用名 | 角色 |
| --- | --- |
| `jp-supply-operation-s`（JP_SUPPLY_OP_APP） | 日本站供给-采购/履约聚合层应用（正逆向、订单查询） |
| `jp-supply-salespricing-s` | 日本站自营定价应用（自营定价中心，计划部署新加坡 VPC） |
| IC（`com.alibaba.global.ic.api.*`） | 国际化商品中心，承载商品/价格/价格因子/商品标 |
| 货通平台（GSP，`gsp-order` / `gsp-assortment`） | 端到端铺货、采购交易、履约协同能力 |
| 巴拿马分销平台（`ovs-pnm-*`） | 采购创单/支付/退款的上层业务能力（当前被依赖，规划剥离） |
| AIDC 供应链平台（SCM）/ TMW 物流平台 | 国内集运仓履约、跨境物流、逆向拒收/质检 |

> ⚠️ **内容分歧**：铺货目标口径不一。《商品上翻》技术目标写「730 前完成 200w+ 商品铺货/更新」，并按 70% 铺货漏斗反推「待铺货 200/0.7 ≈ 285 万」；而定价运行时长预估以「500 万商品（每商品均 10 SKU）」为算例。前者是业务铺货目标，后者是定价系统容量算例，二者口径不同，勿混用。

## 全托管模式

《淘宝商家全托管模式方案设计》给出 6 套候选链路，核心差异在于**货源接入方式（淘内供应链平台 vs 影子店/独立站原生）**与**销售侧市场（淘内平台店 vs 淘外独立站）**，并以开发成本【无/低/中/高】标注（低=10 人日内、中=10~20、高=20 以上）：

1. **淘内供应链平台 + 淘内平台店分销**：以「淘新衣」供应链模式为参照，商家源头入驻或现有店铺商品转发到供应链平台，平台开海外店铺分销。交易/履约/结算基本复用海外基础链路（订单地址转国内仓），整体成本最低。
2. **淘内供应链平台 + 淘外独立站分销**：需把淘内供应链平台与淘外商家商品链路对接（成本【高】），独立站建站/运维成本【高】。
3. **TBC 影子店铺 + 淘外独立站分销**：淘内商家通过影子店铺完成托管，复用 TBC 链路做淘外分销；GSP 创采购单支持淘宝创单（无额外开发），销售侧独立站交易定制【高】。
4. **AE 入淘宝**：AE 作为货源市场接入货通，平台开淘宝店销售（TBC 反向），需 AE 商品同步 + 淘宝发品对接。
5. **独立站站内闭环托管**：类比 AE 全托管，独立站卖家站内签约托管店铺，交易履约站内闭环，商家商品模型构建成本【高】。

各方案共性：订单最终地址转为**国内集运仓**，商家按国内履约发货；销售侧沿用海外交易的外币支付与物流能力；结算通过分账规则扣佣。参考《AE全托管技术方案调研》。

> 关系：全托管为方案储备，本期落地的是**自营模式**（下述定价、采购、铺货均属自营）。全托管与自营都强依赖货通平台/海外基础链路。相关背景见 [[巴拿马跨境分销业务与产品总览.md]] 与 [[采购交易与履约链路.md]]。

## 自营店商品定价

来源：《自营店商品定价技术方案》《方案预研》《运行时长预估》《联调核心用例》。

### 定位与部署

- 自营定价中心**新建应用**（`jp-supply-salespricing-s`），计划部署到**新加坡 VPC 机房**。
- **以 AE 全托管的国际化定价能力为基础**改造适配，但**不采用国际化定价的调度框架**——日本站定价链路较简单，定价规则变更触发价格计算，作为普通 Service 实现，不做过重抽象。
- 定价结果按 **SKU 维度输出日志到 SLS**，便于排查。

### 定价规则（策略）

- 复用国际化定价的策略 CRUD 服务、策略变更 MetaQ 通知机制；本期策略为**单条操作、创建直接生效、不涉及审批**。
- 关联维度仅**叶子类目**；可能存在多条生效策略类目交集，规则：**以最大生效策略 ID 为准（ID 最大=创建时间最新）**。
- 规则配置量业务预估 **不超过 500 条**，按 2000 条实际生效评估；采用**分布式二级缓存**（一级缓存 value 用单值结构而非 list，节省命中链路成本）。
- 规则表 `pricing_strategy`：含 `template_code`、`biz_scene_code`、`status`（-1删除/1生效/2失效）、`env`、`cate_ids`（json 数组）、`attributes`。
- 规则生效/失效发**延时消息**（保证缓存操作完成）；规则生效时调用 **IC 圈选关联叶子类目下商品**，发定价任务消息，本应用消费定价。

**定价规则四因子（小二配置，百分比、两位小数、[0,100)）**：运费藏邮比例、运营成本因子、营销成本因子、利润加价率。

### 价格审核

- 审核维度为 **SKU 维度**，仅 JP 一个国家，审核单为**单层 SKU 维度审核单**。
- 复用国际化定价审核架构的**通用状态机**（基于 cola 状态机简化，核心对象 State/Event/Transition/Condition/Action/StateMachine）与**通用审核单模型**（审核单 + 审核记录，`pricing_audit` 表，支持 `parent_audit_id` 主子关联）。
- 审核单分库分表：定价 DB **16 库 × 16 表 = 256 表**，单表上限 500w，可支持约 12 亿审核单。**`sharding_id` 用 SKU 所属商品 ID**（保证同商品所有 SKU 落同一库）。
- 状态机关键点：审核**通过**→更新 IC 销售价、去除 SKU 未定价标、标记审核单生效；再次系统定价完成时重置为「待提交」并发「发起价格审批」事件。审核类型：2-行业小二审核、3-行业TL审核。审核触发原因：加价金额低于/高于限额、SKU 禁编、利润加价率低于最小限额。即使无需人工审核也生成审核单，保证记录完整。

### 定价链路与 IC 交互

- 因规则缓存内存储的即最新规则，定价任务**直接取最新策略定价**（此处与 PRD 的强串行执行逻辑存在差异，选择实现成本更低的方案，牺牲强顺序）。
- IC 查询：`MerchantProductServiceFacade#queryProduct`（按 itemId+skuId）；商品搜索服务按叶子类目滚动查询；日本站**类目包需新开发**（预计 6 月才 ready，可参考 AE 类目接入）。
- IC 写入：`ProductWriteServiceFacade#saveProduct`。**供货价**通过 IC expand 字段存储（`{currency,value}` 协议待 IC 评审）；**销售价**写全球原价 `priceDTO#fixedPrice`；**价格因子**用 `PriceFactorDTO`（type/factorMap/version）。

**价格因子 Key 与计算公式**：

| Key | 含义 | 公式 |
| --- | --- | --- |
| `CS_POST_COST_CNY` | 跨境物流费 | 物流平台给出的跨境物流费（CNY 元） |
| `POST_HIDE_COST_CNY` | 物流藏邮费 | 跨境物流费 × 运费藏邮比例，CNY 元，两位小数向上取整 |
| `OPS_COST_CNY` | 运营成本 | 税前售价 × 运营成本因子，两位小数向上取整 |
| `MKT_COST_CNY` | 营销成本 | 税前售价 × 营销成本因子，两位小数向上取整 |
| `MARKUP_RATE` | 实际利润加价率 | （税后价 − 供货价）/ 供货价 |
| `TARIFF_RATE` | 关税税率 | 关税税率 |

算价时查询物流费与关税（HSCode 保存后作为 feature 写入 IC）；物流/关税查询改**异步**、HSF bean 加开关控制；IC feature 标请求合并以减少并发更新失败。

### Web 层接口（类 REST，JSON）

定价规则：`/pricing/strategy/getCategoryTree`[GET]、`/create`[POST]、`/update`[POST]、`/operate`[POST]（type 0生效/1失效）、`/get`[GET]、`/list`[GET]；定价审核：`/pricing/audit/list`[GET]（按 itemId、叶子类目、auditType、auditStatus、auditReason、itemEditStatus 过滤，审核列表由商品搜索引擎提供）。

### 运行时长预估

处理能力主要受外部服务 QPS 与定价任务资源限制。预估公式算例：**500 万商品 × 均 10 SKU = 5000 万 SKU，按 500 QPS（SKU 级）→ 约 100000 秒 ≈ 1.16 天**。业务可用性上整体任务控制在一天内可较好对齐各环节（含离线链路）时效。

### 联调核心用例（已完成）

策略新增/失效（DB+缓存正常）；基于策略触发定价（待定价 SKU 消息收发、审核数据新增/更新、IC 写入价格与因子）；**基于 IC 新增消息定价**（货通铺货新商品/新增 SKU 触发，发起方=货通）；小二审核 / TL 审核（通过/拒绝）；小二改税后价；商品分页查询。依赖时间点：物流报价查询（7.30 上线）、关税查询（7.15）、商品搜索/IC、货通。联调关键 IC 标：`jp_p_price_stat`（审核状态）、`fb_had_p_price`（货通写已定价标，需有 `dist_cp_id` 标）。

关联：定价规则见 [[佣金结算与资损防控.md]]（收佣费率）与 [[商品域·铺货·选品与搜索.md]]（商品搜索/IC）。

## 采购与履约

来源：《自营店采购和履约技术方案》。应用 `jp-supply-operation-s`（JP_SUPPLY_OP_APP），TDDL/MySQL **16×16 Sharding**，Tair(ldb) 缓存。

### 设计原则

- **标准业务能力复用**：日本站作为分销商对接巴拿马（跨境供货）平台，完成分销商入驻，原则上直接用巴拿马平台 API 采购淘天商品；
- **业务逻辑独立**：日本站采购作为独立业务层开发维护；
- **单向依赖**：作为业务聚合层，单向依赖外部系统，被依赖点通过消息解耦。

### 关系模型（核心）

新增交易-采购关系实体，记录 BO（日本站订单）与 PO（采购单）映射：

- `bo_po_relation_[0000-0255]`：`bo_id`/`bo_item_id`（外部交易主/子单）、`po_id`/`po_item_id`、`status`（-1待采购/0采购中/1成功/2失败）、`error_code`/`error_msg`；唯一键 `(bo_id, bo_item_id)`。日本站交易为 **1024 个分表**。
- `bo_po_reverse_relation[0-255]`：逆向关系表，含 `reverse_order_id`、`reverse_order_line_id`、`gsp_refund_id`、`refund_status`。

### 正向链路

- **采购创单**：采购中心拆销售单再提交给 GSP（巴拿马分销平台与 GSP 无改动）。日本站主订单冗余 GSP 订单 ID 列表，子订单冗余 GSP 子订单 ID；GSP 销售主订单记录日本站主订单 ID，按 ID 分拆映射规则关联。子单 feature 携带拆单信息：`transitWarehouseCode`（仓 code，如 MAD001）、`jp_sm`（运送方式，如 OCEAN）。**日本站交易不感知采购失败**。
- **采购支付**：复用现用链路，采购中心接支付消息可暂不做；独立站交易暂不需知道支付结果。
- **采购发货**：采购中心全部按**子订单维度**发货消息（基于现有分销商消息 `message_type:3`），需将子单商品 ID/SKU_ID 换为淘宝商品 ID/SKU_ID。
- **采购取消**：按日本站主订单发起取消。

### 逆向链路

- **仅退款**：与日本站逆向联动，符合条件（仅退款/少件/错发）时查询退款详情、查 SCM 履约状态；若货品状态在【已签收～二段出库】则等仓库处理，流程结束；否则查 GSP 子订单号→GSP 未支付则先发起支付→构建 GSP 子订单仅退款参数→调用巴拿马采购退款申请 API。
- **仓库拒收**：退货退款发生在国内仓收货环节，淘宝订单处于售中状态；退货退款同意消息 `message_type:9` 携带 BO 子单号与退货地址。
- **质检异常**：发生在仓库收货后，可能已确认收货，需售后时效判断。
- 逆向依赖 SCM 逆向拒收/质检异常消息、独立站退款单消息与查询接口。

### 无主件码解析工具

二方库 `com.alibaba.jp.supply.purchase:jp-supply-purchase-client`；方法 `OrderAddressExtraInfoParser#getOrderIdFromDetailAddress` 从详细地址中提取订单（boID）信息。

### 订单管理

通过 **FBI 报表**实现，采购/逆向提供离线底表（正向、逆向各 2 人日），由数据团队加工。

### 依赖的外部技术方案

日本站交易正向/逆向技术方案（基础链路-交易，君奕/泽蓝）、TMW 物流平台架构（AIDC 供应链，齐放架构/野芳开发）。开发合计约 28 人日应用 + 4 人日数据 + 5 联调 + 10 测试。

关联：采购/履约的通用能力见 [[采购交易与履约链路.md]]；逆向与资损见 [[佣金结算与资损防控.md]]。

## 商品质量评测

《商品质量评测技术方案》：用短平快方式支撑**服饰、家装两个行业**的商品评测（含商品评测与风格评测）。

模块拆解：

1. **铺货任务准备**：行业待评测商品表（淘宝商品 ID、定价倍率）→ 每行业生成一个货通铺货任务。
2. **已铺货商品素材表**（师尹提供）：含淘宝商品 ID/SKUID、中/日文标题、主图（多张）、SKU 属性中/日文、SKU 价格（来自供货价）、SKU 属性图。
3. **待评测数据宽表** `jptao_seller.tb_supply_review_all`：`biz` 区分服饰/家装；字段含 item_id、title/title_jp、image_url_1~5、sku_id、sku_pv_value(_jp)、sku_image_url、sku_price_cny、pricing_multiple（加价倍率）、sku_price_jp（日元定价）。
4. **PC 评测工具**（笑里，前端方案）。
5. **评测结果合并**：多份 Excel 用 pandas 脚本合并（仅保留首个表头）→ 上传离线数仓（大文件用 MaxCompute Tunnel）。

## 对跨境分销平台依赖与剥离

《日本站对跨境分销平台的依赖及剥离方案》梳理日本站对**巴拿马分销平台**的依赖并给出剥离建议。

### 关键依赖（`jp-supply-operation-s` / `jp-supply-salespricing-s` 依赖）

| 业务域 | 关键服务/消息 | 提供应用 | 类型 | 剥离方案 |
| --- | --- | --- | --- | --- |
| 账号基础 | 主子账号、支付方式绑定 | ovs-pnm-account / ovs-pnm-distributor | 产品功能 | 底层数据在中台 UIC 可脱离；但若用 WF 仍只能依赖分销 |
| 铺货/供货价 | 分销渠道价变更消息、供货价读服务 | ovs-pnm-markting / ovs-pnm-item | MetaQ/HSF | 业务推渠道价转高佣，日本端直连 IC 读设价 |
| 供给/定价 | 海外类目收佣费率查询 | g-sellercenter-core | HSF | 业务提供收佣规则维表，自行实现 |
| 采购创单 | `PurchaseCreateService#createPurchase` | ovs-pnm-purchase | HSF | 参考分销代码重写，直连 GSP |
| 采购支付 | `GspOrderBatchPayService#batchPay`（iPay AB 余额代扣） | ovs-pnm-purchase | HSF | 重写，直连 GSP |
| 取消/详情 | `GspOrderSolution#cancelPurchase`、`PurchaseOrderQueryFacade#queryPurchaseOrder` | gsp-order | HSF | — |
| 退款 | `RefundOrderService#renderRefundOrder/applyRefundOrder/detailRefundOrder` | ovs-pnm-distributor | HSF | 重写，直连 GSP |
| 采购单状态变更 | `GSP_ORDER_TOPIC_PANAMA` | gsp-order | MetaQ | 驱动日本端发货 |
| 商家发货 | `GSP_TAOBAO_ORDER` | global-seller-common-s | MetaQ | — |

### 两套剥离方案

- **系统浅剥离（推荐）**：只剥离上层业务调用代码，核心采购能力仍用分销平台（分销商身份、支付管理、采购模式）。优势：技术成本低、模型不变、快；劣势：业务定制灵活性差、受巴拿马规则约束。
- **业务隔离深剥离**：按货通平台能力实现独立业务身份，与 AE TBC/Lzd TBC/巴拿马分销平行地对接货通原生能力。优势：业务全隔离、自主性强；劣势：成本高，下单模式/接口参数/底层数据模型都变，等同重建类 TBC 链路。

**技术建议：走系统浅剥离**。核心原因：业务模式决定日本站是二方分销商，产品链路与运营（分销工作台子账号登录、IM 与淘宝商家沟通等）对分销系统深度依赖，完全剥离改造巨大。保障要点：确保分销系统内部无专为日本站定制的逻辑，按统一标准保障；海外后续只承接所有分销商通用能力。

货通平台中的分销专有能力（`gsp-order`）包括：账号处理（强依赖分销账号模型、运费险）、价格处理（渲染比价/渠道价下单，方案中已划线弃用）、创单处理（留言/地址拼接/不支持重采/批量采购跨店满减/按淘宝单拆单）、支付处理（多渠道：支付宝/iPayAB/WF）、订单处理（超时关单）。

关联：分销平台能力与账号见 [[巴拿马跨境分销业务与产品总览.md]] 与 [[账号体系与开放平台.md]]。
